# 서버 자동 배포와 운영자 로그인을 들이면서 내린 결정 — 2026년 10월 2일 ~ 3일

## 이 서비스와 팀

**AskBuddy**는 카페 같은 작은 매장의 업무 인수인계를 돕는 서비스다.

- 점주가 업무 영상·음성·문서를 올리면 AI가 내용을 "업무 카드"로 정리한다.
- 직원이 채팅으로 물어보면, AI는 점주가 승인한 카드만 근거로 답한다. 모르면 점주에게 질문을 넘긴다.

서비스는 웹 화면(Vercel), 서버(AWS 가상 서버 한 대), 데이터베이스(Supabase) 세 부분으로 돌아간다.
개발은 차준혁과 김선재 두 사람이 한다. 이 문서의 결정은 차준혁이 내렸다.

이 문서는 [서버를 AWS로 옮긴 기록](20261002_server_migration.md)의 다음 이야기다.
옮긴 직후 남은 문제 두 가지가 출발점이었다.

1. 서버에 새 코드를 올리려면 사람이 서버에 접속해 손으로 명령을 쳐야 했다.
2. 서버 상태를 점검하는 진단 화면이 **로그인 없이** 열려 있었다. 이 화면은 호출할 때마다 AI를 실제로 불러서 돈이 들었고, 데이터베이스 주소·모델 이름 같은 운영 정보도 보여 줬다.

## 결정 1. 운영자는 "환경변수 속 계정 하나"가 아니라 데이터베이스의 사용자 역할로 둔다

**결정한 사람:** 차준혁

**상황**
- 진단 화면을 막는 가장 빠른 방법은 서버 설정에 비밀번호 하나를 넣고 그 비밀번호를 아는 사람만 들어오게 하는 것이었다.
- 하지만 나중에 고객 문의(CS)를 처리하는 기능을 만들면, 매장 소속이 아닌 "서비스 운영자" 계정이 어차피 필요하다.

**행동**
- 사용자 역할에 점주·직원 외에 **운영자**를 추가하기로 했다.
- 이번 범위는 **진단 화면 접근만**으로 좁혔다. 운영자가 매장 데이터를 어디까지 볼 수 있는지는 고객 문의 기능을 설계할 때 감사 기록과 함께 따로 정하기로 했다.

**설계 (AI 제안, 승인)**
- 운영자 로그인은 매장 로그인과 다른 종류의 출입증을 받는다. 그래서 운영자 출입증으로는 매장 데이터를 열 수 없고, 반대로 점주 출입증으로는 진단 화면을 열 수 없다.
- 요청마다 운영자 역할이 아직 유효한지 데이터베이스에서 다시 확인한다. 역할을 회수하면 이미 받은 출입증도 즉시 막힌다.
- 로그인 실패는 이유와 관계없이 같은 응답을 준다. 실패가 반복되면 잠시 막는다.
- 운영자 계정은 가입 화면으로 만들 수 없고, 서버에서 실행하는 전용 스크립트로만 만든다. 기존 점주 계정을 운영자로 바꿔 주지도 않는다.

**결과**
- 진단 화면은 운영자 로그인 뒤에만 열린다. 운영 서버에서 계정을 만들고 로그인까지 확인했다.

## 결정 2. 진단 화면이 잘못 안내하던 두 가지를 같이 고친다

**결정한 사람:** 차준혁 (범위에 포함)

**상황**
- 10월 2일 운영 데이터베이스에 구조 변경 17개가 빠져 있었는데, 진단 화면은 "데이터베이스 접속 주소를 확인하라"고 안내했다. 접속은 멀쩡했고 표가 없었던 것이다. 접속과 표 확인을 한 덩어리로 처리해서 생긴 오진이었다.
- 검색 점검은 보안 정리 때 로그인이 필요해진 경로를 로그인 없이 부르고 있어서 항상 실패로 나왔다.

**행동**
- 접속 확인과 표 확인을 나누고, 없는 표는 이름까지 보여 주게 했다.
- 검색 점검은 내부 검색 기능을 직접 부르게 했다. 운영 데이터베이스에 데모 매장이 없으면 실패가 아니라 "점검 생략"으로 표시한다.
- 점검에 드는 AI 비용은 "개발용"으로 따로 기록해 고객 운영비 계산에 섞이지 않게 했다.

**결과**
- 로컬에서 바로 효과가 보였다. 로컬 데이터베이스에 최근 구조 변경 몇 개가 빠져 있었는데, 새 진단 화면이 빠진 표 이름을 정확히 짚었다.

## 결정 3. 자동 배포의 조건과 순서

**결정한 사람:** 차준혁 (조건·백업·저장 위치) · 인증 방식과 서버 설정 관리는 AI 제안을 승인

**상황**
- 사람이 서버에 들어가 손으로 올리면 빼먹는 단계가 생긴다. 실제로 옮긴 직후 운영 데이터베이스에 구조 변경이 17개나 빠져 있었다.

**행동 (사람의 결정)**
- **테스트를 통과한 코드만** 운영에 올린다. 기본 브랜치에 코드가 들어가고 기존 자동 테스트가 성공했을 때만 배포가 시작된다.
- 데이터베이스 구조 변경은 배포 때 **자동으로 적용**한다. 대신 적용 직전에 **매번 백업**을 남긴다.
- 백업은 AWS의 비공개 파일 저장소(S3)에 두고 **30일 뒤 자동으로 지운다.** 코드 저장소가 공개라서, 깃허브에 백업 파일을 남기면 누구나 내려받을 수 있기 때문이다.
- 서버 접속은 앞서 정한 대로 원격 접속 포트 없이 클라우드 관리 도구로만 한다.

**설계 (AI 제안, 승인)**
- 깃허브가 AWS에 들어갈 때 **오래 쓰는 비밀 키를 깃허브에 저장하지 않는다.** 배포가 돌 때마다 깃허브가 "이 저장소의 이 환경에서 도는 작업"이라는 서명된 증명을 내밀고, AWS가 확인한 뒤 1시간짜리 임시 권한을 준다.
- 배포용 권한은 백업을 **올리기만** 할 수 있다. 읽기·지우기 권한이 없어서, 배포 권한이 새도 기존 백업을 지우거나 빼 갈 수 없다.
- 서버 설정 파일(컨테이너 구성, 인증서 처리)을 코드 저장소에서 관리한다. 비밀값 파일만 서버에 따로 둔다.
- 순서는 "백업 → 구조 변경 → 서버 재시작 → 정상 응답 확인"이다. 한 단계라도 실패하면 거기서 멈춘다. 자동 되돌리기는 하지 않고, 되돌릴지는 사람이 판단한다.

**결과**
- 10월 3일 첫 전체 배포가 성공했다. 백업 파일(약 800KB)이 저장소에 올라갔고, 구조 변경 적용과 서버 재시작, 정상 응답 확인까지 사람 손 없이 끝났다.

## 결정 4. 구현은 AI 에이전트에게 맡기되, 기록과 반영은 사람이 쥔다

**결정한 사람:** 차준혁

**행동**
- 설계 문서와 계획 문서를 기준으로, AI가 작업 단위마다 구현을 맡기고 다른 AI가 검토하는 방식으로 개발하게 했다.
- 커밋·병합·운영 반영은 차준혁이 직접 했다. 운영 데이터베이스 비밀번호를 쓰는 작업은 AI가 실행하지 못하게 막혀 있었다. 백업이 실제로 되는지는 첫 자동 배포에서 확인됐다.

**결과**
- 검토 단계에서 실제 구멍이 잡혔다. 동시에 로그인 요청을 여러 개 보내면 "실패 반복 시 차단"을 우회할 수 있었다. 계획 문서에 적힌 코드 그대로 만들었는데도 생긴 문제였다.
- 계획이 틀린 곳도 드러났다. 이 경험은 아래 "운영 반영 중 만난 문제"에 적었다.

---

## 운영 반영 중 만난 문제

### 1. 서버 디스크가 꽉 차서 접속도 서비스도 멈췄다

**상황**
- 서버 접속 도구가 알 수 없는 오류를 냈다. 서버 쪽 관리 프로그램이 오래된 탓으로 보고 업데이트 명령을 보냈지만, 아무 일도 하지 않는 명령조차 실패했다.
- 서버 화면 기록을 보니 원인은 **디스크 공간 부족**이었다. 디스크가 8GB뿐인데, 서버에서 프로그램을 빌드할 때마다 쌓이는 중간 파일이 공간을 다 채웠다.

**행동 (차준혁의 결정)**
- 디스크를 20GB로 늘리기로 했다. 월 1달러 정도 더 든다. 자동 배포도 서버에서 빌드하므로 8GB로는 다시 찰 것이었다.
- 디스크를 늘린 뒤 재부팅했지만, 공간이 없어 늘어난 디스크에 맞추는 작업까지 실패했고 서비스가 아예 내려갔다. 관리 도구로도 들어갈 수 없었다.
- 그래서 **닫아 두었던 원격 접속 포트를 자기 IP에만, 작업하는 동안만 열었다.** 일회용 열쇠로 접속해 공간을 정리하고 디스크를 키운 뒤 포트를 바로 닫았다.

**결과**
- 서비스가 돌아왔다. 이후 배포 때마다 오래된 빌드 중간 파일과 안 쓰는 이미지를 지우도록 했다. 서버 전환 전 확인 목록에는 "디스크 여유 5GB 이상"을 넣었다.

**배운 점**
- 디스크가 차면 서비스만 멈추는 게 아니라 **고치러 들어가는 길까지 막힌다.** 평소에 닫아 둔 문을 비상시에 잠깐 여는 절차를 알고 있는 게 중요했다.

### 2. 문서에 적힌 순서가 실제로는 불가능했다

**상황**
- 계획 문서에는 "기본 브랜치에 병합하기 전에 서버를 새 설정으로 전환하라"고 적혀 있었다.
- 차준혁이 서버에서 그대로 따라 하다가 새 설정 폴더가 없다는 것을 발견했다. 새 설정 파일은 병합해야 서버가 받아 올 수 있는데, 문서는 그보다 먼저 쓰라고 하고 있었다.

**행동**
- 순서를 바꿨다. 먼저 배포 권한 설정을 **비워 둔 채로** 병합한다. 그러면 자동 배포는 첫 단계에서 아무것도 건드리지 않고 멈춘다. 그다음 서버를 전환하고, 마지막에 권한을 채워 배포를 수동으로 실행했다.
- 서버 전환 때 "옛 설정 폴더를 지우라"는 문서에 차준혁이 의문을 제기했다. 바로 지우는 대신 이름만 바꿔 두고, 문제가 없으면 나중에 지우는 것으로 바꿨다.

**결과**
- 병합 직후 자동 배포가 첫 단계에서 의도대로 멈췄고, 서버와 데이터베이스는 바뀌지 않았다.

### 3. 클라우드 권한 설정에서 세 군데가 어긋났다

**상황**
- 차준혁이 클라우드 권한 설정을 마친 뒤, 다음 단계로 넘어가기 전에 "제대로 됐는지 먼저 확인하라"고 AI에게 시켰다. AI가 설정값을 읽어 보니 세 군데가 문서와 달랐다.
  1. 관리 화면의 기본값이 "기본 브랜치에서 돈 작업"을 믿도록 잡혀 있었다. 배포는 "배포 환경" 기준으로 신원을 증명하므로 맞지 않았다.
  2. 백업 저장소 이름이 권한 설정과 실제 저장소에서 서로 달랐다. 저장소 이름 끝에 지역 표시가 자동으로 붙었기 때문이다.
  3. 정상 응답을 확인할 주소 설정이 빠져 있었다.
- 고친 뒤 배포를 실행하자 권한을 받는 단계에서 2분 가까이 재시도하다 실패했다. 이 저장소는 깃허브 설정상 신원 증명에 조직·저장소의 **숫자 번호**가 붙는데, 권한 설정에는 이름만 적혀 있었다.

**행동**
- 실제로 날아오는 값을 확인해 권한 설정을 맞췄다. 숫자 번호가 붙는 방식은 저장소 이름이 바뀌거나 누가 같은 이름의 저장소를 새로 만들어도 권한을 가로챌 수 없어서 오히려 더 안전하다.

**결과**
- 다음 실행에서 모든 단계가 성공했다.

**배운 점**
- 설정을 마친 뒤 **다음 단계 전에 실제 값을 다시 읽어 확인**한 덕분에, 실패 원인 세 개를 배포 전에 한꺼번에 잡았다. 마지막 하나는 실행해 봐야 드러났다.

## 결정 5. 무중단 배포는 지금 하지 않고, 방법만 정리해 둔다

**결정한 사람:** 차준혁

**상황**
- 지금 방식은 배포할 때 서버가 몇 초 동안 응답하지 않는다.
- 차준혁은 무중단 배포를 하려면 쿠버네티스나 AWS의 컨테이너 관리 서비스를 써야 하는지 물었다.

**행동**
- 서버 한 대로도 할 수 있고, 그런 도구는 서버가 여러 대이거나 자동 확장이 필요할 때 쓰는 것이라는 설명을 들었다. 관리 서비스는 관리비만 월 70달러 이상이라 지금 규모에는 맞지 않는다.
- 지금은 몇 초 끊기는 것을 받아들이고, 나중에 할 방법과 먼저 확인할 것을 [계획 문서](../release/plan/API_ZERO_DOWNTIME_DEPLOY_PLAN.md)로 남기기로 했다.

## 아직 남은 일

- 서버 안의 옛 설정 폴더는 이름만 바꿔 두었다. 며칠 문제없으면 지운다.
- 로그인 차단이 사실상 "이메일 단위"로 동작한다. 서버 앞단을 거치며 사용자 IP가 가려지기 때문이다. 운영자 이메일을 아는 사람이 15분 동안 운영자 로그인을 막을 수 있다. 앞단을 믿고 원래 IP를 받는 설정과 전체 로그인 요청 수 제한은 후속 과제로 남겼다.
- 배포 실패 알림은 깃허브 기본 이메일뿐이다.
