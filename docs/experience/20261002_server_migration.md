# 무료 서버가 끊긴 뒤 운영 서버를 옮기면서 내린 결정 — 2026년 9월 27일 ~ 10월 2일

## 이 서비스와 팀

**AskBuddy**는 카페 같은 작은 매장의 업무 인수인계를 돕는 서비스다.

- 점주가 업무 영상·음성·문서를 올리면 AI가 내용을 "업무 카드"로 정리한다.
- 직원이 채팅으로 물어보면, AI는 점주가 승인한 카드만 근거로 답한다. 모르면 점주에게 질문을 넘긴다.

서비스는 세 부분으로 나뉘어 돌아간다.

| 부분 | 하는 일 | 옮기기 전 위치 |
|---|---|---|
| 웹 화면 | 점주·직원이 보는 화면 | Vercel (웹 호스팅 서비스) |
| 서버 | 로그인, 검색, AI 호출, 업로드 처리 | **Railway** (서버 호스팅 서비스) |
| 데이터베이스와 파일 저장소 | 카드, 질문, 올린 원본 파일 | Supabase (데이터베이스 호스팅 서비스) |

개발은 차준혁과 김선재 두 사람이 한다. 이 문서의 결정은 대부분 차준혁이 내렸다.

---

## 배경: 무료 서버가 갑자기 끊겼다

**상황**
- 2026년 9월 27일, 서버를 올려 두던 Railway의 무료 체험 기간이 끝나 서버가 멈췄다.
- 웹 화면과 데이터베이스는 다른 곳에 있어서 살아 있었지만, 그 둘을 잇는 서버가 없어서 서비스 전체를 쓸 수 없었다.
- 개발은 각자 컴퓨터에서 하고 있어서 개발 자체는 멈추지 않았다. 문제는 시연과 실제 사용자 테스트였다.

**과제**
- 개발 작업에 영향을 주지 않으면서, 가능하면 돈을 들이지 않고 서버를 다시 살려야 했다.

---

## 결정 1. 서버만 옮기고 나머지는 그대로 둔다

**결정한 사람:** 차준혁 (방향 결정) · 구조 분석은 AI 제안

**상황**
- 서버를 옮기는 김에 데이터베이스까지 옮길지, 다른 종류의 데이터베이스(MySQL이나 NoSQL)로 바꿀지도 함께 고민했다.
- AI가 코드를 조사해 보니, 현재 코드는 데이터베이스의 특정 기능에 깊이 기대고 있었다. 검색에 쓰는 벡터 기능, 저장한 결과를 바로 돌려받는 문법, 중복을 처리하는 문법이 수십 곳에서 쓰이고 있었다.
- 다른 종류로 바꾸면 "저장소만 교체"가 아니라 몇 주짜리 재작성이 되고, 그동안 본 개발이 멈춘다.

**행동**
- 차준혁은 데이터베이스는 그대로 두고 서버만 옮기기로 했다.
- 근거가 된 사실: 이 팀은 설계 초기에 데이터베이스 회사의 로그인 기능, 브라우저에서 데이터베이스를 직접 읽는 기능, 실시간 구독 기능을 **일부러 쓰지 않기로** 정해 두었다. 덕분에 데이터베이스 회사에 얕게 묶여 있어서, 서버를 어디로 옮기든 접속 주소만 바꾸면 됐다.

**결과**
- 옮길 대상이 "서버 한 대"로 줄었다. 코드는 한 줄도 바꾸지 않았다.

**배운 점**
- 초기에 외부 서비스의 편의 기능을 덜 쓰기로 한 결정이, 나중에 서비스를 옮길 때 비용을 크게 줄여 줬다.

---

## 결정 2. 서버리스 대신 계속 켜져 있는 서버를 쓴다

**결정한 사람:** 차준혁 (승인) · 판단 근거는 AI 분석

**상황**
- 요청이 올 때만 켜지는 "서버리스" 방식은 대기 중 비용이 0원이라 매력적이었다.
- 하지만 이 서버는 응답을 보낸 **뒤에도** 일을 한다. 업로드한 영상과 음성을 몇 분씩 처리하고, 직원이 모르는 질문을 하면 점주 폰에 알림을 보낸다. 한 시간마다 오래된 기록을 지우는 작업도 서버 안에서 계속 돈다.
- 서버리스는 응답을 보내면 서버를 재우거나 꺼 버린다. 그러면 이 작업들이 조용히 멈춘다. 특히 "직원이 묻는다 → 점주에게 알림" 흐름은 이 서비스의 핵심이라 끊기면 안 됐다.

**행동**
- 서버리스를 쓰려면 작업 대기열과 예약 실행 구조로 다시 짜야 한다는 설명을 듣고, 차준혁은 지금은 계속 켜져 있는 가상 서버 한 대에 그대로 올리기로 했다.

**결과**
- 구조 변경 없이 같은 코드를 그대로 쓸 수 있게 됐다. 사용자가 많아져 확장이 필요해지면 그때 구조 변경을 따로 검토하기로 남겨 뒀다.

## 결정 3. Oracle 무료 서버를 먼저 시도했다가 AWS로 바꿨다

**결정한 사람:** 차준혁

**상황과 행동**
1. **Oracle Cloud 무료 서버를 골랐다.** 메모리를 넉넉히 주는 무료 서버가 있었기 때문이다. 지역은 한국에서 가까운 오사카로 정했다.
2. **가입 직후 계정 준비가 끝나지 않아** 일부 기능이 잠겨 있었다.
3. **무료 서버의 자리가 없었다.** 오사카 지역에 남은 무료 서버가 없다는 오류가 계속 났다. 크기를 줄여도 마찬가지였다.
4. **임시로 아주 작은 무료 서버를 만들었다.** 메모리가 1GB뿐이라 영상 처리에는 부족했다.
5. **AWS로 바꿨다.** AWS 무료 이용 기간이 75일 남아 있었다. 서울 지역에 서버를 둘 수 있어서, 서울에 있는 데이터베이스와도 가까웠다.

**판단 기준**
- 차준혁은 "여러 클라우드를 옮겨 다니면 코드가 바뀌는가"를 먼저 확인했다. 가상 서버 한 대에 같은 방식으로 올리면 코드는 바뀌지 않고, 바뀌는 건 서버 주소와 방화벽 설정뿐이라는 답을 듣고 AWS로 옮겼다.
- 75일 뒤에도 다시 옮길 수 있도록, AWS 전용 서비스는 쓰지 않고 가상 서버 한 대만 쓰기로 했다.

**결과**
- 서울 지역 AWS 서버에 서비스가 올라갔다.

**배운 점**
- 무료 클라우드는 "무료"보다 "지금 자리가 있는가"가 먼저 문제였다. 서비스가 특정 클라우드에 묶이지 않게 만들어 두면, 자리가 없을 때 다른 곳으로 빨리 넘어갈 수 있다.

## 결정 4. 두 사람의 클라우드 계정과 권한을 나눴다

**결정한 사람:** 차준혁 (계정 두 개 생성) · 권한 설계는 AI 제안

**상황**
- 차준혁과 김선재 두 사람이 서버를 관리해야 했다.
- 예전에 클라우드 수업에서는 두 계정 모두에 전체 관리자 권한을 줬다.

**행동**
- 가입할 때 만든 최상위 계정은 평소에 쓰지 않고, 사람마다 계정을 따로 만들었다. 두 계정 모두 2단계 인증을 붙였다.
- 계정 주인(차준혁)은 관리자 권한, 함께 개발하는 사람(김선재)은 서버 관리와 접속에 필요한 권한만 받는 구성을 AI가 제안했다.
- 실수로 비싼 서버를 만들지 않도록 "무료 크기의 서버만 만들 수 있다"는 제한도 함께 제안됐다.

**결과**
- 누가 무엇을 했는지 기록으로 구분할 수 있게 됐다. 김선재 계정의 실제 권한 구성이 제안대로 적용됐는지는 이 문서를 쓰는 시점에 확인하지 못했다.

---

## 결정 5. 서버 접속 문을 닫고, 클라우드 관리 도구로만 들어간다

**결정한 사람:** 차준혁 (예전 수업 정리 노트에서 이 방식을 골라 적용)

**상황**
- 차준혁은 예전 클라우드 수업에서 정리한 노트를 가져왔다. 그 노트는 쿠버네티스를 올리기 위한 복잡한 네트워크 구성이라, 서버 한 대짜리 지금 상황에는 절반 정도만 맞았다.
- 노트에는 "원격 접속 포트를 전 세계에 열어 두면 몇 분 안에 자동 공격 프로그램이 찾아와 비밀번호를 대입한다"는 내용과, 그 대안으로 **포트를 하나도 열지 않고 클라우드 관리 도구로 접속하는 방법**이 정리돼 있었다.

**행동**
- 이미 만든 서버에 그 관리 도구용 권한을 나중에 붙여서 이 방식으로 접속했다.
- 외부에 여는 문은 웹 요청용(일반·암호화 통신) 두 개만 남겼다.
- 노트에 있던 "비밀번호로 원격 로그인 허용"은 수업 과제의 요구였을 뿐이라 따르지 않았다. 이 서버에는 AI 서비스 키와 데이터베이스 관리 키가 들어 있어서 뚫리면 피해가 크다.

**결과**
- 접속용 열쇠 파일을 두 사람이 주고받을 필요가 없어졌고, 접속 기록이 클라우드 계정 단위로 남게 됐다.

## 결정 6. 도메인을 샀다

**결정한 사람:** 차준혁

**상황**
- 웹 화면은 암호화 주소(https)인데, 서버가 IP 주소만 있으면 브라우저가 암호화되지 않은 요청을 막는다. 서버에도 암호화 인증서가 필요했고, 인증서는 보통 도메인 이름에 발급된다.
- IP를 이름처럼 바꿔 주는 무료 서비스로도 당장은 해결할 수 있었다. 다만 무료 주소는 운영 주체가 작고, 보안 필터에 막히거나 인증서 발급 한도를 다른 사용자와 나눠 쓰는 문제가 있었다.
- 더 큰 이유도 있었다. 점주 폰의 알림 구독과 "홈 화면에 추가"한 앱은 **웹 주소에 묶여 있다.** 실제 점주가 생긴 뒤 웹 주소를 바꾸면, 점주들이 알림을 다시 켜야 하고 그 사이 "직원 질문 → 점주 알림" 흐름이 끊긴다.

**행동**
- 차준혁은 국내 등록업체에서 `askbuddy.kr` 도메인을 샀다.
- 도메인 하나로 웹은 `askbuddy.kr`, 서버는 `api.askbuddy.kr`로 나눠 쓰기로 했다. 서버 주소는 고정 IP에 연결했다.

**결과**
- 서버를 다른 클라우드로 옮겨도 이제는 이름이 가리키는 IP 한 줄만 바꾸면 된다. 웹 화면은 다시 배포할 필요가 없다.

**배운 점**
- 도메인은 "보기 좋은 주소"보다 "나중에 바꾸기 어려운 것을 지금 고정하는 일"에 가까웠다.

## 옮기면서 만난 문제

| 문제 | 원인 | 처리 |
|---|---|---|
| 코드 저장소 전용 열쇠를 등록할 수 없었다 | 팀 조직 정책으로 그 기능이 꺼져 있었다 | 저장소가 공개 상태라 열쇠 없이 받았다 |
| 서버가 시작하자마자 꺼지기를 반복했다 | 데이터베이스 접속 주소가 맞지 않아 "그런 프로젝트를 모른다"는 오류가 났다 | 데이터베이스 관리 화면에서 접속 주소를 그대로 다시 복사해 넣었다 |
| 서버가 떠도 회원가입에서 "서버에 연결할 수 없습니다"가 났다 | 요청이 서버에 도착하지 않았다. 웹이 옛 서버 주소를 쓰거나, 서버가 새 웹 주소를 허용 목록에 넣지 않은 경우가 후보다 | **이 문서를 쓰는 시점에 아직 해결 중이다** |
| 서버 기록에 "테이블이 없다"는 오류가 남았다 | 운영 데이터베이스에 최근 구조 변경이 적용되지 않았다 | **적용 전이다.** 무엇이 빠졌는지 먼저 확인한 뒤 적용하기로 했다 |

## 아직 남은 일

- 회원가입 연결 오류의 원인 확인과 해결
- 운영 데이터베이스에 빠진 구조 변경 적용
- 서버 진단 기능 중 하나가 로그인 없이 호출되고, 호출할 때마다 AI 비용이 드는 문제 정리
- AWS 무료 기간(75일)이 끝나기 전에 다음 서버 위치 결정. 이때 데이터베이스는 그대로 두고 서버만 옮긴다는 원칙을 유지한다.
