# 영상 일부 실패 복구와 두 개발 영역 연결 준비에서 사람이 내린 결정 — 2026년 9월 24일~27일

## 이 서비스와 팀

**AskBuddy**는 카페 같은 작은 매장의 업무 인수인계를 돕는 서비스다.

- 점주가 업무 영상·음성·문서를 올리면, AI가 내용을 읽어 "업무 카드"로 정리한다. 예: "아메리카노 만드는 법" 카드.
- 점주가 카드를 확인하고 승인하면, 그 카드가 직원에게 공개된다.
- 신입 직원이 채팅으로 물어보면, AI는 **점주가 승인한 카드만 근거로** 답한다. 근거가 없으면 모른다고 하고 점주에게 질문을 넘긴다.

개발은 두 사람이 영역을 나눠 맡는다.

| 담당자 | 맡은 영역 |
|---|---|
| 차준혁 | **자료 등록 영역**: 올린 자료 읽기 → 카드 만들기 → 점주 승인 → 공개 |
| 김선재 | **질문 답변 영역**: 직원 질문 → 공개된 카드 찾기 → 답변과 근거 표시 → 모르면 점주에게 넘기기 |

두 영역은 "카드가 공개되는 순간"에 맞물린다. 자료 등록 쪽이 카드를 공개하면, 질문 답변 쪽은 그 카드를 검색할 수 있게 준비해야 한다.

## 결정 1. 합치기 전에, 바뀐 코드 전체를 한 번 더 검토한다

**결정한 사람:** 차준혁

**상황**
- 긴 영상은 여러 조각으로 나눠 AI가 읽는다. 그런데 일부 조각만 실패한 영상에 세 가지 문제가 있었다.
  - 작업 상세 화면이 오류로 열리지 않았다.
  - 작업 전체가 "성공"으로 표시됐다.
  - 실패한 조각을 다시 읽을 방법이 없었다.
- 영상을 읽는 동안 데이터베이스 연결을 계속 붙잡고 있어서, 동시에 여러 작업이 돌면 서로 기다리다 멈출 위험도 있었다.
- 이 문제들을 네 조각으로 나눠 고쳤고, 조각마다 따로 검토를 통과했다.

**과제**
- 이 수정을 공용 코드에 바로 합칠지, 그 전에 확인을 더 할지 정해야 했다.

**행동**
- 차준혁은 "합치기 전에 **네 조각을 한꺼번에** 다시 검토하자"고 정했다.
- 조각별 검토는 자기 조각만 본다. 조각과 조각이 맞물리는 부분은 아무도 보지 않는다.

**결과**
- 조각별 검토가 모두 놓친 **심각한 문제**가 전체 검토에서 나왔다.
  - 이 서비스는 AI를 부를 때마다 비용을 기록한다. 이 기록에는 "같은 호출은 한 번만 적는다"는 규칙이 있다.
  - 그런데 실패한 조각을 다시 읽을 때, 시스템은 이 호출을 처음 호출과 **같은 호출로 취급**했다.
  - 그래서 다시 읽기가 비용 기록 단계에서 막혔다. 최악의 경우 내용은 읽었는데 카드는 안 만들어진 채 "성공"으로 표시될 수 있었다.
- 테스트는 비용 기록을 흉내만 내는 가짜 부품을 썼기 때문에 이 규칙을 거치지 않았다. 그래서 테스트는 모두 통과했었다.
- 차준혁은 "합치기 전에 이것부터 고친다"고 승인했다. 고치는 구체적인 방법은 AI가 제안했다.

**배운 점**
- 조각마다 검토를 통과해도, 조각이 맞물리는 곳은 따로 봐야 한다.
- 가짜 부품으로 통과한 테스트는, 진짜 부품에 있는 규칙까지 지켜진다는 증거가 아니다.

## 결정 2. 동료와 같은 문제를 고쳤다면, 동료의 수정을 기준으로 다시 쌓는다

**결정한 사람:** 차준혁

**상황**
- 첫 번째 수정이 공용 코드에 들어간 뒤, 김선재가 그 수정을 **따로 검토해서** 문제 세 개를 더 찾았다. 그리고 그 수정을 공용 코드에 먼저 올렸다.
- 그중 하나는 차준혁의 두 번째 수정과 **같은 문제를 같은 방식으로** 고친 것이었다.
  - 그 문제: 카드 저장과 "어느 조각이 실패했는지" 기록이 따로 저장됐다. 그래서 그 사이에 오류가 나면 카드가 두 번 만들어질 수 있었다.
- 그래서 차준혁의 두 번째 수정을 공용 코드에 합치려 하자, 같은 줄을 서로 다르게 고친 **충돌**이 났다.

**과제**
- 충돌을 어떻게 풀지 정해야 했다.
  - 방법 1: 차준혁의 작업 위에 공용 코드를 합치면서 충돌 부분만 손본다.
  - 방법 2: 차준혁의 옛 작업을 버리고, 최신 공용 코드에서 새로 시작한다.

**행동**
- 차준혁은 **방법 2**를 골랐다.
  1. 김선재의 수정이 들어간 최신 공용 코드에서 새 작업 공간을 만들었다.
  2. 김선재의 수정과 겹치지 않는 부분만 옮겼다. 결정 1에서 찾은 비용 기록 문제의 수정이다.
  3. 겹치는 부분은 **김선재의 코드를 그대로** 썼다.
  4. 옛 작업 공간과 옛 합치기 요청은 닫고 지웠다. 닫을 때 "새 요청으로 대체한다"는 기록을 남겼다.

**결과**
- 새 합치기 요청은 김선재의 구조를 그대로 두고, 빠진 수정 하나만 얹은 작은 변경이 됐다.
- 같은 문제를 두 가지 방식으로 고친 코드가 섞이는 일을 피했다.
- 자동 테스트 950개가 통과했다.

**배운 점**
- 두 사람이 같은 문제를 고쳤다면, **이미 공용 코드에 들어간 쪽을 기준**으로 삼는다.
- 충돌을 억지로 합친 큰 변경보다, 새로 쌓은 작은 변경이 검토하기 쉽다.

## 결정 3. 두 영역을 연결하기 전에, 코드보다 "설명 자료"를 먼저 맞춘다

**결정한 사람:** 김선재(요청), 차준혁(수용)

**상황**
- 점주가 카드를 승인하는 순간과 직원 검색에 반영되는 순간이 **아직 연결되지 않았다.**
  - 질문 답변 쪽(김선재)에는 "검색용 데이터를 미리 준비해 두고, 공개하는 순간에 켜는" 기능이 이미 있다.
  - 자료 등록 쪽(차준혁)의 승인 버튼은 이 기능을 쓰지 않는다. 카드를 옛 방식의 검색 목록에 바로 넣는다.
- 게다가 "어느 카드의 몇 번째 수정본을 공개하나"를 주고받는 기존 형식이 모호했다. 숫자만 나열돼 있어서, 어느 숫자가 어느 카드 것인지 알 수 없었다.

**과제**
- "카드가 공개되는 순간"을 두 사람이 어떻게 맞출지 약속을 정해야 했다.

**행동**
- 김선재는 코드를 짜기 전에 차준혁에게 **자료 다섯 가지**를 요청했다.
  1. 카드의 "수정 중인 판", "점주가 검수한 판", "공개된 판"이 어디에 어떻게 저장되고, 어떻게 비교되는지
  2. 카드 두 장 중 한 장만 고쳤을 때, 검색 준비 요청과 "공개 후 전체 카드 목록"이 어떻게 생기는지 예시
  3. 승인할 때 도는 코드가 어디서 시작하고 끝나는지, 그 안의 어디에 "검색 데이터 켜기"를 넣을지
  4. 점주 답변을 처리한 결과 네 가지의 예시
     - 기존 카드에 이미 있는 내용이라 연결만 함
     - 점주의 추가 확인이 필요함
     - 새 카드로 공개함
     - 실패함
  5. "추가 확인 필요"로 남은 답변을 점주가 나중에 승인할 때, 원래 질문과 어떻게 다시 이어지는지
- 아직 만들지 않은 부분은 **"예정"이라고 표시**해 달라고 했다.
- 차준혁은 이 요청대로 자료를 정리해 공유했다.

**결과**
- "예정" 표시를 하다 보니, 이미 있는 것과 없는 것이 분명해졌다.
- **가장 큰 빈칸이 드러났다.**
  - 질문 답변 쪽은 답변 근거를 "이 카드의 이 줄"처럼 정확히 가리키려고, 카드를 "구역과 사실 한 줄 한 줄" 단위로 받아야 한다.
  - 그런데 자료 등록 쪽은 카드를 "제목 + 본문" 통글로만 저장한다.
  - 그래서 이 조립 단계를 먼저 만들어야 두 영역을 연결할 수 있다.
- **설계 공백도 하나 발견됐다.** "추가 확인 필요"로 끝난 점주 답변을 나중에 승인해도, 지금은 질문 답변 쪽에 알릴 방법이 없다. 두 사람이 함께 정해야 할 문제로 남았다.

**배운 점**
- 두 사람이 나눠 만든 시스템은 **맞물리는 곳의 약속을 먼저 글로 맞춰야** 한다.
- "아직 안 만든 것은 예정으로 표시"라는 요청 하나로 할 일의 순서가 자연스럽게 정해졌다.

## 결정 4. 작업 결과를 저장하고 공유하는 시점은 사람이 정한다

**결정한 사람:** 차준혁 (9월 14일부터 지켜 온 작업 원칙)

**상황**
- AI에게 여러 단계의 코드 작업을 맡기면, AI가 단계마다 알아서 저장하고 공유하려는 흐름이 생긴다.

**과제**
- 무엇이 언제 공용 기록에 남는지를 사람이 통제해야 했다.

**행동**
- "작업 결과의 저장과 공유는 사람이 명시적으로 요청할 때만 한다"는 원칙을 이번에도 지켰다.
- AI는 변경을 저장하지 않은 채로 두고 보고만 했다. 저장과 공유는 차준혁이 요청할 때만 했다.

**결과**
- 검토 결과를 보고 "고친 뒤 올릴지, 지금 올릴지"를 사람이 매번 판단할 수 있었다.
- 결정 1과 결정 2를 내릴 판단 시점이 이 원칙 덕분에 생겼다.

**배운 점**
- 기록 시점을 사람이 쥐고 있으면 "검토 → 판단 → 기록" 순서를 지킬 수 있다.

## 이 문서에 적지 않은 것

아래는 사람이 아니라 AI가 정한 것이라 뺐다.
- 실패한 조각만 다시 읽는 방식과 그 세부 규칙
- 비용 기록 문제를 푼 구체적인 방법 (다시 읽을 때마다 호출에 "몇 번째 실행인지" 표시를 붙임)
- 연결 약속에 대한 자료 등록 쪽의 제안들. 아직 두 사람이 합의하기 전이다.
