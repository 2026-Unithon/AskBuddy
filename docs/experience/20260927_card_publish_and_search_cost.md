# 카드 공개 연결과 검색 비용에서 사람이 내린 결정 — 2026년 9월 27일

## 이 서비스와 팀

**AskBuddy**는 카페 같은 작은 매장의 업무 인수인계를 돕는 서비스다.

- 점주가 업무 영상·음성·문서를 올리면 AI가 내용을 "업무 카드"로 정리한다.
- 점주가 카드를 확인하고 승인하면 직원에게 공개된다.
- 직원이 채팅으로 물어보면, AI는 **점주가 승인한 카드만 근거로** 답한다. 모르면 점주에게 질문을 넘기고, 점주의 답이 다시 지식이 된다.

개발은 두 사람이 영역을 나눠 맡는다.

| 담당자 | 맡은 영역 |
|---|---|
| 차준혁 | **자료 등록 영역**: 자료 읽기 → 카드 만들기 → 점주 승인 → 공개 |
| 김선재 | **질문 답변 영역**: 직원 질문 → 공개 카드 검색 → 답변과 근거 표시 → 모르면 점주에게 넘기기 |

두 영역은 "카드가 공개되는 순간"에 맞물린다. 카드가 공개되면, 질문 답변 쪽은 그 카드를 찾을 수 있도록 **검색용 데이터**(카드 글을 AI가 숫자 목록으로 바꾼 것. 이 변환을 "임베딩"이라고 한다)를 준비해야 한다.

## 결정 1. 두 영역을 잇는 약속은 자료 등록 쪽의 제안서대로 간다

**결정한 사람:** 차준혁

**상황**
- 점주가 승인해도 질문 답변 쪽 검색에 반영되지 않았다. 승인 버튼이 옛 방식의 검색 목록에만 카드를 넣었기 때문이다.
- 두 사람은 "카드가 공개되는 순간"의 약속을 정해야 했다. 김선재가 자료 다섯 가지를 요청했고, 차준혁 쪽은 그에 대한 제안서를 만들었다.
  - 카드별로 "점주가 검수한 판"과 "공개할 판"을 짝지어 전달한다.
  - 공개할 때는 바뀐 카드와 그대로인 카드를 합친 전체 목록을 만든다.
  - 공개와 검색 반영을 한 번에 처리하고, 하나라도 실패하면 전부 취소한다.

**과제**
- 상대와 세부를 다시 협의할 때까지 구현을 멈출지, 제안대로 먼저 만들지 정해야 했다.

**행동**
- 차준혁은 "제안서대로 먼저 간다. 나중에 김선재와 이야기해서 바뀌는 게 있으면 그때 반영한다"고 정했다.

**결과**
- 협의를 기다리지 않고 공개 연결을 끝까지 만들었다. 점주 승인, 점주 답변 반영, 나중 승인, 제외·복원이 모두 같은 공개 절차를 거친다.
- 가짜 자료가 아닌 실제 데이터베이스로 시험하는 과정에서, 가짜 부품으로는 보이지 않던 오류 네 개를 찾아 고쳤다.

**배운 점**
- 상대를 기다리는 동안 멈추기보다 "제안대로 만들고 바뀌면 고친다"로 가면 진행이 막히지 않는다. 다만 제안은 문서로 남겨 둬야 나중에 무엇이 바뀌었는지 추적할 수 있다.

## 결정 2. 상대 영역의 코드는 건드리지 않고, 필요한 변경은 인계 문서로 넘긴다

**결정한 사람:** 차준혁

**상황**
- 공개 연결을 끝까지 만들려면 두 군데가 질문 답변 쪽(김선재) 코드에 걸렸다.
  - 점주가 "검토 대기"로 남은 답변을 나중에 승인하는 버튼
  - 그 승인을 질문 답변 쪽에 알리는 기능
- 팀 규칙은 "상대가 주로 맡은 파일은 동시에 고치지 않는다"다.

**과제**
- 상대 코드까지 직접 고쳐 빨리 끝낼지, 자기 영역만 고치고 나머지를 넘길지 정해야 했다.

**행동**
- 차준혁은 "자기 영역 파일만 고치고, 상대가 바꿔야 할 것은 인계 자료로 함께 준비한다"를 골랐다.

**결과**
- 자료 등록 쪽은 필요한 기능을 모두 만들고, 상대가 연결할 자리를 함수 형태로 비워 두었다.
- 인계 문서에 상대가 바꿔야 할 곳을 "무엇을, 왜, 어느 위치, 준비된 기능" 형식으로 정리했다.
- 서로의 코드가 동시에 바뀌며 충돌하는 일을 피했다.

**배운 점**
- 영역 경계를 지키면 속도는 조금 느려지지만, 누가 무엇을 책임지는지 흐려지지 않는다.

## 결정 3. 점주 답변도 "출처"로 인정하되, 상대가 준비될 때까지는 공개하지 않는다

**결정한 사람:** 차준혁

**상황**
- 이 서비스는 "공개된 지식은 모두 출처를 가진다"는 원칙이 있다.
- 그런데 점주가 채팅 질문에 답해서 생긴 카드는 원본 자료 파일이 없다. 기존 데이터 구조는 출처를 "자료 파일"로만 받았다.

**과제**
- 점주 답변 카드를 어떻게 공개할지 정해야 했다. 선택지는 셋이었다.
  - 자료 파일이 있는 카드만 먼저 공개한다.
  - 데이터 구조에 "점주 답변"이라는 출처 종류를 추가한다.
  - 점주 답변마다 가짜 자료 파일을 만든다.

**행동**
- 차준혁은 "데이터 구조와 약속에 점주 답변 출처를 추가하되, 상대 코드는 건드리지 않고 인계 자료로 함께 준비한다"를 골랐다.

**결과**
- 공개된 지식이 "이 내용은 점주의 이 답변에서 나왔다"를 정직하게 가리킬 수 있게 됐다.
- 질문 답변 쪽 코드는 아직 "자료 파일 없는 출처"를 처리하지 못한다. 그래서 상대가 준비할 때까지 점주 답변 출처 카드는 공개하지 않도록 막아 두었다. 막아 두는 스위치는 AI가 설계했다.

**배운 점**
- 출처를 억지로 만들어 채우는 것(가짜 파일)보다, 출처의 종류를 정직하게 늘리는 편이 나중에 "왜 이렇게 답했나"를 설명하기 쉽다.

## 결정 4. 카드 한 장을 공개할 때마다 전체를 다시 계산하지 않는다 — "같은 글이면 복사"

**결정한 사람:** 차준혁 (문제 제기와 방향 선택). 두 방식의 비교는 AI가 제시했다.

**상황**
- 카드 한 장만 승인해도, 검색 준비 단계가 **매장의 공개 카드 전체**를 다시 임베딩하고 있었다. 카드가 100장이면 1장 대신 101장을 계산한다.
- 차준혁이 설명을 듣다가 먼저 문제를 짚었다.
  - "겹치는 사실을 검사하는 단계가 앞에 있지 않나? 그렇다면 전체를 다시 계산하는 건 너무 비효율적이다."
- 확인해 보니 겹침 검사는 경로마다 달랐다(점주 답변에만 있고, 새 자료 업로드에는 없다).
- 게다가 겹침 검사가 있든 없든, 공개하는 순간 전체를 다시 계산하는 것은 따로 일어나고 있었다.

**과제**
- 바뀌지 않은 카드의 계산 결과를 어떻게 재사용할지 정해야 했다.
  - 방법 A: 공개할 때 "같은 카드 판·같은 구역·같은 글"이면 이전 계산 결과를 그대로 복사하고, 바뀐 것만 새로 계산한다.
  - 방법 B: 바뀐 카드만 따로 준비하고, 검색할 때 이전 결과와 합쳐서 쓴다.
- 차준혁은 "구현 난이도와 상관없이, 카드 100~200장 규모에서 어느 쪽이 더 효율적인가"를 기준으로 삼았다.

**행동**
- 두 방식 모두 새로 계산하는 것은 바뀐 카드뿐이라, AI 비용은 같았다.
- 차이는 다음과 같았다.
  - 방법 A는 공개할 때 데이터 복사가 조금 늘지만, 검색이 한 묶음만 보면 되어 단순하다.
  - 방법 B는 검색할 때마다 여러 묶음을 합쳐야 한다. 검색은 공개보다 훨씬 자주 일어난다.
- 차준혁은 이 비교를 보고 **방법 A**로 정했다. 방법 B는 카드가 수천 장 이상일 때 다시 검토하기로 했다.

**결과**
- 질문 답변 쪽에 "같은 글이면 복사" 방식을 요청하는 내용을 인계 문서에 넣었다. 적용되면 카드 1장 승인에 계산도 1장분만 든다.

**배운 점**
- "지금 얼마나 비효율인가"보다 "어느 작업이 더 자주 일어나는가"가 방식을 가른다. 가끔 하는 공개에 조금 더 쓰고, 자주 하는 검색을 단순하게 두는 편이 낫다.

## 결정 5. 쌓이는 옛 검색 데이터는 정리한다 — 기준 틀은 정하고 숫자는 나중에

**결정한 사람:** 차준혁

**상황**
- 방법 A로 가든 아니든, 공개할 때마다 검색 데이터 한 벌이 새로 쌓인다. 지우지 않으면 저장 공간과 비용이 계속 는다.
- 차준혁이 정리 기준이 필요하다고 짚었다. 선택지로 "기간으로 자르기(예: 1년)"와 "개수로 자르기(예: 3개)"를 제시했다.

**과제**
- 무엇을 남기고 무엇을 지울지, 그 기준을 정해야 했다.

**행동**
- 먼저 "지워도 되는 근거"를 확인했다.
  - 과거 답변의 근거 확인은 검색 데이터가 아니라 카드의 판·원문 기록으로 한다.
  - 그래서 옛 검색 데이터를 지워도 "그때 왜 그렇게 답했나"는 확인할 수 있다.
- 기준의 틀은 **"지금 쓰는 것 + 직전 몇 개 + 며칠"** 로 정했다. 기간과 개수를 섞은 형태다.
  - 기간만 쓰면 공개가 잦은 매장에서 수천 벌이 쌓인다.
  - 개수만 쓰면 연속 승인 몇 번에 방금 바꾼 것까지 지워질 수 있다.
- 차준혁은 **몇 개, 며칠이라는 구체적인 숫자는 지금 정하지 않고**, 두 담당자가 운영 데이터를 보고 추후 함께 정하기로 했다.

**결과**
- 인계 문서에 정리 구조와 "숫자가 정해지기 전에는 정리를 켜지 않는다"는 조건을 적었다.

**배운 점**
- 근거 없이 숫자를 먼저 박으면 나중에 바꾸기 어렵다. 틀(무엇을 기준으로 자를지)과 값(얼마로 자를지)을 나눠 결정하면, 틀은 지금 확정하고 값은 데이터를 본 뒤 정할 수 있다.

## 결정 6. 데이터베이스 연결 개수 설정은 한 곳에서 관리한다

**결정한 사람:** 차준혁

**상황**
- 서버가 동시에 쓰는 데이터베이스 연결 수(최대 10개)가 코드 한가운데 숫자로 직접 적혀 있었다.
- 팀 규칙은 "설정값은 설정 파일 한 곳에 둔다"다.
- 차준혁이 "10개인 이유가 데이터베이스 서비스의 제약인가"를 물었다. 확인해 보니 서비스 제약이 아니라 누군가 정한 값이었다.

**과제**
- 값을 늘릴지, 위치를 옮길지 정해야 했다.

**행동**
- 차준혁은 "설정 파일로 옮긴다"를 골랐다.
- 값을 늘리는 것은 근본 해결이 아니라는 점도 함께 확인했다. 연결이 모자라는 원인은 "AI 응답을 기다리는 동안 연결을 쥐고 있는 것"이다.

**결과**
- 설정 이동은 후속 작업으로 잡았다.

**배운 점**
- "왜 이 숫자인가"를 물으면, 제약인지 임의 값인지가 드러난다. 임의 값이면 한 곳에 모아 두는 것만으로도 나중에 바꾸기 쉬워진다.

## 결정 7. 새 작업 공간은 같은 폴더에서 만든다

**결정한 사람:** 차준혁

**상황**
- AI가 새 작업을 할 때마다 별도 폴더에 작업 공간을 따로 만들었다.
- 그러자 편집기와 AI 대화가 보는 폴더와 실제 코드가 있는 폴더가 달라져, 이어서 작업하기 불편했다.

**과제**
- 작업을 격리하는 이점과 이어서 작업하는 편의 중 무엇을 택할지 정해야 했다.

**행동**
- 차준혁은 "새 작업 공간(브랜치)은 같은 폴더에서 만든다"로 정했다.

**결과**
- 이후 작업은 원래 폴더에서 이어진다. 대신 새 작업을 시작하기 전에 저장하지 않은 변경이 섞이지 않았는지 확인한다.

**배운 점**
- 도구가 권하는 기본 방식보다, 실제로 매일 쓰는 흐름에 맞는 방식이 결국 더 빠르다.

## 이 문서에 적지 않은 것

아래는 사람이 아니라 AI가 정한 것이라 뺐다.
- 공개 절차의 세부 순서와 실패 처리
- 오래된 카드에 문제가 있을 때 그 카드만 빼고 공개하는 규칙
- 제외·복원 직후 공개판을 다시 만드는 방식
- 점주 답변 자동 처리 기능을 기본으로 꺼 두는 결정
- 두 검색 준비 방식의 비교 수치와 세부 설계 (사람은 비교를 보고 방향을 골랐다)
