# 이관 경계와 실험 설계 — 같은 모델로 쓰기·읽기 품질을 개선하는 방법

개정 2026-09-14 · 코드 확인 기준 main @ 0b8e1c4 · 실행 결과가 아닌 설계 문서

이 문서는 Gemini에 맡길 변환과 서버가 보존할 계약을 구분하고, 구조 변경의 효과를 판정하는 방법을 정한다. 제품·데이터 계약은 [ASKBUDDY_MVP_CURRENT.md](ASKBUDDY_MVP_CURRENT.md) 31절, 담당자별 구현 순서와 완료 조건은 [DEV_TODO_CURRENT.md](DEV_TODO_CURRENT.md)가 기준이다. 신규 스키마·단계·지표는 구현과 재측정 전까지 계획이다.

## 1. 범위와 판단 원칙

이번 개선에서 생성·추출 모델은 gemini-3.6-flash로 고정한다. 임베딩은 text-embedding-3-small 1536차원, STT는 whisper-1을 유지한다. 다른 모델로의 승격, 큰 모델 재호출, 멀티벤더 비교는 이번 실험 축에 넣지 않는다. 실제 호출 모델 ID·응답 메타데이터와 코드 설정값은 실행 manifest에 함께 기록한다.

목표는 원본에서 확인되는 사실이 JSON·카드·답변을 거치며 사라지거나 섞이는 위치를 줄이는 것이다. JSON 형식, ID 참조, 승인 상태, 스냅샷 일치, 처리 구간 누락은 서버가 검사할 수 있다. 자연어의 의미가 참인지, 원본을 빠짐없이 이해했는지까지 결정론 검사로 보장할 수는 없다. 숫자·낱말 포함 검사와 모델 자체 confidence는 의미 정확성의 증명이 아니다.

| 책임 | 모델에 맡기는 일 | 서버와 평가가 맡는 일 |
|---|---|---|
| 원본 이해 | 작은 근거 구간에서 사실·조건·모호성 후보 추출 | 원본·구간·원시 JSON 보존, 형식·근거 위치 검사, 사람 정답지와 비교 |
| 대상 정리 | 별칭·대상·규격 연결 후보 제안 | 매장 격리, 확정 ID, 규격 구분, 불확실한 병합의 검수 대기 |
| 카드 조립 | 제공한 사실 ID의 묶음·순서·표현 후보 제안 | 사실 값 재작성 방지, ID 참조와 disposition 검사, 카드 버전·사실 스냅샷 보존 |
| 검색·답변 | 선택적으로 질의 의도·근거 충분성·답변 표현 제안 | 승인 버전 검색, 근거 묶음, 사실·조건 연결 검사, 답변·추가질문·점주 전달 정책 |
| 승인·수정 | 승인 권한 없음 | 점주 승인, 변경 이력, 충돌 처리, 접근 권한과 감사 |

원장 선저장이 구조적으로 보장할 수 있는 것은 “이미 추출해 저장한 사실이 카드 재조립 때문에 사라지지 않음”이지 “원본의 모든 사실을 추출함”이 아니다. 구조 계약과 의미 정확성의 평가를 분리한다.

## 2. 출발점과 증거 수준

현재 코드는 자료별 전처리 뒤 ExtractionResult.cards를 생성한다. 구간이 있을 때만 선택적으로 map/reduce를 수행하고, 최종 카드의 facts를 source_facts에 적재한다. map 단계의 독립 사실 원장과 사실 ID만 참조하는 카드 조립은 아직 완성된 동작으로 간주하지 않는다. 코드 기본값은 영상 분할 0초·추출 1패스이며, 환경별 실제 설정은 실행 manifest로 확인한다.

현재 읽기는 pgvector 후보와 낱말 앵커 검사, 승인 카드 기반 답변 생성, 인용·숫자·낱말 검사 및 폴백을 사용한다. retrieval_strong_score=0.62가 설정에 남아 있다는 이유만으로 현재 검색을 “0.35/0.62 두 단계 게이트”라고 설명하지 않는다. 실제 경로와 승인 버전 사용 여부는 코드·계약 테스트로 확인한다.

| 자료 | 이번 검토에서 확인한 범위 | 사용할 수 없는 주장 |
|---|---|---|
| askbuddy-handoff-20260914.zip의 dev 정답지 | dev 사실 180건, owner 상태 TEST | 점주가 확정한 운영 골든셋, 전 매장 대표성 |
| 같은 인계본의 읽기 스모크 | 고유 질문 8개 | 실제 직원 질문 전체의 정확도, 반복 실행 행 수를 독립 질문 수로 계산 |
| 같은 인계본의 실행 데이터 | extraction_runs 실행 데이터가 없어 문서 수치를 재현할 수 없음 | 과거 E-O0 수치가 이번 코드에서 재현됐다는 주장 |
| 과거 문서의 실험 표 | 당시 작성자가 남긴 측정 기록 | 같은 데이터·실행 조건의 확정 A/B 비교나 기본값 승격 근거 |

정답지의 대상·규격·속성·값·근거를 담당자가 확인하고 판정자·판정일을 남긴다. 개발자 임시 라벨과 점주 확인 라벨을 구분한다. 수집 전 지정한 holdout은 dev와 분리하고, 같은 원본의 일부 구간이나 수정본이 두 집합에 나뉘어 들어가지 않게 한다.

## 3. 두 개발자의 독립 작업 경계

개발자 W는 입력 → JSON → 사실 원장 → 카드와 게시를, 개발자 R은 질문 → 승인된 근거 → 답변을 맡는다. W 완성을 기다린 뒤 R을 시작하지 않는다. C0에서 공유 계약과 격리된 합성 승인 fixture를 먼저 동결하고 각 경로를 독립 검증한다. 실제 W 산출물을 사용한 통합 승격은 W의 준비 이후 진행한다. 계약 변경은 새 버전으로 제안하고 양쪽 계약 테스트를 통과시킨 뒤 반영한다.

| 경로 | 고정 입력 | 독립적으로 검증할 출력 | 다른 경로와의 경계 |
|---|---|---|---|
| W | 원본 artifact, 구간 manifest, source truth, 고정 용어·규격 fixture | 추출 JSON, 원장 사실·근거, disposition, 카드 draft·버전 스냅샷 | R 구현 없이도 published_knowledge/v1 형태의 fixture를 내보낼 수 있어야 함 |
| R | 사람이 검증한 승인 카드·사실·근거 스냅샷, 질문·기대 동작 fixture | 검색 근거, 답변·인용, 추가질문·점주 전달, 검증 결과 | W의 현재 추출 품질과 무관하게 동일 fixture로 검색·답변을 평가 |
| 통합 | W의 특정 게시 버전 + R의 특정 버전 + 고정 질문셋 | 원본부터 최종 응답까지의 오류·손실과 비용 | 한쪽 최신 결과를 자동으로 섞지 않고 두 버전·hash를 명시 |

공유 계약의 정확한 필드와 상태는 MVP 31절을 따른다. 실험 fixture는 다음 경계를 반드시 검사한다.

- PublishedKnowledgeSnapshot의 schema_version=published_knowledge/v1, JWT의 store_id, knowledge_revision, snapshot_hash, 현재 승인 card_id·card_version_id, 불변 fact_revision 참조, evidence·rendered blocks, glossary version.
- W의 reference-only CardPlan과 서버 렌더링. subject/variant/predicate/value/polarity/conditions/order/dependencies 및 열린 속성·raw assertion이 유실되지 않는지 검사한다. 모르는 variant는 모든 규격에 일치하는 wildcard가 아니다.
- 추출 occurrence마다 LINKED / REVIEW_PENDING / EXCLUDED(reason)를 기록한다. 중복 내용이어도 서로 다른 근거 occurrence는 보존한다. 미처리·잘못 연결·렌더링 누락을 서로 구분한다.
- effective_facts는 draft용이다. 승인된 카드 버전은 불변 fact_revision 또는 값·근거 스냅샷을 사용한다. 점주 수정·재조립·재승인 후에도 과거 승인 내용이 최신 사실로 바뀌지 않는지 검사한다.
- 기존 승인 자료의 RAW block/span 경로를 허용한다. 자동 역추출한 사실이 원문 승인을 상속하지 않는지, 점주 원문 NEW/IDENTICAL과 변환된 SUPPLEMENT/CONFLICT가 계약에 맞게 처리되는지 검사한다.
- W가 카드 버전·렌더링·게시와 knowledge_apply를, R이 chat·점주 원문 전달·pending·알림·검색·답변 계획을 맡는다. 사실 참조·게시 pointer·검색 인덱스·knowledge_revision의 원자적 전환, tenant/version cache, 최종 렌더링 전 현재 버전 재확인을 통합 테스트한다.
- 추가 API POST/GET /learn/chat/v2의 ANSWER / CLARIFY / ESCALATE / REFUSE / SAFE_ROUTE를 평가한다. ERROR는 action이 아닌 구조화된 인프라 오류다. CLARIFY는 pending·점주 알림 없이 범위와 TTL이 있는 문맥을 유지한다. REFUSE/SAFE_ROUTE는 고정 정책 안내이며 자동 pending·알림이 없고 별도 확인 요청 때만 ESCALATE한다. ESCALATE는 pending 저장 완료 뒤에만 WAITING을 노출한다. 기존 v1에 새 enum을 섞지 않으며 CLARIFY를 NO_ANSWER로 접지 않는다.

미승인·폐기·구버전·다른 매장·점주 수정 전후·모르는 규격·충돌된 값을 fixture에 포함한다. 원장에 존재한다는 이유만으로 승인 스냅샷에 없는 사실을 R이 사용하면 안 된다.

## 4. 평가 집합과 집계 단위

지표마다 분모를 고정한다. 카드 장수, JSON 행 수, 답변 문장 수를 서로 대신 쓰지 않는다.

| 기호 | 정의 |
|---|---|
| T | 사람이 원본과 대조해 확정한 평가 대상 사실 ID 집합. 대상·규격·값·조건·근거를 함께 판정 |
| O_r | 실행 r이 출력한 모든 사실 occurrence. 낮은 confidence·모호성·충돌·중복도 원본 결과에 보존 |
| F_r | O_r의 주장을 사전 고정한 원자화·중복 규칙으로 집계한 사실 주장 집합. 중복 근거는 별도 occurrence로 남김 |
| L_r | 실행 r에서 스키마·ID 검사를 통과해 원장에 보존된 사실 ID 집합. 탈락 주장과 이유도 별도 보고 |
| Q | 고유 질문 ID 집합. 같은 질문을 반복 호출한 실행 행은 질문 개수를 늘리지 않음 |
| Q_A / Q_U / Q_M / Q_P | 각각 승인 근거로 충분히 답할 수 있는 질문 / 근거 없어 ESCALATE해야 하는 질문 / 추가 확인이 필요한 질문 / REFUSE 또는 SAFE_ROUTE가 필요한 정책 질문. 기대 행동을 사전에 지정해 중복 분류하지 않음 |
| Q_source_A | 원본상 답이 존재하고 정책상 직원에게 제공 가능한 질문의 사전 고정 집합. W가 만든 승인 snapshot에 답이 남았는지와 무관하게 통합 평가 분모로 유지 |

정답 사실 하나와 출력 주장 하나의 대응은 사전 고정한 매칭 규칙으로 판정한다. 대상·규격·조건을 놓쳤거나 다른 대상의 숫자를 붙인 것은 단순 문자열 일치로 정답 처리하지 않는다. 복합 주장은 고정 규칙으로 원자화하며, 출력 한 행에 여러 값을 합쳐 precision 분모를 줄이지 않는다. 자동 매칭은 보조 도구이며 애매한 사례는 사람 판정을 남긴다.

전체 합산 micro 지표와 자료별·유형별 macro 지표를 함께 보고한다. 원본 형식, 규격, 부정/예외, 위치, 수량/단위, 순서, 모호성·충돌, 복수 질문을 층화한다. 작은 층은 사례 수를 함께 쓰고 일반화하지 않는다.

R 독립 평가의 Q_A는 고정 승인 fixture가 제공하는 지식을 기준으로 정한다. 통합 비교에서는 Q_source_A를 snapshot마다 재라벨링하지 않는다. W가 사실을 누락하거나 검수 대기에 남겼다면 ESCALATE가 R의 권한 정책상 올바를 수 있지만 원본부터의 답변 성공으로 세지 않는다. 각 snapshot의 Q_A 크기와 Q_source_A와의 차이를 별도 보고한다.

## 5. W 지표 — 추출과 조립을 분리한다

| 지표 | 분자 / 분모 | 해석과 주의점 |
|---|---|---|
| source_fact_recall | T 중 F_r에서 정확히 재현한 사실 수 / 전체 T 사실 수 | 원본 대비 추출 재현율. 실패·빈 응답의 해당 truth는 분모에 남음 |
| ledger_source_recall | T 중 L_r에 정확한 값·규격·조건·근거로 보존된 사실 수 / 전체 T 사실 수 | raw 출력 recall과 원장 저장 후 recall을 분리. 저장 실패도 해당 truth의 실패 |
| extraction_precision | F_r 중 원본이 실제로 지지하는 주장 수 / 전체 F_r 주장 수 | 낮은 confidence도 포함. 추출 0건이면 N/A이며 100%로 두지 않음 |
| unsupported_fact_rate | F_r 중 근거가 없거나 근거와 모순되는 주장 수 / 전체 F_r 주장 수 | 미확정 판정 수·비율도 별도 보고하여 오답에서 숨기지 않음 |
| critical_fact_error_rate | 수량·단위·규격·부정·조건·순서 중 하나 이상이 틀린 주장 수 / 해당 요소가 평가되는 추출 주장 수 | 오류 종류별 건수와 원본 truth의 누락률도 함께 보고 |
| json_schema_success_rate | 완전한 응답이 스키마 검사를 통과한 추출 시도 수 / 전체 추출 시도 수 | 재시도 전후·잘림·빈 응답·호출 실패를 별도 기록 |
| ledger_preservation_rate | 영속 저장돼 ID로 다시 읽을 수 있는 유효 추출 사실 수 / 저장해야 하는 유효 추출 사실 수 | 조립 전에 확인. 원본 사실 재현율과 다른 지표 |
| fact_evidence_accuracy | 위치·인용 원문·사실 지지 관계가 모두 맞는 추출 사실 수 / 전체 추출 사실 수 | 위치 없음·잘못된 인용도 분모에 남음 |
| card_disposition_coverage | 유효한 LINKED/REVIEW_PENDING/EXCLUDED와 필요한 참조·사유가 기록된 occurrence 수 / 전체 추출 occurrence 수 | 미연결 사실을 전부 손실로 부르지 않음. 상태별 건수·비율을 함께 보고 |
| card_truth_coverage | 카드 버전의 상세·사실 스냅샷에 정확히 포함된 T 사실 수 / 카드로 제공해야 하는 T 사실 수 | 제공 대상 truth는 사전 고정. 모두 검수 대기로 보내 coverage를 높일 수 없음 |
| disposition_error_rate | 잘못 연결·제외·검수 분류한 occurrence 수 / disposition이 필요한 전체 occurrence 수 | 사유별 사람 판정과 미처리 수를 함께 보고 |
| card_snapshot_integrity | 값·규격·근거·revision이 참조 사실과 일치하는 카드-사실 연결 수 / 전체 연결 수 | 오래된 승인 카드, 점주 수정, 재조립 후에도 검사. 의미 정확성 보장은 아님 |
| card_rendering_completeness | 포함 확정 사실·필수 문맥 중 올바른 카드 블록에 보존된 항목 수 / 포함 확정 사실·필수 문맥 전체 항목 수 | 처리 설명률과 구분하고 보류·제외율을 함께 보고. 필수 문맥의 원자화 규칙은 사전 고정 |
| review_burden | 작업별 실제 검토 시간, 수정·제외·미처리 수, 중도 이탈 수 / 각 작업·검수 세션 | 자동화가 점주의 작업을 늘리는지 확인. 시간·건수를 임의의 단일 정확도로 합치지 않음 |

card_disposition_coverage=100%는 모든 출력 occurrence의 처리 이력이 있다는 뜻이다. 추출 실패, 오인식, 과도한 제외, 잘못된 묶음은 별도 지표로 남는다. ID를 모두 참조해도 본문이 다른 내용을 말할 수 있으므로 렌더링의 값·조건 일치 검사와 사람의 카드 완전성 판정을 구분한다. 모든 비율에서 분모 0은 N/A와 건수를 보고한다.

실행 간 출현 여부가 달라지는 사실도 T와 결과 표에서 빼지 않는다. 사실별로 매 실행의 추출 / 누락 / 잘못된 값 / 모호 / 실패를 기록하고 출현 빈도, 새로 맞힌 사실, 새로 잃은 사실을 모두 보고한다. 안정된 사실만 고른 결과는 보조 분석이며 기본값 승격의 주 지표로 사용하지 않는다.

## 6. R 지표 — 후보 검색과 완성 답변을 분리한다

R의 독립 평가에서는 승인 fixture에 어떤 답이 있는지 먼저 확정한다. 통합 평가에서는 원본에는 답이 있지만 W가 누락한 질문과 승인 근거 자체에 답이 없는 질문을 구분한다.

검증기 자체는 같은 후보 답변 묶음을 켬/끔 상태로 재생해 비교한다. validator_block_precision은 실제 오답 후보를 차단한 수 / 전체 차단 후보 수, validator_false_block_rate는 정답 후보를 차단한 수 / 전체 정답 후보 수, validator_missed_error_rate는 오답 후보를 통과시킨 수 / 전체 오답 후보 수로 정의한다. 질문 단위 block_precision·false_abstention_rate와 이름·분모를 분리한다. 검증기를 끈 실험은 오프라인이며 직원에게 노출하지 않는다. 후보 답변 판정과 폴백 이후 최종 응답 판정을 섞지 않는다.

인용·숫자·낱말 검사, 단위·규격·조건 검사, 선택적 모델 의미 검토는 각각 오류를 일부 잡는 장치다. 어느 하나도 의미 정답의 최종 판정자가 아니며, 추가 검토에 같은 Gemini를 쓰더라도 사람 평가와 대체하지 않는다. 검색은 lexical 후보 합집합과 RRF 전에 vector 임계값으로 후보 전체를 제거하지 않고, 근거 충분성은 융합 이후 판정하는 계약을 검증한다.

## 7. 짝비교·대조군·holdout 실행 규칙

1. 실행 전에 가설, 주 지표, 허용 회귀 폭, 비용·지연 예산, 데이터·코드·프롬프트·스키마 hash, 변경할 축, 반복 횟수와 중단 조건을 등록한다. 수치 기준이 미정이면 병행 구현과 개발 평가는 계속하되 기본값 승격 판정은 하지 않는다.
2. A와 B는 같은 원본·정답지·질문·승인 스냅샷을 사용한다. 추출 이후 단계를 비교할 때는 STT·전처리 artifact를 고정한다. 전처리가 실험 축이면 변경된 artifact와 hash를 양쪽 모두 기록한다.
3. A와 B를 각각 최소 3회 실행하고 사실 ID·질문 ID로 짝비교한다. 실행 순서는 교차 또는 사전 무작위화한다. 온도 0.0도 결정성을 보장하지 않으며, 최소 3회는 초기 변동 확인의 하한이지 통계적 충분성 보장이 아니다.
4. A/A는 동일 설정을 별도로 반복하는 negative control이다. 이전 문서의 “음성 대조군”은 이 negative control을 뜻하며 반드시 VOICE 자료를 뜻하지 않는다. A/A에도 같은 데이터, 반복 정책, cache 정책을 적용한다. 기존 LLM 응답을 cache에서 재생한 호출을 새 확률적 반복으로 세지 않는다.
5. 결과는 매 반복의 전체 분모·성공·실패·비용, 사실/질문별 전후, 평균·범위·변동을 보고한다. 개선/퇴행 수와 가능한 불확실성 구간을 제시하되 작은 매장 수·표본 수의 한계를 명시한다. A/A 변동과 구별되지 않는 차이는 개선 확정으로 쓰지 않는다.
6. 실패 구간, 빈 JSON, 재시도, 불안정 사실을 결과에서 지우지 않는다. 사전 정의한 외부 장애나 하네스 결함 때문에 실험을 무효화할 때는 해당 시도와 사유를 보존하고 제외 기준·재실행 범위를 공개한다. 결과가 나쁜 실행만 재시도하지 않는다.
7. holdout은 사전 등록한 평가 캠페인으로 개봉한다. 캠페인에 정한 A/B·A/A 반복 횟수와 설정으로 모두 실행하고, 반복 사이의 프롬프트·규칙·임계값 튜닝을 금지한다. “한 번 개봉”은 모델을 단 한 번 호출한다는 뜻이 아니다.
8. holdout 결과를 보고 수정한 후보는 같은 holdout으로 다시 일반화 성능을 주장하지 않는다. 해당 집합은 이후 회귀 테스트로 보관하고 새로운 holdout 또는 별도 미래 자료로 재검증한다.

같은 사실·질문을 3회 실행했다고 독립 표본 수가 3배가 되는 것은 아니다. 반복은 모델 변동을 측정하는 중첩 관측이며 매장·원본·질문 수준의 의존성을 보존한다. 불확실성 추정 방법과 재표집 단위는 사전 등록한다. 독립 매장이 적으면 그 한계를 그대로 보고하고, 반복 횟수를 늘리면 min–max 범위가 반드시 좁아진다고 가정하지 않는다. A/A의 관측 범위만을 유의성 검정이나 비열등 판정의 대체물로 쓰지 않는다.

실행 manifest에는 run ID, fixture/원본/전처리 hash, 모델 설정과 실제 응답 모델, schema/prompt/코드 버전, 분할·중첩·프레임 설정, 검색·답변 옵션, 승인 인덱스 snapshot, cache 정책, token usage, 종료 이유, 원시 응답 artifact, 재시도와 판정 이력을 남긴다. JSON 복구나 추가 검증 호출도 전체 비용·실패 이력에 포함한다.

X-R-O2의 결과는 고정 데이터와 주입 근거 조건에서의 진단값이다. 모든 검색 구조에 대한 수학적 상한으로 주장하지 않는다. W의 현재 손실이 크더라도 R의 고정 승인 fixture 평가는 유효하므로 읽기 개발을 중단할 이유가 되지 않는다.

## 9. 원가·지연·승격 조건

품질과 함께 자료당·질문당 입력/출력 토큰, 실제 호출 수, 재시도 수, cache hit, 처리 시간 p50/p95를 기록한다. 쓰기는 원본 길이·페이지·프레임 수와 함께 보고하고, 읽기는 생성·검증·검색 비용과 전체 지연을 구분한다. 가격·환율 환산에는 적용일과 단가를 명시한다. 표본이 적으면 p95의 관측 수와 불안정성을 표시한다.

관측되지 않은 token·단가·오류 호출 비용은 0이 아닌 미확정으로 표시하고 비용 관측 커버리지를 함께 보고한다. 일부 호출 비용 합계를 전체 비용처럼 표시하거나 미확정 비용으로 예산 통과를 판정하지 않는다.

추가 LLM 호출이 없는 변경도 CPU·검색·인덱스·저장·운영 비용이 발생할 수 있으므로 “원가 0”이라고 부르지 않는다. 네이티브 비디오, 프레임 확대, 예상질문 생성, 재순위는 자동 채택하지 않고 해당 축에서 비용을 측정한다.

기본값 승격에는 다음이 모두 필요하다.

- 공유 계약·격리·승인·버전·재처리 불변식 테스트가 통과한다.
- 사전에 고정한 안전 회귀셋에서 오답·교차 노출·승인 위반 0건을 요구한다. 이 유한 회귀셋 통과를 모든 실제 입력에 대한 무오류 보장으로 해석하지 않는다.
- 사전 등록한 주 품질 지표가 A/A 변동을 고려해 개선되고, 위험 오류·기권·완전성의 허용 회귀 범위를 지킨다.
- 원가·지연 예산을 충족하고 실패·재시도·미확정 판정이 보고에서 빠지지 않는다.
- R은 W의 계약 fixture를, W는 R의 답변 오류 사례를 교차 검토한다. 실제 W 산출물 통합 평가와 필요한 holdout 캠페인 결과까지 근거에 연결한다.

“평가에서 특정 오류 0건”과 “그 오류가 절대 발생하지 않음”은 다른 주장이다. 임계값·예산·판정자 또는 holdout이 준비되지 않은 상태에서는 실험 후보와 관측 결과까지만 기록한다. 미정 수치 예산은 승격을 막으며 C0 이후 병행 구현 자체를 막지 않는다.

### 9-1. pull 65c2403의 D18·D21 적용

사용자 회신으로 U1 범위를 확정했고 U2는 입력틀·시나리오·실측으로 전환했다. 초기 등록비 I, 월 운영비 O_m, 첫 달 지출 I+O_1, 누적 지출을 분리한다. 등록비/3,000은 예산환산 개월이며 실제 회수기간이 아니다. 지속 Storage 보관비는 등록 파일도 발생 월 운영비로 센다. 첫 달 운영비를 안정기와 평균내 상한을 통과시키지 않는다.

[C0 원가 계측 계획](plan/C0_COST_MEASUREMENT_PLAN.md)의 CP-00A~C를 C0-2/3 본구현보다 앞세운다. extraction_runs에 nullable summary를 추가하고 provider attempt 원장·Storage inventory/전송을 집계한다. 읽기에도 누락 usage→0·부분합 오류를 보완한다. 종료 run freeze는 유지하고 늦은 정산은 새 cost report로 남긴다. EVALUATION 비용과 제품 월 비용을 이중 집계하지 않는다.

### 9-3. 승격 판정 기준 — 역할 분리 (2026-09-15 확정)

하나의 대표값으로 성능·안정성·안전성을 모두 판정할 수 없다. 셋을 나눈다.

| 판단 | 기준 |
|---|---|
| 전체 성능 개선 | 고정 분모에서 반복별 성공 수 차이 Δᵢ 의 **중앙값** |
| 사실·질문별 안정성 | 매번 성공 / 매번 실패 / 반복 간 변동을 **별도 보고** |
| 안전성 | **모든 반복**의 오류·악화를 확인한다. 불안정 사례도 제외하지 않는다 |

만장일치만으로 승격을 판정하면 구멍이 생긴다. `성공/성공/성공` 에서
`성공/성공/실패` 로 바뀐 필수 사실이 "갈렸다" 는 이유로 비교에서 빠져
**실제 발생한 실패가 '악화 0건' 뒤에 가려진다.** 이 경우는 안정성 저하로 반드시 남기고
승격을 차단한다.

중앙값 단독도 충분하지 않다. 전체 성공 수가 늘면서 특정 필수 사실이 악화될 수 있다.
**대표 개선량과 항목별 안전 조건을 함께** 적용한다.
미판정 필수 사례가 있으면 "악화 0건 확인" 으로 처리하지 않는다.

D18 의 `최소 3회·중앙값·2/3 양의 방향·최소 개선량` 은 개발 단계의 판단 규칙으로
유지하되 **통계적 확신과 구분한다.** 3회 통과나 A/A 한 번의 순증 0 이 개선의 확실성을
증명하지 않는다. 반복을 늘린다고 관측된 최댓값−최솟값이 반드시 줄어들지도 않는다 —
범위는 표본이 늘면 오히려 커진다.

실험 전에 고정할 것: 정답·채점기·입력 snapshot 버전과 전체 분모, 반복 수·실행 순서·
실패와 미판정 처리 방법, 대표 개선량과 안전·비용·지연 조건, 결론이 불명확할 때의
추가 실험 범위. 결과를 보고 정하면 그 실험은 탐색이지 검증이 아니다.

### 9-2. CP-00A~C 구현 이후의 상태 (2026-09-14)

쓰기 경로 계측이 붙었다. `ai_usage_attempts`가 유료 호출마다 attempt 단위로 쌓이고, 유료 호출 **전에** STARTED를 먼저 커밋한다 — 응답을 못 받은 호출이 원장에서 사라지면 관측률이 실제보다 높아진다. 재시도는 `logical_call_id` 로 묶여 한 번의 논리 호출로 센다. Storage는 클라이언트가 보낸 크기가 아니라 서버가 확인한 bytes를 쓴다.

첫 실측(평가용 카페 자료 B, 추출 5회)은 **미관측 0건**이었다. prompt 28,084 / completion 4,542 / thought 9,502 토큰이 관측됐고 `extraction_runs` 집계도 동작했다. 다만 `cost_status=COMPLETE`는 **관측이 완전하다는 뜻이지 금액을 안다는 뜻이 아니다** — `config/rate_card.json`의 요율이 전부 null이라 `cost_usd`는 여전히 없다. 리포트 계층이 이 둘을 섞어 읽지 않게 `price_status`를 따로 본다.

`scripts/cost_report.py`가 단계별 단가·관측률, 등록/운영 분리, LOW/BASE/HIGH 시나리오, D21 판정을 낸다. **현재 판정은 UNDETERMINED이고 통과가 아니다.** 막고 있는 것은 넷이다 — 답변(ANSWER) 호출 미관측(R 몫), 저장비 미측정, 요율표 미설정, 환율 미입력. 요율을 채우면 같은 원장으로 소급 계산되므로 지금 토큰을 쌓아두는 것이 낭비가 아니다.

이 구조가 막는 실패는 하나다: 못 잰 호출을 0으로 합산하면 총액이 사실보다 싸 보이고, 그 수치로 "월 3,000원 안에 들어왔다"고 적게 된다. 그래서 PARTIAL/UNKNOWN에는 총액을 내지 않는다.

판정은 PASS/FAIL/UNKNOWN이다. known subtotal로 상한을 넘으면 FAIL, 상한 이하라도 필수 usage/요율/Storage 귀속이 누락되면 UNKNOWN이다. 필요한 변동비가 모두 관측된 경우에만 PASS이며 할인 전 동일 tariff 추정과 actual billing을 구분한다. 비용을 맞추기 위한 입력 누락·질문 miss 변환·실패 run 제외는 허용하지 않는다. 고정비의 규모 변화는 별도 재검토한다.

## 11. 실험 기록과 외부 설명
