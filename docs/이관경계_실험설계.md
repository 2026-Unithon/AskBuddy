# 이관 경계 — 무엇을 Gemini에 넘기고 무엇을 우리가 쥐는가

작성 2026-09-13 · 기준 `main @ 6b31e04`
목적: "알고리즘을 직접 짤 것인가, 모델에 넘길 것인가"를 감이 아니라 **측정으로** 결정한다.

---

## 1. 판단 기준 (이 3개로 자른다)

**Q1. 시간이 지나면 무엇이 이걸 좋게 만드나?**
- **모델이 좋아지면 좋아진다** → **이관.** 우리가 붙들면 모델 발전을 못 받아먹고 유지보수만 는다
- **우리 도메인 데이터가 쌓이면 좋아진다** → **우리 것.** 모델은 우리 매장 용어를 모른다

이게 가장 강한 판별식이다.

**Q2. 출력이 검증 가능한가?**
검증 가능하면 이관해도 안전하다(틀리면 서버가 잡는다). 검증 불가능한 걸 이관하면 통제를 잃는다.

**Q3. 결정론이어야 하는가?**
승인·권한·격리·폐기 판정은 같은 입력에 항상 같은 출력이어야 한다. **영구히 우리 것.**

---

## 2. 이관은 공짜가 아니다 — 원가 축

영상 사례에서 확인: 네이티브 비디오 입력은 프레임 20장 대비 **토큰이 10배 이상**이다.
(전송 페이로드는 작아지지만 과금 토큰은 반대다. 이 둘을 혼동하지 말 것)

→ **이관 결정은 항상 (품질 이득) vs (원가·지연 증가)의 저울이다.**
→ 따라서 평가 하네스는 **정확도만 재면 안 된다.** 케이스당 원가와 p95 지연을 같이 찍어야 한다.
→ 9,900~20,000원 구독 모델이므로 원가 상한이 곧 설계 제약이다.

## 3. 구간별 현재 판정

| 구간 | 판정 | 근거 |
|---|---|---|
| 영상 프레임 선택 | **이관** (확정) | 모델이 좋아지면 좋아진다. 우리 데이터와 무관 |
| 음성 전사 | **이관** | 위와 동일. 단 전사문 자체는 검증·표시용으로 계속 보관 |
| 카드 문장 생성 | **이관** (이미) | 검증 3종이 뒤를 받친다 |
| 카테고리 분류 | **이관** (이미) | 허용목록을 우리가 주므로 통제됨 |
| doc2query 예상질문 | **이관** | 생성물이고, 틀려도 검색 후보만 늘 뿐 |
| 리랭킹 | **실험 대상** | 품질 이득은 있으나 호출 1회 추가. 원가로 갈린다 |
| 추출 2패스 분할 | **실험 대상** | 호출수 증가 대비 품질 이득 미확인 |
| 앵커·동의어 사전 | **우리 것** | 매장 용어가 쌓일수록 좋아진다 (Q1) |
| 임계값 (0.35 / 0.62) | **우리 것** | 우리 데이터로 튜닝하는 값 |
| 서버 검증 3종 | **영구 우리 것** | 결정론 필요 (Q3). 모델이 좋아져도 없애지 않는다 |
| 승인 게이트 / 버전 / 격리 / 감사 | **영구 우리 것** | 원장이다. 모델은 상태를 갖지 못한다 |

**한 줄**: 모델은 변환기, 서버는 원장. 변환은 계속 넘기고, 원장은 절대 안 넘긴다.

## 4. 실험 인프라 — 플래그 + 하네스

리포에 이미 이 패턴이 있다 (`api/app/config.py`):
```python
answer_mode: Literal["extractive", "grounded_llm"] = "grounded_llm"
ingest_mode: Literal["mock", "real"] = "mock"
```
**이 패턴을 그대로 확장한다.** 모든 이관 후보는 환경변수 플래그 뒤에 두고, 하네스가 조합을 돌린다.

### 추가할 플래그

| 플래그 | 값 | 대상 코드 |
|---|---|---|
| `video_input_mode` | `frames` \| `native` | `ingest/extract/gemini.py`, `preprocess/video.py` |
| `anchor_mode` | `hard` \| `soft` \| `off` | `reg/retrieve.py:134` |
| `glossary_expand` | `on` \| `off` | `reg/retrieve.py` `_anchors()` |
| `query_variants` | `on` \| `off` | 추출 + 임베딩 인덱싱 |
| `rerank_mode` | `none` \| `llm` | 검색 후단 |
| `extract_passes` | `1` \| `2` | `ingest/pipeline.py` |
| `answer_mode` | (기존) | — |

**규칙: 되돌릴 수 없는 변경은 실험이 아니다.** 플래그 없이 넣지 않는다.

### 하네스가 찍어야 할 3축

```
정확도   hit율 / 정답카드 적중 / 오답 생성률 / miss_reason 분포
원가     케이스당 입력·출력 토큰 → 원화 환산
지연     p50 / p95
```

세 축을 같이 찍고 **파레토 프론티어**에서 고른다. 정확도 1%p 올리자고 원가 3배 쓰는 조합을 걸러내는 게 목적이다.

### 실험 순서 (한 번에 하나씩만 바꾼다)

```
E0  기준선 — 현재 설정 그대로 측정. 이게 없으면 나머지가 무의미
E1  anchor_mode: hard → soft            (한 줄, 원가 0)
E2  glossary_expand: off → on           (원가 0)
E3  query_variants: off → on            (추출 원가만 증가, 검색 지연 0)
E4  video_input_mode: frames → native   (원가 크게 증가 — 품질 이득이 그만한지)
E5  extract_passes: 1 → 2
E6  rerank_mode: none → llm             (E1~E3으로 부족할 때만)
```

E1·E2는 원가가 안 늘어나므로 **이득만 확인되면 즉시 기본값 승격.**
E4·E6은 원가가 늘어나므로 **구독 원가 상한 대비 계산 후 결정.**

## 5. 진행 방식 — 실험은 계속 돌린다

**개발 동결하지 않는다.** 이 문서는 "지금 우리가 쓰는 방법론"을 명시하고,
"무엇을 실험으로 결정할지"를 함께 적어두는 문서다. 둘 다 지원서에 그대로 들어간다.

### 현재 방법론 (지금 확정해 쓰는 것)

| 구간 | 현재 방식 | 근거 |
|---|---|---|
| 영상 입력 | 3초 간격 프레임 추출 → 상위 N장 멀티모달 투입 | `preprocess/video.py` |
| 음성 | Whisper 전사 후 텍스트 투입 | `preprocess/audio.py` |
| 카드 추출 | 단일 프롬프트 1패스 + `response_schema` 강제 | `ingest/extract/gemini.py` |
| 검색 | 벡터 2단 게이트 (0.35 하한 + 0.62 강점수) + 낱말 앵커 AND | `reg/retrieve.py` |
| 답변 | 승인 카드 상위 3장만 입력, temperature 0.0 | `learn/answering.py` |
| 검증 | 서버 3종 → 실패 시 생성문 폐기, 카드 원문 폴백 | 계약 v1 |

### 실험으로 결정할 것 (아직 안 정한 것)

4절의 E0~E6. 각 항목은 **플래그 뒤에서 병행 실험**하고, 하네스 3축(정확도·원가·지연)으로
파레토 비교한 뒤 기본값을 승격한다. 결과는 6절에 누적한다.

### 병행 실험 규칙

1. **기본값은 항상 현재 검증된 경로.** 실험 플래그는 opt-in
2. **한 번에 하나만** 바꾼다
3. 되돌릴 수 없는 변경은 실험이 아니다 — 플래그 없이 머지하지 않는다
4. 데모·심사 시연 경로는 기본값으로만 돈다. 실험 브랜치가 시연을 깨지 않게 한다
5. E0 기준선을 먼저 찍는다. 기준선 없는 개선은 주장일 뿐이다

### 원가 0 항목은 우선 처리

E1(앵커 소프트화)·E2(glossary 연결)는 추가 호출이 없다.
이득만 확인되면 마감 전이라도 기본값 승격 가능.
E4(네이티브 비디오)·E6(LLM 리랭커)는 원가가 붙으므로 구독 원가 상한 계산 후 결정.

## 6. 답변 경로 아키텍처 실험 — 모델 배치와 게이트 수

### 6-1. 단계 분해

답변 경로는 6단계다. **각 단계가 독립적인 실험 좌표**다.

```
S1 질문 정규화   앵커 추출 · glossary 확장          현재: 코드(규칙)
S2 검색          임베딩 + 2단 게이트                현재: OpenAI 임베딩 + pgvector
S3 리랭크        후보 재순위                        현재: 없음
S4 생성          카드 3장 → 답변                    현재: gemini-3.6-flash, temp 0.0
S5 검증          3종 (인용·숫자·낱말)               현재: 코드(결정론)
S6 폴백          CARD_ORIGINAL / FALLBACK           현재: 코드
```

### 6-2. 조합 폭발을 먼저 막는다

6단계 × 3사 × 모델 여러 개 = 수백 조합. **전수 탐색은 불가능하다.**
두 가지로 자른다.

**(1) 오라클 상한 실험 — 병목부터 찾는다. 이게 먼저다.**

| 실험 | 방법 | 알 수 있는 것 |
|---|---|---|
| `E-O1` 검색 상한 | 생성 없이 검색만 평가 (recall@k) | S2가 정답 카드를 아예 못 가져오는 비율 |
| `E-O2` 생성 상한 | **정답 카드를 직접 주입**하고 S4~S5만 평가 | 검색이 완벽했을 때의 정확도 = 생성 단계 천장 |
| `E-O3` 검증 손실 | S5를 끈 상태 vs 켠 상태 비교 | 검증이 막아낸 오답 수 vs **정답을 잘못 막은 수** |

`E-O2`가 이미 95%인데 실측이 70%라면 **병목은 검색(S2)**이다. 이때 생성 모델을 Claude로 바꾸는 실험은 낭비다.
반대로 `E-O2`가 75%면 검색을 아무리 고쳐도 75%가 천장이다.

**→ 병목 단계 하나만 실험한다. 나머지는 고정.**

**(2) 좌표 하강 — 한 단계씩 고정하며 최적화**

전 조합이 아니라 `S(병목) 최적화 → 고정 → 다음 병목` 순서. 매 라운드 하네스 3축으로 검증.

### 6-3. 모델 배치 원칙

| 단계 성격 | 무엇을 쓰나 | 이유 |
|---|---|---|
| **결정론 검증** (숫자 포함, 낱말 포함, 인용 화이트리스트) | **모델 안 쓴다. 코드.** | 같은 입력에 같은 출력이어야 한다. 여기 LLM을 넣는 건 퇴보 |
| **판정형** (관계 IDENTICAL/NEW/SUPPLEMENT/CONFLICT) | 작은·빠른 모델 + 스키마 강제 | 출력 공간이 좁다. 큰 모델 낭비 |
| **생성** | 중간 모델 + temp 0.0 + 스키마 강제 | 뒤에 검증 3종이 있으므로 과투자 불필요 |
| **어려운 케이스** | 큰 모델로 라우팅 | 단 **비율 상한**을 둔다. 전체의 N%까지만 |
| **멀티모달 추출** | Gemini | 비디오·오디오 네이티브 |

**핵심: S5(검증)에 LLM을 넣지 않는다.** 검증이 확률적이면 검증이 아니다.
게이트를 늘린다는 건 LLM 게이트를 늘린다는 뜻이 아니라 **결정론 규칙을 늘린다**는 뜻이어야 한다.

### 6-4. 벤더별 실제 차이 (실험 전 사전 지식)

`config.py`에 이미 `openai_api_key` / `gemini_api_key` / `anthropic_api_key` 세 칸이 다 있다.

| | 강점 | 우리 맥락 |
|---|---|---|
| Gemini | 비디오·오디오 네이티브, `response_schema` 강제 | 추출(S4 카드생성)에 이미 사용 중. 멀티모달은 사실상 대안 없음 |
| OpenAI | structured output, 임베딩, Whisper | S2 임베딩(`text-embedding-3-small`) · STT에 이미 사용 중 |
| Claude | 긴 문맥 추론, 지시 준수 | S3 리랭크 · S4 생성 후보. 구조화 출력은 tool use 경유 |

**멀티벤더의 숨은 비용** — 실험 설계에 반드시 반영:
- 지연이 벤더별로 다르다 (S2→S4를 다른 벤더로 넘기면 왕복이 늘어난다)
- rate limit·장애가 각각 → 벤더마다 폴백 경로가 필요
- 프롬프트는 이식되지 않는다. 벤더 바꾸면 재튜닝 비용이 붙는다
- 스키마 강제 방식이 다르다 (`response_schema` vs strict JSON vs tool use)

**→ 원칙: 단계별로 벤더를 고르되, 한 단계에는 한 벤더.**
그리고 교체가 플래그 한 줄이 되도록 **호출부를 어댑터 인터페이스 뒤로** 뺀다. 이게 실험의 전제조건이다.

### 6-5. 게이트 수 트레이드오프

게이트를 하나 늘리면 네 가지가 동시에 움직인다.

```
오답 차단률      ↑  (좋음)
정답 오차단률    ↑  (나쁨)  ← 이게 진짜 비용
지연             ↑
원가             ↑ (LLM 게이트인 경우)
```

**정확도 한 숫자로 재면 안 된다.** 최소 이 넷을 분리한다.

| 지표 | 정의 |
|---|---|
| `block_precision` | 차단한 것 중 실제 오답 비율 |
| `false_block_rate` | **카드에 답이 있는데 miss로 떨어진 비율** |
| `leak_rate` | 검증을 통과한 오답 비율 |
| `p95` | 게이트 추가에 따른 지연 증가 |

**`false_block_rate`가 가장 위험한 지표다.** 알바가 "몰라요"를 세 번 받으면 앱을 안 연다.
오답 하나보다 헛발질 세 번이 신뢰를 빨리 깎는다.

**게이트 실험 (`E-G*`)**

| 실험 | 구성 |
|---|---|
| `E-G0` | 현재 — 검색 2단 + 서버 검증 3종 |
| `E-G1` | 검색 게이트 완화 (앵커 soft) — `false_block_rate` 감소분 측정 |
| `E-G2` | 생성 **전** 게이트 추가 (카드 충분성 판정: 이 카드로 답할 수 있는가) |
| `E-G3` | 생성 **후** 규칙 검증 추가 (단위·범위·모순 검사) |
| `E-G4` | 2티어 라우팅 (저신뢰 케이스만 큰 모델 재생성) |

`E-G2`는 **호출 1회 추가로 무의미한 생성을 막는 것**이라 원가가 오히려 내려갈 수 있다. 우선 검토 대상.
`E-G3`은 코드 규칙이라 원가 0. **가장 먼저 시도할 게이트.**

### 6-6. 실험 순서

```
1. E-O1 / E-O2 / E-O3    병목 진단 — 이것 없이 모델 실험 시작하지 않는다
2. E-G3                  원가 0 규칙 게이트
3. E-G1                  false_block_rate 개선
4. 병목 단계만 벤더·모델 교체 실험
5. E-G2 / E-G4           원가 계산 후
```

**측정 없이 모델부터 바꾸지 않는다.** "Claude가 더 좋다더라"는 실험이 아니다.

## 8. 지원서·심사 대응

### 원천기술 포지셔닝

설명회 노트: *"단순 AI 활용 최적화/편의 제공 서비스는 내년에 선정 안 됨. 원천기술에 가까운 핵심 알고리즘이어야 함"*

→ **우리 원천기술은 프레임 샘플링이 아니라 검증 게이트다.** 이관을 진행할수록 이 포지셔닝이 더 선명해진다.

- 검색 2단 게이트 (0.35 하한 + 0.62 강점수 + 낱말 앵커)
- 서버 검증 3종 (인용 화이트리스트 / 답변 숫자 ⊆ 카드 숫자 / 답변 낱말 ⊆ 카드 낱말)
- 실패 시 생성문 폐기 → 카드 원문 폴백
- 승인 카드(`published_version_id`)만 검색·학습 노출

**"AI가 매장 지식을 답한다"가 아니라 "검증되지 않은 문장은 알바에게 도달하지 않는다".**

### 이 문서 자체가 지원서 재료다

설명회에서 평가지표로 지목된 항목에 그대로 대응한다.

| 평가 항목 | 이 문서의 대응 |
|---|---|
| 사전 준비 증빙 (2기 신설) | 3절 구간별 판정 — 무엇을 검토하고 무엇을 왜 골랐는지 |
| 사업화 계획 = 가설 확인의 실행 순서 | 4절 E0~E6 실험 순서가 곧 검증 마일스톤 |
| 정량 지표 요구 | 하네스 3축(정확도·원가·지연). "빠름/우수" 같은 정성 표현 배제 |
| 실행 가능성 증명 (1순위) | 6절 실험 기록 누적 — 측정하고 결정한 이력 |
| 원가 구조 설명 | 2절 이관=원가 증가. 구독가 대비 상한 계산 |

**서술 톤**: "이렇게 만들었습니다"가 아니라
**"현재는 A 방식이고, B와의 비교를 E4로 측정해 10월 중 결정합니다"**.
심사위원(투자심사역 53.3%)이 보고 싶은 건 완성품이 아니라 **의사결정 체계**다.
"아직 안 정했다"를 측정 계획과 함께 쓰면 약점이 아니라 강점이 된다.
