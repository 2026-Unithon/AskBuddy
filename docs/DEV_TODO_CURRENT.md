# 13단계 — 쓰기 경로: 입력 소스 → 지식 카드

> **책임 분리.** 이 단계는 "자료를 넣었을 때 카드가 제대로 만들어지는가" 만 다룬다.
> 질문·검색·답변은 전부 14단계다.
>
> 추출이 사실을 흘리면 카드에 그 내용이 없고, 검색은 없는 것을 찾지 못한다.
> 이때 지표는 "검색이 나쁘다"로 보이지만 **오진이다.** 그래서 쓰기를 먼저 닫는다.

## 13.1. 평가 자료 확정과 사실 정답지

- [ ] 기준선을 잴 매장 자료를 정한다. 실제 카페 자료가 원칙이고, 확보가 어려우면
      현실적인 가상 매장을 만든다. 어느 쪽인지 문서에 명시한다.
- [ ] **상용 브랜드의 실제 자료는 내부 측정용으로만 쓴다.**
      - 브랜드명·상호·로고·메뉴 고유명을 **어디에도 쓰지 않는다.**
        데모·지원서·시연·발표자료는 물론 **이 저장소의 `.md` 문서·커밋 메시지·코드 주석에도** 쓰지 않는다.
      - "어느 브랜드 자료로 테스트했다" 는 서술 자체를 남기지 않는다.
      - 문서에는 `평가용 카페 자료 A` 처럼 익명 식별자만 쓴다.
      - 데모·시연 매장은 **가상 매장**으로 따로 만든다. 측정용 자료와 분리한다.
      - 원본 자료는 Git 제외 경로에만 둔다.
- [ ] 승인 카드가 **최소 30장** 나오는 분량이어야 한다.
      카드 3장으로는 모든 지표가 1.0 으로 나온다. 잘해서가 아니라 너무 쉬워서다.
- [ ] 원본 자료와 DB 백업은 Git 에 커밋하지 않는다.

### 입력 유형 커버리지 (전부 포함)

추출 프롬프트는 `{source_type}` 을 받는다. 유형마다 결과가 다르므로 하나만 넣으면
나머지의 추출 손실을 모른다.

| 유형 | 자료 예 | 이 유형에서만 나오는 실패 |
|---|---|---|
| `VIDEO` | 매장 둘러보기, 음료 제조 | 화면에 보이지만 말로 안 한 것 (프레임 샘플링 누락) |
| `VOICE` | 구두 인수인계 녹음 | STT 오인식 ("언더카운터" → "언더카운타") |
| `SCAN` | 레시피북, 공지·규칙 | 표·레이아웃 파싱, 한 페이지 다항목 |
| `KAKAO` | 점주–알바 대화 | 대화체 사실 추출, 화자 구분, 번복된 지시 |

- [ ] 4개 source type 을 **전부** 포함한다.
- [ ] 레시피성 자료와 비레시피성(공지·규칙·위치) 자료를 **둘 다** 포함한다.
- [ ] 활성 카테고리를 고르게 덮는다. 한 카테고리만 채우면 자동 분류를 검증하지 못한다.
- [ ] **같은 대상이 여러 자료에 걸친 경우를 반드시 포함한다.**
      예: 영상엔 제조 순서만, 레시피북엔 수량·규격. 13.3 병합 검증의 재료다.

### 다중 매장 — 개발셋과 검증셋을 미리 가른다

여러 카페로 평가한다면 **전부를 개발에 쓰지 않는다.** 전부로 프롬프트를 고치면
그 매장들에만 맞는 시스템이 되고, "정확도 N%" 가 처음 보는 매장에서 몇 %인지
아무 말도 못 하는 숫자가 된다.

| 구분 | 비율 | 용도 |
|---|---|---|
| **개발셋(dev)** | 2곳 | 프롬프트·임계값을 고친다. 몇 번이고 본다 |
| **검증셋(holdout)** | 3곳 | **봉인한다.** 개선이 끝난 뒤 한 번만 돌린다 |

- [ ] 자료 수집 **전에** 어느 매장이 dev 이고 어느 매장이 holdout 인지 정한다.
- [ ] 분할을 `api/eval/data/SPLIT.md` 에 적고 **커밋한다.**
      나중에 분할을 바꾸는 것은 부정행위다. 미리 못 박아 기록에 남긴다.
- [ ] **holdout 을 개선 중에 들여다보지 않는다.** 한 번 열면 그 순간 개발셋이 된다.
- [ ] holdout 실행은 명시적 플래그를 요구하게 해서 실수로 도는 것을 막는다.

### 진행 순서 — 1~2호점은 순차, 3호점부터 병렬

| 단계 | 병렬 가능? | 이유 |
|---|---|---|
| 자료 수집 | **가능** | 사람이 모으는 일. 서로 독립 |
| 1호점 파이프라인·포맷 확정 | **불가** | 정답지 포맷이 아직 안 굳었다 |
| 2호점으로 포맷 검증 | **불가** | 1곳으로 만든 포맷은 그 매장에 맞춰져 있다. 여기서 깨뜨려본다 |
| 3~5호점 라벨링 | **가능** | 포맷이 굳은 뒤라 서로 독립 |
| 개선 실험 | **불가** | 한 번에 하나만 바꾼다 (0절 실험 규율) |

- [ ] 1호점으로 파이프라인·정답지 포맷·지표를 먼저 확정한다.
- [ ] 2호점에서 포맷이 깨지면 **3~5호점 라벨링 전에** 고친다.
      라벨링은 사람 시간이라 가장 비싸다. 다시 하지 않게 한다.

### 매장 격리 검증이 공짜로 생긴다

매장이 하나면 골든셋의 "다른 매장에만 답이 있는 질문" 항목이 공허하다.
여러 카페가 같은 DB 에 있으면 이게 진짜 테스트가 된다.

- [ ] 5곳이 전부 같은 메뉴(예: 카페라떼)를 팔고 **레시피가 서로 다른** 상태를 만든다.
      문장이 임베딩상 거의 같으므로 `store_id` 필터가 빠지면 즉시 드러난다.
- [ ] 매장 A 질문에 매장 B 카드가 한 건이라도 섞이면 배포하지 않는다.
- [ ] 공통 용어사전과 `store_glossary` 분리는 다중 매장에서 **필수**가 된다.
      매장 A 의 은어가 매장 B 검색에 영향을 주면 격리가 의미 단위로 깨진다.

### 디렉터리와 식별자

```
api/eval/data/              ← Git 제외
  SPLIT.md                  ← 분할 기록. 이것만 커밋
  store-a/

    truth/    facts.json    ← 사실 정답지 (13단계)
              golden.json   ← 골든셋 (14단계)
    manifest.json           ← 자료 목록·수집일·유형·해시·판정자

```

- [ ] `store_slug` 는 `eval-a` ~ `eval-e` 로 둔다. 데모 매장(`demo-cafe`)과 분리한다.
- [ ] **익명 식별자만 쓴다.** 브랜드명은 `manifest.json` 에도 DB `store_name` 에도 넣지 않는다.
- [ ] `evaluation_runs.label` 에 매장과 실험을 함께 적는다. (`a-E0-baseline`, `b-E1-anchor-soft`)

### 사실 정답지

- [ ] 원본(전사문·PDF·영상)을 **사람이** 읽고 "여기 담긴 업무 사실 N개" 를 적는다.
- [ ] 각 사실에 출처 위치(페이지·타임스탬프)를 남긴다.
- [ ] 판정자·판정일을 남긴다. 누가 정한 정답인지 모르면 나중에 이견을 못 푼다.
- [ ] **매장 사실 관계는 점주 확인이 필수다.** 우리는 무엇이 맞는지 모른다.
- [ ] 사실을 **source type 별로 갈라 기록한다.** 전체 손실률만으로는 어느 프롬프트를

## 13.3. 자료 간 병합·충돌·점주 검수

> **현재 미구현이다.** `ingest/pipeline.py` 의 `_persist()` 는 추출 카드를 그대로 insert 한다.
> 기존 카드를 조회·비교·병합하지 않는다.
> `IDENTICAL/SUPPLEMENT/CONFLICT/NEW` 판정은 `learn/knowledge_loop.py` 에 이미 있으나
> `POST /learn/pending/{id}/answer`(점주 답변)에서만 호출된다.
> 같은 지식인데 **들어온 경로에 따라 다르게 취급되고 있다.**

### 병합

- [ ] 추출 카드를 적재하기 전에 같은 매장의 기존 카드와 대조한다.
- [ ] `knowledge_loop` 의 관계 판정을 재사용한다. 새 판정기를 만들지 않는다.
- [ ] **자동으로 덮어쓰지 않는다** (불변식 9). 보완·충돌은 `knowledge_change_proposals` 로
      올려 점주가 결정한다.
- [ ] 재실행·retry 가 같은 제안을 중복 생성하지 않게 한다.
- [ ] 병합 판정에 쓴 근거(어느 자료의 어느 위치)를 양쪽 다 보존한다.

### 자료 우선순위 — 참고값일 뿐 확신이 아니다

```
점주 직접 답변·수정  >  레시피북 = 최근 공지  >  나머지 문서·영상·음성·카톡 (전부 동등)
```

- [ ] `sources` 에 자료 권위 등급을 둔다. 위 3단계로 둔다. 나머지는 서로 우열을 두지 않는다.
- [ ] **이 등급은 정렬·기본 제안용 참고값이다. 자동 확정 근거가 아니다.**
      상위 등급 자료라고 해서 옳다는 보장이 없다. 레시피북이 오래됐을 수도,
      공지가 번복됐을 수도 있다. **검수를 통과하기 전에는 어느 값도 확정이 아니다.**
- [ ] 숫자·수량이 충돌하면 상위 등급 자료의 값을 **기본 제안**으로 올린다.
      화면에서 미리 선택된 상태로 보여주되, **점주가 바꿀 수 있어야 한다.**
- [ ] 등급은 migration 으로 컬럼을 추가하고, 기본값은 업로드 시 유형에서 유추하되
      점주가 바꿀 수 있게 한다.

### 관계가 잡히면 4종 전부 검수로 올린다

> **`IDENTICAL`·`NEW`·`SUPPLEMENT`·`CONFLICT` 어느 쪽이든 검수 대상이다.**
> 관계 판정 자체가 기계의 추정이다. 판정이 맞는지도 사람이 봐야 한다.
> `IDENTICAL` 이라고 조용히 연결해버리면, 판정이 틀렸을 때 아무도 모른다.

- [ ] 관계가 잡히면 **새 카드와 검사에 걸린 기존 카드를 전부 묶어** 검수 요청을 만든다.
      기존 카드 하나만이 아니라 **매칭된 모든 카드**를 함께 보여준다.
- [ ] 검수 항목에 표시할 것:
      - 판정된 관계(`IDENTICAL`/`NEW`/`SUPPLEMENT`/`CONFLICT`)와 **그 판정이 틀렸다고 할 수 있는 수단**
      - 값이 다른 지점과 **각각의 출처**
        (예: `평가용 카페 자료 A` 영상 3:14 "225ml" vs 같은 자료 문서 12행 "275ml")
      - 각 출처의 권위 등급. 단 **참고 표시일 뿐 선택을 강제하지 않는다**
- [ ] 점주가 결정하기 전에는 **어느 쪽도 검색·학습에 노출하지 않는다.** 기존 공개본을 유지한다.
- [ ] 점주 결정 후 공개 버전이 바뀌면 학습 재확인(`RECONFIRM_REQUIRED`)이 걸린다.
- [ ] 검수 없이 자동 공개되는 경로를 만들지 않는다.

### 병합·충돌 검증 (필수 테스트)

- [ ] 같은 메뉴를 영상·레시피북 두 자료로 넣고 카드가 **합쳐지는지** 확인한다.
- [ ] 여러 자료에 걸친 사실(영상엔 제조 순서, 레시피북엔 수량)이 **한 카드에 모이는지** 확인한다.
- [ ] **같은 이름 다른 규격은 별도 카드로 유지되는지** 확인한다.
      예: HOT 카페라떼(스팀우유 275ml)와 ICE 카페라떼(우유 8부 225ml)는 **합치면 안 된다.**
- [ ] 숫자 충돌(225ml vs 275ml)이 `CONFLICT` 제안으로 올라가는지 확인한다.
- [ ] **`IDENTICAL` 판정도 검수로 올라가는지** 확인한다. 조용히 연결되면 안 된다.
- [ ] **`NEW` 판정도 검수 없이 공개되지 않는지** 확인한다.
- [ ] 기존 카드가 여러 장 매칭되면 **그 전부가 한 검수 항목에 묶이는지** 확인한다.
- [ ] 상위 등급 자료의 값이 기본 선택돼 있되 **점주가 하위 등급 값을 고를 수 있는지** 확인한다.
- [ ] 점주가 결정할 때까지 기존 공개 카드가 그대로인지 확인한다.
- [ ] 같은 자료를 다시 넣어도 중복 카드·중복 제안이 생기지 않는지 확인한다.

# 14단계 — 읽기 경로: 질문 → 근거 기반 답변 (RAG)

> **책임 분리.** 이 단계는 "카드가 이미 제대로 있다" 고 전제하고
> 질문 → 검색 → 근거 게이트 → 생성 → 검증만 다룬다.
> 카드 자체의 품질은 13단계 책임이다.
>
> **13단계의 `E-O0` 없이 시작하지 않는다.** 추출 손실을 모르면 검색을 오진한다.

## 14.1. 평가 하네스 [완료]

- [x] 인증된 내부 전용 `/team/evaluations` 생성·조회 API를 구현한다.
      게이트는 JWT `scope="team"`. `/auth` 로그인 토큰으로는 403, 매장 교차 조회는 404 로 실측 확인.
- [x] 기존 `quality_evaluations` 테이블과 실행 이력을 연결한다.
      같은 표에 섞지 않고 `quality_evaluations.evaluation_run_id` 포인터로 연결한다.

미측정으로 남은 것:

- [ ] 실제 기준선은 13.2 골든셋(30~50문항)으로 잰다. 현재 통과한 것은 카드 3장 기준 스모크 8문항이다.

## 14.2. 골든셋과 사람 판정

### 사람 판정은 필수다 (생략 불가)

MRR·nDCG 는 **정답을 판별하지 않는다.** 사람이 정해준 정답 대비 순서만 잰다.
`expected_card_ids` 는 채점의 입력이지 산출이 아니다. **라벨 품질이 하네스 전체의 천장이다.**

- [ ] **pooling 으로 라벨링한다.** 전수(질문 50 × 카드 50)는 불가능하다.
      각 질문을 현재 검색기로 돌려 상위 10개만 뽑고, 그 10개에만 관련/무관을 판정한다.
- [ ] **두 종류의 판정을 가른다.**
      - 매장 사실 관계("우유는 언더카운터 2단이 맞는가") → **점주만 안다. 점주 확인 필수**
      - 검색 관련성("이 질문에 이 카드가 관련 있는가") → 팀이 판정 가능
- [ ] 판정자·판정일을 남긴다.
- [ ] **검색 로직을 바꾸면 풀을 다시 판정한다.** pooling 의 약점은 현재 검색기가 한 번도
      못 끌어온 카드가 영원히 '정답 아님'으로 남는 것이다.
- [ ] **13단계 카드가 확정된 뒤에 라벨링한다.** 카드가 바뀌면 `expected_card_ids` 가
      전부 어긋나 골든셋이 무효가 된다.

### 골든셋 30~50문항 구성 요건

- [ ] 각 질문에 기대 카드 ID, 핵심 사실, 답변 가능 여부, 카테고리, 근거를 라벨링한다.
- [ ] 숫자·온도·시간·용량·고유명사·부정문·예외를 포함한다.
- [ ] 정식어, 동의어, 줄임말, 현장 은어, 오타와 음성 인식 변형을 포함한다.
- [ ] 답이 없는 질문과 다른 매장에만 답이 있는 질문을 포함한다.
- [ ] 안전·위생·응급 질문의 거절 또는 직접 확인 경로를 포함한다.
- [ ] `IDENTICAL`, `NEW`, `SUPPLEMENT`, `CONFLICT` Q&A 관계를 각각 포함한다.
- [ ] Q&A 기반 카드의 카테고리·로드맵·FAQ 반영을 포함한다.
- [ ] **여러 자료에 걸쳐야 답이 나오는 질문을 포함한다.**
      예: "아이스 카페라떼 우유 몇 ml예요?" — 영상만으론 못 답하고 레시피북까지 합쳐야 나온다.
- [ ] **같은 이름 다른 규격을 가르는 질문을 포함한다.** (HOT/ICE, 사이즈별)

## 14.6. 하이브리드 검색과 LLM reranker

필수 비교군:

| 실험군 | 용어사전 | LLM reranker |
|---|---:|---:|
| 기준 | 미적용 | 미적용 |
| 사전 효과 | 적용 | 미적용 |
| reranker 효과 | 미적용 | 적용 |
| 최종 후보 | 적용 | 적용 |


- [ ] lexical/BM25와 vector 점수를 결합해 상위 후보를 만든다.
      결합은 **RRF(Reciprocal Rank Fusion)** 로 한다. BM25 점수와 코사인 유사도는 척도가 달라
      가중합이 성립하지 않는다. RRF 는 순위만 쓰므로 이 문제를 우회한다.
      효과는 13단계 하네스의 MRR·nDCG@10 전후 비교로 판정한다.
      상수 `k`(관례 60)도 가정하지 말고 하네스로 정한다.
- [ ] **`RETRIEVAL_THRESHOLD` 게이트는 RRF 앞단에 그대로 둔다.**
      RRF 는 순위만 다루므로 후보가 전부 형편없어도 1등을 뽑아준다.
      miss 판정은 계속 원 점수로 한다. 안 그러면 `false_block_rate` 는 내려가고
      근거 없는 답변이 올라간다.
- [ ] 질문과 같은 매장의 승인된 현재 카드만 후보에 포함한다.
- [ ] 상위 후보 수를 제한하고 질문과 카드만 LLM reranker에 전달한다.
- [ ] reranker는 순위, 관련도, answerable, 짧은 근거만 구조화 JSON으로 반환한다.
- [ ] reranker가 카드에 없는 사실이나 최종 사용자 답변을 만들지 못하게 한다.
- [ ] timeout, schema 오류, 모델 오류 시 기존 검색 순위로 폴백한다.
- [ ] 기능 플래그로 즉시 비활성화할 수 있게 한다.
- [ ] **벤더 호출부를 어댑터 인터페이스 뒤로 뺀다.** 교체가 플래그 한 줄이 되지 않으면
      비교 실험 자체가 불가능하다. 실험의 전제조건이다 (`이관경계_실험설계.md` 6-4절).
- [ ] 한 단계에는 한 벤더만 쓴다. 단계별로는 달라도 된다.
- [ ] latency, token, 비용, 순위 변화와 정답률을 기록한다.
- [ ] 사전·hybrid·reranker 네 비교군을 13단계 골든셋과 실제 입력셋으로 평가한다.
- [ ] 근거 없는 답변률 또는 매장 격리가 악화되면 배포하지 않는다.
- [ ] 검색 결과가 충분해도 최종 근거 검증과 안전 폴백은 유지한다.

# 통합 검증 — E2E와 CI 게이트 (13·14단계 공통)

> 쓰기·읽기 양쪽이 닫힌 뒤에 돈다. 전체 순환을 한 번에 검증하므로 어느 한 단계에 속하지 않는다.

## 통합·E2E

- [ ] 사장님 1명과 직원 2명의 전체 순환을 자동화한다.
- [ ] 업로드 → job → 카드 → 승인 → 로드맵 → 질문 → 답변을 검증한다.
- [ ] miss → 점주 답변 → 카드 신규/보완/충돌 검토 → 재질문을 검증한다.

# 실행 요청 순서

**책임이 갈려 있다. 13단계는 쓰기(자료 → 카드), 14단계는 읽기(질문 → 답변)다.**
쓰기를 먼저 닫는다 — 추출이 흘린 사실은 검색으로 복구되지 않는다.

## 13단계 — 쓰기 경로

1. ~~`12.5-3 개발 스킬`~~ — 완료
2. `13.1 평가 자료 확정하고 사실 정답지 만들자` — **다음 차례.**
   4개 source type 전부, 카드 30장 이상, 사람 판정. 자료가 먼저 정해져야 시작한다
3. `13.2 추출 평가 하네스 만들고 E-O0 재줘`
4. `13.3 자료 간 병합·충돌 붙여줘` — 현재 미구현. 충돌은 점주 검수로
5. `13.4 입력·추출 품질 개선해줘` — E-O0 손실이 큰 유형부터
6. `13.5 RECIPE/TASK 카드 모델 해줘`

## 14단계 — 읽기 경로

7. `14.2 골든셋 만들자` — 13단계 카드가 확정된 뒤에
8. `14.3 E0 기준선 찍고 병목 진단해줘` — E-O1/E-O2/E-O3
9. `14.4~14.5 검색 기반과 용어사전 해줘` (E1·E2 — 원가 0, 이득 확인 시 즉시 승격)
10. `14.6~14.7 하이브리드·reranker와 보안 해줘` (E6 — 원가 계산 후)

## 마무리

11. `통합 검증 해줘` — E2E와 CI 게이트
12. `15단계 운영 인수 진행해줘`

## 순서를 바꾸지 않는 것

- **자료 확정 전에 라벨링하지 않는다.** 자료를 나중에 추가하면 정답지가 무효가 된다.
- **13단계 카드가 확정되기 전에 골든셋을 만들지 않는다.** 카드가 바뀌면 기대 카드 ID가 어긋난다.
- **`E-O0` 없이 검색을 고치지 않는다.** 추출 손실을 모르면 검색을 오진한다.
- **`E0`·병목 진단 없이 모델·벤더 교체 실험을 시작하지 않는다.**
  "Claude가 더 좋다더라"는 실험이 아니다.
