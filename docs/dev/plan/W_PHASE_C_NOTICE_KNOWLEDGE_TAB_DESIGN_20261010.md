## 3. 지금 코드에서 확인할 것 (계획 단계)
- 직원 하단 탭·상단 버튼 컴포넌트(`web/components/kit/tab-bar.tsx`, 레시피 탭 화면), 카드 목록 API 가 카테고리·로직으로 걸러지는지.

## 4. 설계

### C-D1 공지 데이터
- 표 `store_notices`(가산 migration): `notice_id`, `store_id`, `title`, `body`, `valid_from`·`valid_until`(nullable), `status`(`DRAFT`·`PUBLISHED`·`HIDDEN`), `origin`(`EXTRACTED`·`OWNER_WRITTEN`), `source_id`·`segment locator`(추출일 때 근거), `created_by`, `published_at`, `created_at`.
- 표 `store_notice_cards(store_id, notice_id, card_id)` — 그 공지로 바뀐 카드 연결("바뀐 카드 N개"로 이동).
- 표 `store_notice_reads(store_id, notice_id, user_id, read_at)` — 사람마다 읽음.
- 매장 격리: 모든 함수 `store_id` 필수, JWT 매장.

### C-D2 공지가 만들어지는 길
1. **분류기 → `NOTICE` 구간**(Phase B): 그 구간을 공지 추출 로직이 제목·본문·기간으로 정리해 `DRAFT` 공지로 만든다(Phase B 의 `NOTICE` 사실 검수 대기를 이 표로 대체). 같은 자료의 지식 변경 구간은 카드 쪽으로 가고, 이어진 카드를 `store_notice_cards` 에 잇는다.
2. **점주 직접 작성**: 점주 화면에서 제목·본문·기간 입력 → `DRAFT` 또는 바로 게시.
3. 점주가 `DRAFT` 를 확인·수정 → 게시(`PUBLISHED`). 게시 시 직원 알림(기존 앱 내 알림 + Web Push, D15)은 계획 단계에서 범위 확인.

### C-D3 직원 화면
- **상단 공지 버튼**(C-U2): 마이페이지 버튼 왼쪽. 안 본 개수 = 게시됐고 기간이 끝나지 않았고 읽지 않은 공지 수. 0 이면 숫자 없음. 누르면 공지 목록.
- **공지 목록**(C-U4): 최신순(`published_at` 내림차순). 기간 끝난 공지는 회색 + "기간 끝남". 공지를 열면 읽음 처리, 본문 + 기간 + "바뀐 카드" 링크.
- **매장 지식 탭**(C-U3): 맨 위 "공지사항"(안 본 개수 표시) → 그 아래 카테고리 목록(카드 수) → 카테고리 → 카드 목록(지금 레시피 탭 카드 모양 재사용: 카테고리 칩·제목·확인 상태·"바뀌었어요") → 카드 상세.
- **레시피 탭**(C-A1): 메뉴 카드만. 카드에 로직 값이 필요하다 → 카드 판을 만들 때 그 카드 사실들의 분류 로직(Phase B 기록) 중 다수를 `knowledge_cards.logic`(가산 칸)에 둔다. 점주가 바꿀 수 있게 할지는 계획 단계에서 확인.

### C-D4 점주 화면
- 공지 관리: 초안 목록(추출됨) · 게시됨 · 직접 쓰기 · 숨기기.
- 업로드 결과 요약에 "공지 N개 초안" 표시.

## 5. 검증
- 단위: 안 본 개수(기간·읽음·상태), 최신순·회색 판정(매장 시간대 기준), 공지 ↔ 카드 연결, 격리.
- 실제 DB: 분류기 `NOTICE` 구간 → 공지 초안 → 게시 → 직원 목록·읽음; 지식 변경 구간 → 카드 새 초안과 공지 연결.
- web: `pnpm check`, 저장소 스킬 2개, 합성 API Playwright(390·360): 공지 버튼 개수, 목록 회색, 매장 지식 맨 위 공지사항, 카테고리 → 카드.

## 6. 범위 밖
공지 예약 게시, 공지 댓글·확인 서명, 근무조별 공지 대상, 공지 내용을 R 답변 근거로 쓰기(필요하면 R 과 계약 검토).
