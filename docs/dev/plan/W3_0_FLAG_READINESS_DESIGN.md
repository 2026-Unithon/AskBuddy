# W3-0 설계 — W2 플래그를 배포판에서 켤 수 있게 만들기 (2026-10-07)

> W3 는 **W3-0 → W3a → W3b** 순서로 나눈다(2026-10-07 사용자 결정).
> W3-0: W2 구조(대상·revision·업로드 제안)를 실제로 켤 수 있게 정리한다. 이 문서의 범위.
> W3a: 대상 단위 사실 조립(CardPlan)·조립 호출 병렬화(W_NEXT_PLAN Task W3-1b) → 서버 검증·렌더링 → 블록 고정·occurrence 처분 → 공개판에 사실 싣기. 다음 스펙.
> W3b: 점주 카드 검수 화면(사실·문장 단위 추가·수정·삭제·순서 변경). 그다음 스펙.

## 1. 목표와 완료 조건

**목표:** 지금은 기본 꺼져 있는 `w_entity_revision_enabled`·`w_upload_proposals_enabled` 를 **배포판에서도 켤 수 있는 상태**로 만든다.
켜면 그 뒤로 올라오는 자료부터 대상·불변 revision·충돌·업로드 제안이 쌓이고, W3a 가 그 결과를 입력으로 쓴다.

**완료 조건**
1. 아래 §3 의 고칠 것이 모두 구현되고 단위 테스트·실제 DB 검증을 통과한다.
2. 두 플래그를 켠 **합성 종단 검증**(§3-6)이 실제 DB 에서 통과한다.
3. 처리량 측정(§3-5) 결과가 `docs/dev/review/` 에 기록돼 있다.
4. 배포판 켜기 절차(§3-7)가 문서로 준비돼 있다. **실제로 배포 환경 값을 바꾸는 일은 사용자가 한다.**

## 2. 사용자 결정 (2026-10-07)

| 결정 | 내용 |
|---|---|
| 범위 나누기 | 선행 정리(W3-0) → W3a → W3b |
| 소급 이관 | **하지 않는다.** 기존 `source_facts`·카드는 그대로 두고, 플래그를 켠 뒤 올라온 자료만 새 구조로 간다. 옛 자료와 새 자료의 같은 대상 사실은 모이지 않는다(자료를 다시 올리면 모인다) |
| HOT/ICE 동시 | 한 사실에 HOT·ICE 가 함께 적혀 있고 값이 공통이면 **규격별 두 사실로 나눈다**(D19) |
| 플래그 켜기 | W3-0 완료 후 **배포판도 켠다**(사용자가 환경 값을 바꿈) |

이전 결정(W2, 2026-09-29)은 그대로다: 대상은 정규화 이름·별칭 정확 일치만 자동 병합, 비슷한 이름은 후보 제안만. 값 충돌은 나란히, 기본 선택 없음.

## 3. 할 일

### 3-1. HOT/ICE 동시 사실을 규격별 두 사실로 나누기 (원장 단계)

**어디서:** 추출 결과를 원장에 저장하기 직전(`api/app/ingest/pipeline.py` `_persist_ledger` 의 `insert_source_facts` 앞).
`validate_assertions`(`api/app/ingest/occurrences.py:235`) 가 판정을 붙인 뒤의 사실 목록을 받아 나눈다.

**규칙**
- 대상: `variant` 를 `entity_names.parse_variant` 로 읽었을 때 온도가 **HOT 과 ICE 둘 다** 나오는 사실(지금 `VARIANT_MULTI` 로 표시되는 것).
- 결과: 원래 사실 하나 → HOT 사실 하나 + ICE 사실 하나. 값·단위·부정·조건·예외·순서·근거 인용(`evidence`)·`original_assertion` 은 같다.
  `variant` 는 각각 HOT/ICE(사이즈 등 나머지 규격 낱말은 유지).
- `local_ref`: `<원래 ref>~HOT`, `<원래 ref>~ICE`. 다른 사실의 `requires` 가 원래 ref 를 가리키면 **둘 다**를 가리키게 바꾼다.
- 근거 위치(occurrence)는 두 사실 모두 원래 위치를 그대로 갖는다(같은 구간·같은 locator).
- 나눴다는 표시를 `check_flags` 에 남긴다(예: `{"variant_split": "HOT_ICE"}`) — 검수·디버깅에서 원래 한 문장이었음을 알 수 있게.
- 온도 외 규격(사이즈 둘 이상 등)은 이번에 나누지 않는다. 지금처럼 `other` 로 남고 `VARIANT_MULTI` 사유가 붙는다.

**플래그:** `w_entity_revision_enabled` 가 켜졌을 때만 나눈다. 꺼져 있으면 원장 쓰기가 지금과 바이트 단위로 같다
(평가 기준선 D16 보호 — 평가 실행은 플래그를 켜지 않는다).

**왜 원장 단계인가:** D19 는 "사실(`source_facts`)은 `variant` 로 갈라 저장한다" 고 정했다. 원장에서 나누면 그 아래(대상·revision·충돌·제안, W3a 조립)가
바꿀 것 없이 그대로 동작한다. W2 연결 단계에서 나누면 `uq_fact_occurrences_sfo`(근거 위치 하나에 판 하나) 를 바꿔야 하고 원장↔판 1:1 이 깨진다.

### 3-2. `import_legacy_correction` 적용 순서

`api/app/ingest/fact_revisions.py:300`. 점주가 이미 정정한 사실(head 가 EXTRACTION 이 아닌 판) 위에
더 오래된 `corrected_value` 를 새 head 로 얹지 않는다.
- head 의 `change_kind` 가 EXTRACTION 이 아니면 아무것도 쓰지 않고 `None` 을 돌려주며, 건너뛴 사유를 로그에 남긴다.
- 같은 이관을 다시 돌려도 결과가 같다(멱등, 기존 `legacy_source_fact_id` 검사 유지).

### 3-3. W2 에서 넘어온 정합성 정리

1. **병합된 대상이 낀 후보:** `merge_entities` 가 (병합된 대상, 제3 대상) PENDING 후보를 남기지 않는다.
   남은 대상(keep)과 제3 대상 사이에 같은 후보가 없으면 keep 쪽으로 다시 걸고, 이미 있으면 옛 후보를 닫는다(사유 `MERGED`). 이력 이벤트를 남긴다.
2. **병합 뒤 재처리의 제안 중복:** 업로드 제안을 만들 때 대상 ID 를 병합 체인 끝(살아 있는 대상)으로 바꿔 찾는다.
   병합된 대상 아래 PENDING_REVIEW 제안이 있으면 새로 만들지 않고 그 제안을 살아 있는 대상으로 옮긴다(이력 남김). 결정된 제안은 건드리지 않는다(W2 Ruling J 유지).
3. **같은 순위 재처리의 `matched_cards`:** PENDING_REVIEW 제안은 관계 순위가 같아도 `matched_cards` 를 새 계산으로 갱신한다.

### 3-4. 점주 답변 삭제 경로 확인 (확인 결과 기록)

R 소유 `owner_answers` 는 트리거가 R revision 이 붙은 답변의 삭제·원문 수정을 막는다
(`supabase/migrations/20260917130000_m3_owner_answer_delivery.sql:46`, `owner original is immutable`).
앱 코드에는 `owner_answers`·`pending_questions` 를 지우는 경로가 없다(계획 단계 확인).
따라서 W 링크(`fact_revision_meta.owner_answer_id`·`fact_owner_answer_links`)의 `on delete restrict` 가 새로 막는 제품 삭제 경로는 없다.
**코드 변경 없이** 이 사실을 `W_NEXT_PLAN` 플래그 점검 항목과 R 인계 문서 8번에 적어 닫는다.
매장 삭제는 기존과 같이 불변 원장들 때문에 막히며, 데모 매장은 보관 방식으로 처리한다(현행 유지).

### 3-5. 처리량 측정

- 합성 대량 자료(예: 사실 300건, 대상 60개, 구간 10개)를 실제 DB 에서 처리하며 잰다:
  자료당 연결 시간, 매장 advisory lock 을 쥔 시간, 대상 하나당 후보 계산 시간, 동시 구간 2개일 때 대기 시간.
- **합격선은 두지 않는다**(카드 생성 지연 상한은 D21 에서 보류). 숫자와 측정 조건을 기록하고,
  매장 lock 을 쥔 시간이 자료 처리 전체 시간의 큰 몫을 차지하면 그 사실을 적는다.
- 결과: `docs/dev/review/W3_0_THROUGHPUT_<날짜>.md`. 측정 스크립트는 `api/scripts/` 에 남긴다(합성 데이터만, 모델 호출 없음).

### 3-6. 합성 종단 검증 (두 플래그 켜고)

실제 DB(`verify_r_schema_rebuild.py` 가 부르는 W 검증)에 시나리오를 더한다. 모델은 합성 대역, 비용 0.
1. 자료 A(영상 구간 2개 동시 처리) 업로드 → 대상·판·occurrence·충돌·제안 생성.
2. 자료 B 에 HOT/ICE 동시 사실 → 두 사실로 갈라져 각 규격 슬롯에 들어감(§3-1).
3. A 와 값이 다른 사실 → 충돌 양쪽 보존, 기본 선택 없음.
4. A 재처리 → 중복 없음.
5. 대상 병합 → 후보·제안 정리(§3-3), 병합 뒤 재처리에서 제안 중복 없음.
6. 대상 분리 → 이력, 공개본·기존 카드 행 불변.
7. 점주 정정 → 새 판, 옛 이관 정정은 그 위에 얹히지 않음(§3-2).
8. 플래그를 다시 끈 뒤 처리 → 새 W2 행이 생기지 않고, 이미 쌓인 행은 그대로.

### 3-7. 배포판 켜기 절차 (문서)

`docs/dev/plan/W3_0_FLAG_ROLLOUT.md` 에 적는다. 실행은 사용자가 한다.
1. 배포 DB 에 W2 migration 3개(`20260930090000`·`100000`·`110000`)와 W3-0 에서 더한 것이 적용됐는지 확인하는 조회문.
   migration 은 배포 워크플로(`.github/workflows/deploy-api.yml` 의 `supabase db push`)가 서버 배포 **전에** 적용한다 — 순서는 이미 맞다.
2. 배포 서버의 API 환경 값에 두 플래그를 켜는 방법(값 이름 `W_ENTITY_REVISION_ENABLED=true`·`W_UPLOAD_PROPOSALS_ENABLED=true`,
   서버 env 파일 위치는 `.github/scripts/ssm_deploy.sh` 가 쓰는 서버 스크립트 기준으로 계획 단계에서 확인해 적는다).
   `w_upload_proposals_enabled` 는 `w_entity_revision_enabled` 를 요구한다(설정 검증이 막음). 코드 기본값은 계속 꺼짐.
3. 켠 뒤 확인할 것: 새 업로드 1건 처리 후 대상·판·occurrence 행 수, 오류 로그, 처리 시간.
4. 되돌리기: 플래그를 끄면 새 쓰기만 멈춘다. 쌓인 행은 지우지 않는다(불변 원장).

## 4. 하지 않는 것

- 기존 자료·카드의 소급 이관.
- 카드 조립·렌더링·공개판 변경(W3a), 검수 화면(W3b).
- 사이즈 둘 이상인 사실 나누기.
- 배포 환경 값 직접 변경, 실제 유료 모델 실행.
- R 소유 파일 수정(`owner_answers` 트리거 포함).

## 5. 제약 (W_NEXT_PLAN §2 와 같음)

매장 격리(store_id 필수·WHERE), 가산 migration(이미 적용된 파일 수정 금지), 공통 파일 가산 변경, 새 동작은 플래그 뒤,
플래그 꺼짐이면 원장·수집 DB 쓰기 불변, 주석 한국어, 실제 브랜드·상호·메뉴 고유명 금지, 커밋은 사용자가 한다.
검증: `pytest`, 실제 DB 재구축(`verify_r_schema_rebuild.py`), 매장 격리 검사.

## 6. 위험

- **HOT/ICE 나누기 오판:** `parse_variant` 가 HOT·ICE 를 둘 다 읽었지만 실제로는 "HOT 만, ICE 는 별도 값" 인 문장일 수 있다.
  값이 공통이라는 판단은 추출 모델이 한 사실로 냈다는 점에 기댄다. `check_flags` 표시로 검수에서 되돌아볼 수 있게 한다.
- **배포 후 처리 지연:** 매장 lock 이 수집을 매장 단위로 줄 세운다. §3-5 측정이 크면 켜기 전에 사용자에게 알린다.
- **소급 없음의 한계:** 플래그를 켠 직후에는 대상 사실이 적어 W3a 조립·업로드 제안이 빈약하다. 자료를 다시 올리면 모인다.
