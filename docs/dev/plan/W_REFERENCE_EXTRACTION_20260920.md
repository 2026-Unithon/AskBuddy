# 참조 추출 — 형식과 규칙

> 2026-09-20. 평가 트랙 문서다. 제품 코드가 아니다.
> 강한 모델에 자료를 직접 먹여 뽑은 사실을 **참조(reference)** 로 둔다.
> **참조는 정답지가 아니다.** 사람 검토를 거친 것만 정답지로 승격한다.

## 왜 필요한가

현재 정답지가 전수가 아니라 표본이다. `a-scan-recipebook` 기준:

| | |
|---|---|
| 정답 사실 | 28건 |
| 그 안의 메뉴 종류 | 17개 |
| 문서의 실제 메뉴 | 약 101개 |
| 판매가가 적힌 메뉴 | 6개 |

이 정답지로 재면 **문서를 전부 정확히 읽어도 대부분이 점수를 못 받는다.**
정답지에 없는 사실은 `판정불가`나 `오연결`로 떨어지므로, 많이 뽑을수록 불리해진다.
실제로 2026-09-19 실행에서 뽑은 주장 99건 중 94건이 `판정불가`였다.

참조 추출은 이 표본을 전수에 가깝게 넓히기 위한 **재료**다.

## 역할 한계 — 지키지 않으면 측정이 거짓말이 된다

1. **생성과 판정을 같은 세션에 맡기지 않는다.** 사실을 뽑은 세션이 "맞다"고
   하는 것은 독립 검증이 아니다. RD-01 의 외부 AI 판정은 **판정** 역할이고
   이 문서는 **생성** 역할이다.
2. **검토 전에는 정답지로 쓰지 않는다.** 참조를 그대로 정답지로 삼으면 이후
   측정하는 값은 정확도가 아니라 그 모델과의 일치율이다.
3. **매장 사실 확인이 아니다.** 참조도 정답지도 `owner_confirmed = TEST` 다.
   자료에 그렇게 적혀 있다는 뜻이지 현재 매장이 그렇게 운영한다는 뜻이 아니다.
4. **참조가 우리 파이프라인보다 항상 옳다고 가정하지 않는다.** 참조도 틀린다.
   불일치는 "우리가 틀렸다"가 아니라 "둘이 다르다"로 기록하고 사람이 가른다.

## 브랜드명 취급

자료 원문에는 실제 상호·메뉴 고유명이 있다. 참조 추출 결과에도 그대로 남는다.

- 결과 파일은 **Git 제외 경로에만** 둔다 (`api/eval/data/<store>/` 아래).
  이 경로는 `.gitignore` 에 이미 잡혀 있다.
- 커밋 메시지·`docs/`·코드 주석·테스트 픽스처에 옮기지 않는다 (CLAUDE.md).
- 정답지(`truth/facts.json`)는 익명 표현을 쓴다. 원본↔익명 대응은 각 매장의
  `MENU_MAP.json` 에 있고 그 파일도 커밋하지 않는다.
- 참조를 정답지로 승격할 때 `MENU_MAP.json` 의 익명 표현으로 바꾼다.
  검사는 `scripts/check_eval_data.py` 가 한다.

## 스키마

`results` 배열 하나만 담은 JSON. 각 원소는 아래 필드를 갖는다.

| 필드 | 필수 | 설명 |
|---|:-:|---|
| `fact_id` | ✓ | `<접두사>-0001` 부터. 접두사는 자료마다 다르게 (예: 레시피북 `rb`) |
| `subject` | ✓ | 사실의 대상. 메뉴명·기물명·규칙 이름 |
| `variant` | ✓ | 규격 구분. `HOT`/`ICE` 등. 없으면 `null` |
| `attribute` | ✓ | 속성 이름. 아래 규칙 참고 |
| `value` | ✓ | **단위를 뺀 값** (`"275"`). 단위는 `unit` 에 |
| `unit` | ✓ | `"ml"`·`"g"`·`"oz"`·`"샷"`·`"분"` 등. 없으면 `null` |
| `polarity` | ✓ | `AFFIRM` 또는 `NEGATE`. "넣지 않는다"는 `NEGATE` |
| `conditions` | ✓ | 적용 조건 배열. 없으면 `[]` |
| `exceptions` | ✓ | 예외 배열. 없으면 `[]` |
| `step_order` | | 순서가 있는 사실의 번호. 없으면 `null` |
| `original_assertion` | ✓ | **원문 표현 그대로.** 값을 되짚는 근거 |
| `page` | ✓ | 근거가 있는 쪽 번호 (1부터) |
| `must_have` | ✓ | 이 사실이 빠지면 업무가 안 되는가 |
| `source_key` | ✓ | manifest 의 `source_key` (예: `a-scan-recipebook`) |
| `source_type` | ✓ | `SCAN`·`VIDEO`·`VOICE`·`KAKAO` |

### `value` 와 `unit` 을 나누는 이유

원장의 중복 판정 열쇠가 `unit` 을 포함한다. `275ml` 와 `275g` 은 다른 사실이고,
값만 보면 한 행으로 합쳐져 뒤엣것이 사라진다. 참조도 같은 기준으로 나눠야
우리 산출물과 대조가 된다.

값이 숫자가 아니면 (`"물 8부"`, `"가득"`) `value` 에 그대로 쓰고 `unit` 은 `null`.
괄호 환산값이 있으면 (`"물 8부 (425ml)"`) 원문은 `original_assertion` 에 남기고
`value`/`unit` 은 환산값 기준으로 적는다.

### `polarity`·`conditions`·`exceptions` 를 요구하는 이유

같은 값이라도 조건·부정이 다르면 다른 사실이다. "여름엔 얼음 3개"와
"겨울엔 얼음 3개"가 한 건으로 합쳐지면 뒤엣것이 사라진다. 원장도 같은 기준으로
고쳐 두었다.

### `attribute` 규칙

같은 뜻을 다른 이름으로 적으면 대조가 안 된다. 액상류는 내용에 따라 가른다.

```
판매가 · 제조순서 · 컵 · 샷 수 · 얼음 · 재료 · 토핑 · 분류
스팀우유량 · 온수량 · 우유량 · 물량 · 사이다량 · 콜라량 · 베이스량 · 원액량
블렌더 회전수 · 우리는 시간 · 1펌프 용량
```

목록에 없는 속성이 필요하면 새로 만들되, **같은 실행 안에서 일관되게** 쓰고
결과 파일의 `meta.new_attributes` 에 적는다.

## 파일 위치와 이름

```
api/eval/data/<store>/reference/<source_key>__<모델>__<YYYYMMDD>.json
```

예: `api/eval/data/store-a/reference/a-scan-recipebook__claude-opus-5__20260920.json`

같은 자료를 다시 뽑으면 **덮어쓰지 않고 새 파일**로 남긴다. 참조끼리의 변동도
정보다.

## 함께 기록할 메타

파일 최상위에 `meta` 를 둔다. 없으면 나중에 "그때 그 참조"가 무엇이었는지
짚을 수 없어 비교가 무의미해진다 (D17).

```json
{
  "meta": {
    "source_key": "a-scan-recipebook",
    "source_sha256": "<원본 파일 해시>",
    "model": "<모델 이름과 버전>",
    "extracted_at": "2026-09-20",
    "method": "페이지 래스터화 후 판독 · 숫자 칸 크롭 확대 재확인",
    "pages": 3,
    "rows_transcribed": 101,
    "self_check": "판매가/제조순서/분류가 각각 101 — 행 누락 없음",
    "new_attributes": [],
    "notes": "표기 차이·불확실한 셀을 여기에 남긴다"
  },
  "results": []
}
```

`source_sha256` 은 `shasum -a 256 <파일>` 로 구한다. 원본이 바뀌면 참조도
무효다.

## 불확실한 것은 비우지 않는다

읽히지 않는 셀을 빈 값이나 추정으로 채우지 않는다. 그 사실을 **빼고**,
`meta.notes` 에 어느 쪽 무엇이 안 읽혔는지 적는다. 추정으로 채우면 정답지로
승격될 때 틀린 값이 정답이 된다.

## 실행할 세션에 줄 지시문

아래를 그대로 붙여 쓴다. 자료 파일을 함께 올린다.

```
첨부한 문서에서 업무에 필요한 사실을 빠짐없이 뽑아 JSON 으로 주세요.

방법
- 페이지를 이미지로 렌더해 직접 읽으세요. 숫자 칸이 흐리면 그 부분을
  크롭·확대해 다시 확인하세요.
- 표는 행 단위로 먼저 전사한 뒤, 코드로 사실로 펼치세요. 사실을 하나씩
  손으로 쓰면 뒤로 갈수록 빠집니다.
- 다 만든 뒤 검증하세요: 모든 행이 같은 속성 집합을 갖는지, 행 수가 표의
  행 수와 맞는지. 안 맞으면 어디가 빠졌는지 찾아 고치세요.

규칙
- value 는 단위를 뺀 값만, 단위는 unit 에 따로 적으세요 ("275" + "ml").
- 원문 표현은 original_assertion 에 그대로 남기세요.
- "넣지 않는다" 같은 부정은 polarity 를 NEGATE 로 하세요.
- 적용 조건과 예외는 conditions / exceptions 배열에 적으세요.
- 읽히지 않는 칸은 추정하지 말고 빼세요. 무엇이 안 읽혔는지 notes 에 적으세요.
- 하단 각주·단서 조항도 사실로 포함하세요.

스키마는 아래와 같습니다. (위 표의 필드 목록을 붙여넣는다)
```

## 뽑은 뒤 — 우리가 할 일

참조는 재료일 뿐이다. 정답지로 승격하려면 순서가 있다.

1. **익명화 다리** — 참조의 원본명을 `MENU_MAP.json` 기준으로 익명 표현에 잇는다.
   이 다리가 없으면 대조 단계에서 전부 불일치로 나온다.
2. **대조** — 기존 정답지 28건과 참조를 맞춰 본다. 값이 다른 건이 있으면
   그것부터 사람이 본다. 참조가 옳다고 가정하지 않는다.
3. **사람 표본 검토** — 전수를 다 보지 않아도 된다. 표본을 정해 확인하고
   검토자·검토일·판단 이유를 남긴다 (RD-01).
4. **승격** — 검토를 통과한 것만 `truth/facts.json` 에 넣는다. 분모가 바뀌므로
   이전 실행과 나란히 놓을 수 없다. 갱신일과 새 분모를 기록한다.
5. **재측정** — 분모가 바뀐 뒤 기준선을 다시 잡는다. 옛 손실률과 비교하지 않는다.

4번에서 분모가 바뀌면 **지금까지의 모든 추출 수치가 비교 불가**가 된다.
그래도 해야 한다. 표본 정답지로 잰 값은 애초에 문서 재현율이 아니었다.

## 이 문서가 정하지 않는 것

- 제품 추출을 어떻게 고칠지. 그것은 에이전트 추출 설계의 몫이다
- 어느 모델이 더 정확한지. 참조는 상한선을 보여줄 뿐 모델 비교가 아니다
- 사람 검토의 담당·일정. RD-01 결정 사항이다
