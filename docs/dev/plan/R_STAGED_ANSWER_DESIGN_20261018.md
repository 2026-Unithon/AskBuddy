# R 단계적 응답 설계 — 일반 의미 답변을 켤 수 있게 만들기

2026-10-18 (KST). 담당 R. 기준 `main` `1cd6e33`(PR #59·#60 머지 뒤).
근거 측정: [유료 진단 기록](../review/R_LIVE_DIAGNOSTIC_20261015.md) §13.
정본 규칙: D6(폴링) · D12 · D21 · 아키텍처 불변식 5·6.

**이 문서는 설계와 결정 요청이다. 계약을 바꾸지 않았고 코드도 건드리지 않았다.**

---

## 1. 이 문서가 생긴 이유 — 지연이 아니라 가능성의 문제다

유료 진단에서 성공 턴을 실측했다. 처음에는 "느리다" 로 읽었는데, 운영 설정을 보니
**느린 게 아니라 켤 수 없는 것**이었다.

운영 상한은 설정값이 아니라 **코드가 강제**한다(`app/config.py:24-30`).

```python
chat_deadline_seconds:   float = Field(default=5.0, gt=0, le=5)   # 5초를 넘길 수 없다
search_deadline_seconds: float = Field(default=1.0, gt=0, le=1)
llm_total_budget_seconds:float = Field(default=3.0, gt=0, le=3)   # 3초를 넘길 수 없다
```

`general_decision` 에도 `asyncio.timeout(min(timeout,3.0))` 이 한 번 더 박혀 있다.
진단 러너가 이 경로를 돌리려고 **소스를 메모리에서 고쳐** 실행하고 그 증거를
`diagnostic-timeout-override.json` 에 남긴 이유가 이것이다.

실측값과 나란히 두면 결론이 분명하다.

| | 운영 상한 | 실측 |
|---|---|---|
| 제안 generate | — | 3,226 / 3,258 / 3,669 ms |
| 검증 generate | — | 8,305 / 8,778 / 12,852 ms |
| LLM 합계 | **≤ 3초** | 11.5 ~ 16.5초 |
| 턴 전체 | **≤ 5초** | 14.9 ~ 18.2초 |

**일반 의미 경로는 현재 운영 설정에서 켤 수 없다.** 지금은 꺼져 있어
(`r_general_semantics_enabled=False`) 운영이 깨진 상태는 아니다. 그러나 플래그를 켜면
해당 턴은 전부 `504 DEADLINE_EXCEEDED` 다. 3초 예산은 **제안 한 번도** 못 들어간다.

## 2. 측정이 말하는 것

- 성공 턴의 **98.8%가 두 번의 모델 호출**이다. 검색·저장·렌더는 ~200 ms
  (단, 진단은 임베딩을 합성으로 대체했다. 운영의 질의 임베딩 실호출은 여기 없다 —
  `search_deadline_seconds ≤ 1` 이 그 구간을 1초로 묶는다)
- 같은 검증 프롬프트의 generate 지연이 **8,305 / 8,778 / 12,852 ms** 로 변동 55%.
  **평균을 깎는 최적화로 닿을 거리가 아니다**
- 서버 쪽에서 깎을 것은 이미 깎았다 — `countTokens` 왕복 제거로 제안 단계 1.9초
  (PR #61). 남은 것은 전부 모델 안에 있다

## 3. 선택지

| | 내용 | 판정 |
|---|---|---|
| **A** 동기 유지 + 상한 상향 | `le=5`·`le=3` 가드를 풀고 16~20초를 기다린다 | **권고하지 않음.** 사용자가 빈 화면으로 16초를 본다. D21 p95 5초를 정면으로 버린다. 변동 55%라 새 상한을 몇으로 둘지도 못 정한다 |
| **B** 단계적 응답(폴링) | 먼저 돌려주고 나머지는 폴링 | **권고.** 제품이 이미 쓰는 모양이다(D6 폴링, 업로드 job, pending 질문) |
| **C** 스트리밍 | 모델 출력을 흘려보낸다 | **배제.** 검증 전 내용을 보여주게 된다 — D12·불변식 6 위반 |
| **D** 검증 생략·축소 | 검증 호출을 없애 절반을 아낀다 | **배제.** `verdict.supported`·`candidate_coverage` 는 제안 모델의 자기 오류를 잡는 독립 검사다. 지우면 "서버 검증" 이 제안 모델의 자기 신고가 된다 |

## 4. B 의 모양 (제안)

### 4-1. 흐름

```
POST /learn/v2/chat
  ├ 끝까지 예산 안에 들어가면          → 200 + 지금과 똑같은 ChatResponse   (변화 없음)
  └ 일반 의미 경로로 넘어가면          → 202 + {진행 중, 찾은 카드, 티켓}
                                          ↓ 폴링
GET  /learn/v2/chat/{request_id}      → 진행 상태 또는 완성된 ChatResponse
```

- **기존 경로는 그대로다.** 플래너가 승인 사실로 바로 답하는 지금 동작(대부분)은
  5초 안에 끝나고 200 을 준다. 202 는 일반 의미 경로로 넘어갈 때만이다
- **먼저 보여줄 것**: 검색이 찾은 **승인 카드 제목**. 서버는 이미 ~1초 안에 들고
  있으면서 응답에 싣지 않는다. 근거가 될 카드를 먼저 보여주는 것은 추정이 아니다
- **멱등**: `request_id` 기반 receipt 멱등이 이미 있다. 폴링 재조회는 기존 receipt
  재생과 같은 경로다 — 새 멱등 규칙을 만들지 않는다

### 4-2. 상태

```
RETRIEVED → PROPOSING → VERIFYING → (ANSWERED | CLARIFY | ESCALATE | ERROR)
```

**불변식 5 를 깨지 않는다.** `WORKING`(진행 중)은 pending 도 알림도 아니다.
`WAITING` 은 지금처럼 **ESCALATE 저장 성공 뒤에만** 쓴다. 새 상태를 넣을 때 이
구분이 흐려지면 "모른다고 넘겼다" 와 "아직 생각 중" 이 같은 화면이 된다.

### 4-3. 실패와 만료

- 모델 단계 실패는 지금과 같은 오류 코드로 티켓에 실린다(새 의미를 만들지 않는다)
- 티켓 만료 시간을 정해야 한다(제안: 모델 단계 상한과 같게). 만료는 `ERROR` 이지
  `WAITING` 이 아니다
- 직원이 화면을 닫았다 들어와도 같은 `request_id` 로 결과를 받는다

## 5. 계약 영향 — **여기서 멈춘다**

B 는 R 단독으로 못 한다.

| 바뀌는 것 | 파일 | 소유 |
|---|---|---|
| `AnswerAction` 에 진행 상태 추가(또는 별도 필드) | `app/contracts/chat.py` | **W·R 공동** |
| `POST /learn/v2/chat` 의 202 응답 | `app/learn/v2_router.py` | R |
| `GET /learn/v2/chat/{request_id}` 신설 | `app/learn/v2_router.py` | R |
| 진행 상태 저장(가산 칸 또는 새 표) | R 소유 migration | R |
| 직원 채팅 화면의 폴링·중간 표시 | `web/components/staff/*`, `web/components/r-v2-chat.tsx` | 확인 필요 |

CLAUDE.md 는 `contracts/*` 를 R 이 바꾸지 말라고 한다 — "필요하면 멈추고 사용자에게
알린다". **그래서 멈췄다.** 이 문서가 그 알림이다.

## 6. 지금 R 이 확인한 것 / 하지 않은 것

확인:
- 운영 상한이 코드로 강제된다는 것(`config.py:24-30`, `general_decision` 의 3초 캡)
- 실측 지연과 그 분해(§1·§2, 유료 13회 누적 $0.1758)
- 기존 폴링 surface 가 이미 여럿 있다는 것(`/v2/pending`, `/v2/sessions/{id}/history`,
  `/v2/notifications`) — 새 패턴을 발명하지 않아도 된다

하지 않음:
- **코드 변경 0, 계약 변경 0, migration 0, 유료 호출 0**
- 티켓 만료·폴링 주기·화면 문구는 정하지 않았다(§7 결정 뒤)

## 7. 결정 요청

| # | 결정 | 선택지 |
|---|---|---|
| 1 | 단계적 응답으로 갈 것인가 | **B 권고** / A(상한 상향) / 당분간 일반 경로를 끈 채로 둔다 |
| 2 | B 면 계약 변경을 언제 W 와 여는가 | 지금 / Phase B·C 가 끝난 뒤 |
| 3 | 진행 상태를 `AnswerAction` 에 넣을까, 별도 필드로 둘까 | 별도 필드가 기존 5행동 의미를 안 건드린다(권고) |
| 4 | 직원 채팅 화면(`r-v2-chat.tsx`·`staff/ask-screen.tsx`)의 주 편집자 | R 이면 함께, W 면 인계 |

**3번을 권고하는 이유**: `AnswerAction` 은 "AI 가 무엇을 했는가"(답함·되물음·넘김·
거절·안내)의 집합이다. "아직 하는 중" 은 그 축이 아니다. 섞으면 평가 분모
(`answer_metrics` 의 action 정확도)와 저장 계약이 같이 흔들린다.

## 8. 이 문서가 주장하지 않는 것

- p95 인수가 아니다. 측정은 진단 조건(상한을 늘린 격리 실행)의 표본 몇 건이다
- 일반 의미 경로의 품질 판정이 아니다 — 그건 사전등록 캠페인의 몫이다
- B 가 p95 5초를 만족시킨다는 주장이 아니다. **체감 지연을 다루는 것이지 실제 지연을
  줄이는 게 아니다.** 실제 지연은 모델 안에 있고, 거기는 Phase E(역할별 모델)와
  후보 수 축소가 다룰 영역이다
