# R 회의 결정 대기 및 재개 체크리스트

2026-09-18 사용자 회신을 반영했다. 아래 **RD-01과 RD-02는 명시적 대기**다. 답변이 없다는 이유로 자동 확정하거나 실행하지 않는다. 이 문서는 별도 할 일 목록이며 작업/회의가 실제 예약됐다는 뜻은 아니다.

## RD-01 — 두 매장 질문 정답 확정: 대기

사용자 결정: “일단 대기, 따로 해야할일로 정리 진행”.

- 현재: `store-a`, `store-b` 각각 40개 초안, 서로 다른 문구 37개, 사람 검토 0개. 개발 자료만 대상이며 holdout은 열지 않는다.
- 회의 결정: 매장 사실을 확인할 검토자, 실제 점주 확인인지 팀 테스트 판정인지, 검토 일정과 결과 저장 담당.
- 검토 단위: 질문 원문, 기대 행동, 필수 여부, 적용 대상/규격, 조건, 예외, 금지 주장, 판단 이유. 불확실한 조건을 빈 목록이나 승인으로 대신하지 않는다.
- 선행 자료: 각 매장 내부 `r-review/worksheet-*.md`와 선택된 `queue-*.json`, 원자료/출처. 실제 내용은 공용 회의록·Git에 복사하지 않는다.
- 진행 방식: 회의에서 지정한 방식으로 1~5개씩 확인하고 명시적으로 회신한 항목만 기록. 원자료 사실 정답을 R 질문 정답으로 자동 변환하지 않는다.
- 근거 연결: W가 준비한 **실제 승인 snapshot**에 fact revision/RAW 블록을 매핑. 검토 자체는 먼저 할 수 있지만, 매핑이 없으면 평가 준비 완료가 아니다.
- 완료 기준: 선정된 전체 문항 검토, 출처/검토자/판단 이유 기록, 승인판 참조와 선행 근거 검사, `finalize_r_dev_review.py` 통과. 매장 사실 확인과 코드 구조 검증을 구분한다.

지원 도구: `record_r_review.py --store store-a --queue <선정 queue 파일명>`으로 검토 기록을 초기화/조회한다. 실제 회신을 JSON으로 옮긴 뒤 같은 디렉터리의 `--decision <파일명> --expected-hash <현재 intake hash> --request-id <고유 키>`로 저장한다. 수정은 새 revision이며 이전 판단을 보존한다. `mapped_judgments`는 이후 기존 `finalize_review` 입력으로 연결하며 자체 승인/공개하지 않는다. 이번 작업에서 실제 검토 기록을 초기화하거나 판정하지 않았다.

## RD-02 — 유료 모델 평가: 대기, 회의 결정

사용자 결정: “이것도 대기, 따로 해야할일로 정리하고, 회의를 통해 결정”.

- 회의 결정: 총 예산 상한, provider별 최대 호출 수, 허용 입력/출력 토큰, 시간 상한, 실행 담당, 중단·재개 기준. 기존 대화에서 제시한 예산 선택지는 **승인되지 않았다**.
- 사전 고정: 검토 정답/승인 snapshot hash, 코드·프롬프트·모델·사전 버전, 비교 arm, 후보 수/cutoff, 평가 순서, 최소 반복 수, 실패 처리, 비열등/최소 개선 기준.
- 실행 규모 주의: 80문항 전체를 baseline/candidate/A-A 각 3회 실행하면 **720회 질문 실행**이다. 질문 실행당 embedding/reranker/제안 등의 호출 수가 다르므로 720회를 총 유료 호출 수로 계산하지 않는다. 예산에 맞게 사전 등록한 부분 캠페인을 사용할 수 있지만 실행 후 실패 문항을 분모에서 빼지 않는다.
- 실행 환경: 운영과 격리한 로컬 DB, 실제 평가 run ID, EVALUATION 원가 귀속, 호출 전 durable receipt. 승인된 개발 자료만 사용. mock 공급자 결과는 실측 품질로 보지 않는다.
- 산출물: 검색 누락/충분성 오판/과차단/인용 오류/잘못 합침·불필요한 분리, 행동·대화 완료, p50/p95 지연, 실패·미판정 분모, 원장 기반 비용. 결측 원가는 UNKNOWN.
- 완료 기준: 사전 등록 조건의 반복/A-A와 안전·효과·비용 게이트, 사람의 실제 출력 판정, 변경 버전에 대한 채택 결정. 비교 보고서 존재만으로 제품 활성화하지 않는다.
- 재개 절차: 회의 결정을 문서에 기록 → 비용 상한 강제 검사를 준비/확인 → 명시적 실행 지시 → 격리 실행 → 판정/보고 → 제품 적용 검토.

## 함께 준비할 의존성 — 아직 완료가 아닌 항목

| 항목 | 필요한 산출물 | 다음 작업 |
|---|---|---|
| W 승인 snapshot | 실제 승인/원장/revision/색인이 일치하는 snapshot, 매장별 내부 ID와 익명 slug 대응 | W 공개 서비스에서 내보내고 구조·현재 공개 상태를 대조 |
| W owner-answer worker | claim/heartbeat/재시도/원자 finish를 호출하는 실제 소비자 | 현재 `claim_owner_event`/`finish_owner_event`는 존재하지만 제품 호출자는 없음. 구현 담당·연결 배포 단위 확정 후 실제 producer와 인수 |
| 일반 의미 판단 제품 adapter | 평가로 채택한 해석/참조 제안과 서버 suitability·문맥·저장 검증 연결 | 현재 shadow는 평가 전용. 모델 자기평가를 승인으로 바꾸지 않고 제품 adapter 구현 및 활성화를 별도 완료해야 함 |
| 제품 종단 | 점주 1명·직원 2명, 원문 전달→검토/발행→FAQ/학습/재질문, 구/신 전환·복구 | 합성 DB 검증과 구분해 실제 W 연결 후 실행 |
| 운영 로그 | 호스팅 일반 로그 원문 중복 OFF, 30일 metadata 보존, 조회 권한 | 저장소 구현 외에 실제 배포 서비스의 설정 증거 확인 |

이 의존성 표는 사용자에게서 새로 승인받은 결정 목록이 아니다. 준비해야 할 산출물과 미완료 구현을 드러낸다. **RD-01/RD-02를 대기시켰다고 나머지 R 전체가 완료된 것은 아니다.**
