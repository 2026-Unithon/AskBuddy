# Phase B — 입구 라우터 · 자료 분류기 · 정규화기 · 체크리스트 카드 단위 (설계)

작성: 2026-10-10 (KST). 담당: W. 선행: **Phase A**(`W_PHASE_A_FACT_ONLY_DESIGN_20261010.md`, 레거시 RAW 제거·사실→카드 단일 경로).
결정 출처: 2026-10-10 사용자 대화.

## 1. 목표

사실 추출 로직은 자료의 **용도**마다 완전히 달라진다. 그래서 자료가 들어오는 **입구에서, 본 추출 전에** 어떤 로직으로 보낼지 정한다.
분류에 쓰는 훑기는 싸고 빠르게 하고, 무거운 처리(전체 STT·고해상도 렌더링·촘촘한 프레임)는 **로직이 정해진 뒤 한 번만** 한다.

```
[입구]              [정규화기 ① 가벼운 훑기]   [분류 1회]           [정규화기 ② 본 추출]      [로직 추출기]   [공통 — Phase A]
업로드 완료   ─┐
               ├→  probe(): 고른 표본       → 구간별 로직 판정 → full(로직): 필요한 깊이로 → 사실 추출  → 원장 → 조립 → 카드
점주 답변 완료 ─┘   (싸게, 결과는 캐시)        (NONE 이면 끝)      (훑기 결과 재사용)
```

이번 범위: **라우터 틀 + 정규화기 2단계 + 새 확장자(avi·docx·hwp) + 분류기 + 분류기 테스트 + 지금 추출기 등록 + 외부 모델 관찰 템플릿 + 체크리스트 카드 단위.**
로직별 전용 추출기는 관찰 템플릿으로 근거를 모은 뒤 나중에 등록표에 한 줄씩 더한다.

## 4. 두 축

### 4-1. 로직(용도) — 라우터가 정한다

| 로직 | 무엇 | 사실의 모양 | 카드 | 예 |
|---|---|---|---|---|
| `RECIPE` 레시피 | 메뉴 제조 | 규격(HOT/ICE·사이즈)별 수량·단위, 순서 | 수치 + 순서 | 아메리카노 ICE 샷 2, 물 225ml |
| `PROCEDURE` 업무 절차 | 오픈·마감·청소·기기 사용·발주 | 순서, 선행 단계, 조건 | 순서(체크리스트에 연결될 만한 카드) | 매장청소: 의자 올리기 → 락스물 희석 → … |
| `POLICY` 운영 규칙·응대 | 환불·할인·응대·금지 | 조건·예외·부정 | 목록 | 영수증 없으면 환불 불가, 단 당일은 가능 |
| `REFERENCE` 매장 정보 | 보관 위치·비품·연락처·기기 정보 | 대상-속성-값 | 수치·목록 | 바닐라향 시럽: 창고 2번 선반 |
| `NOTICE` 공지·일정 | 이번 주 공지·행사·근무 변경 | 기간이 있는 정보 | **카드로 만들지 않고 검수 대기**(기한 있는 지식은 별도 설계) | 이번 주 토요일 휴무 |
| `NONE` 무관 | 잡담·셀카·영수증 | 추출 안 함 | `NO_RESULT` | |

### 4-2. 정규화기(형식) — 확장자로 정해진다

| 정규화기 | 확장자 | 공통 중간 형식의 구간 |
|---|---|---|
| `DOC_TEXT` 문서(글자) | pdf(글자 층 있음), **docx**, **hwp(hwpx 포함)**, txt(카톡 아님) | 쪽·문단, 글자(+표는 행 구조) |
| `DOC_IMAGE` 문서(이미지) | pdf(스캔), jpg·jpeg·png | 쪽·이미지, (+필요 시 글자 인식) |
| `AUDIO` 음성 | mp3·m4a·wav | 시간 구간, 전사 글 |
| `VIDEO` 영상 | mp4·mov·**avi** | 시간 구간, 전사 글 + 프레임 |
| `CHAT` 대화 | 카톡 내보내기 txt·캡처 이미지 | 날짜·화자 구간, 줄 |
| `OWNER_TEXT` 점주 답변 글 | (파일 없음) | 질문 맥락 + 답변 글 한 구간 |

점주 답변의 **첨부 파일**은 확장자대로 위 정규화기를 탄다(B-D1). 점주 답변 하나 = 답변 글(`OWNER_TEXT`) + 첨부 각각의 IR 을 **한 묶음**으로 분류·추출한다.

- **공통 중간 형식(IR):** `IntakeSegment { segment_id, locator(PAGE|TIME|DATE|LINE|WHOLE, 범위), text, images[], table_rows[]? }` 의 목록. 로직 추출기와 분류기는 **파일이 아니라 IR 만** 본다.
- 확장자 추가 = 4-2 표에 한 줄(`capabilities.py` 가 정본). 정규화기 추가는 형식이 정말 다를 때만.
- 같은 확장자가 두 정규화기에 걸리면(pdf: 글자/스캔, txt: 문서/카톡, jpg: 문서/카톡 캡처) 업로드 입력 종류(지금의 VOICE·VIDEO·KAKAO·SCAN 선택)와 파일 검사(pdf 글자 층 유무)로 코드가 가른다. 모델 호출 없음.

### 4-3. 사실 형식 — 공통 핵심 + 로직별 확장 (B-U14)
로직마다 뽑을 것이 다르지만, **원장·조립·R 인용은 하나의 사실 형식만** 다룬다(Phase A). 그래서 형식을 셋으로 나눈다.

1. **공통 핵심(모든 로직 동일, 바꾸지 않음):** `subject`·`variant`·`attribute`·`value`·`unit`·`polarity`·`conditions`·`exceptions`·`step_order`·`requires`·`original_assertion`·`locator`·`confidence`. 지금 원장(`source_facts`)·사실 판·카드 렌더링·공개 계약이 이 칸만 쓴다.
   - 예전 지시문의 `page` 는 `locator {kind: PAGE|TIME|DATE|LINE|WHOLE, value}` 로 넓힌다(영상은 시간, 카톡은 날짜·줄).
2. **로직별 속성 사전:** `attribute` 이름 목록이 로직마다 다르다. 같은 이름을 일관되게 쓰게 한다(예전 레시피 목록이 `RECIPE` 사전의 시작).

   | 로직 | 속성 사전 시작값 |
   |---|---|
   | `RECIPE` | 판매가·제조순서·컵·샷 수·얼음·재료·토핑·분류·스팀우유량·온수량·우유량·물량·사이다량·콜라량·베이스량·원액량·블렌더 회전수·우리는 시간·1펌프 용량 |
   | `PROCEDURE` | 절차 단계·도구·소요 시간·주기·시점(오픈/마감/교대)·담당·완료 기준·주의 |
   | `POLICY` | 허용·금지·대상·한도·처리 방법·안내 문구·근거 |
   | `REFERENCE` | 위치·수량·연락처·규격·사용법·관리 주기 |
   | `NOTICE` | 내용·대상·시작·끝 |

3. **로직별 확장 칸 `ext`(선택, 로직마다 스키마):** 공통 핵심에 없는데 그 로직에 꼭 필요한 것만. 원장에는 `ext` JSON 으로 보존하고, 카드 렌더링·R 은 지금 쓰지 않는다(쓰게 되면 그때 계약 검토).

   | 로직 | `ext` |
   |---|---|
   | `PROCEDURE` | `timing`(OPEN·CLOSE·SHIFT_CHANGE·ANYTIME), `frequency`(매일·주 1회 등 원문) |
   | `POLICY` | `scope`(고객·직원·전체) |
   | `REFERENCE` | `location_path`(구역 > 선반 등 원문) |
   | `NOTICE` | `valid_from`·`valid_until`(날짜, 모르면 null) |
   | `RECIPE` | 없음 |

- 이렇게 하면 로직이 달라도 **원장·조립·인용 경로는 하나**이고, 다수결 참조·비교 도구도 공통 핵심 키로 돈다. 로직별 차이는 사전과 `ext`, 지시문의 규칙에만 있다.
- `ext` 저장을 위해 `source_facts`(와 사실 판 메타)에 nullable `ext jsonb` 를 더한다(가산 migration). 사실 판 hash·공개 계약에는 넣지 않는다.

## 5. 설계

### B-D1 입구와 순서
- **업로드 완료:** 작업 처리(`process_source`)에서 정규화기 `probe()` → 분류 → `full(로직)` → 로직 추출기 → Phase A 의 원장·조립.
- **점주 답변 완료 (B-U15):** 답변 = 글 + 첨부 파일.
  - **첨부 연결은 W 안에서 닫는다(R 계약 변경 없음):** 점주가 답변 화면에서 파일을 고르면 web 이 기존 서명 URL 업로드(`POST /ingest/upload-url`)로 올리고, W 새 API 가 그 자료를 **대기 질문 id** 에 묶는다(표 `owner_answer_attachments(store_id, pending_question_id, source_id)`, 가산 migration). 답변 제출은 지금처럼 R API.
  - W worker 가 `OWNER_ANSWER_SUBMITTED` 를 받으면 그 질문의 첨부를 찾아, 답변 글(`OWNER_TEXT`) + 첨부들을 **한 묶음**으로 훑기 → 분류 1회 → 구간별 로직 → 본 추출 → 원장·조립. 질문 문장은 맥락으로 들어간다.
  - 첨부 업로드가 제출보다 늦게 끝나는 경우: 제출 시점에 `UPLOADED` 가 아닌 첨부는 기다리지 않고 **뒤따르는 보충 처리**로 같은 답변에 붙인다(같은 대상이면 Phase A-D4 새 초안). 화면은 업로드가 끝나야 제출 버튼을 켠다(1차 방어).
  - 답변 화면 web 파일의 주 편집자 확인이 필요하다(R 화면이면 R 인계로 첨부 UI 요청). 계획 단계에서 확인.
- W3b 의 점주 텍스트 사실 추가(`POST …/facts/parse`)는 구조화 편집이라 라우터를 타지 않는다.

### B-D2 정규화기 두 단계 (B-U9·B-U10)
각 정규화기는 두 함수를 가진다. 상한·간격은 `config.py`(시작값, 분류기 테스트로 조정).

| 정규화기 | ① `probe()` — 분류용, 싸게 | ② `full(로직)` — 로직에 맞는 깊이 |
|---|---|---|
| `DOC_TEXT` | 글자 추출(무료) 후 처음·중간·끝 + 고른 간격 쪽/문단 앞부분, 위치 표시, ≤ 3,000자 | 전체 글자 + 표 행 구조. 이미지가 박힌 쪽은 렌더링 추가 |
| `DOC_IMAGE` | 고른 간격 최대 6쪽, 긴 변 512px | 전체 쪽 고해상도(기존 SCAN 경로·LAYOUT 모드) |
| `AUDIO` | 처음·중간·끝 + 고른 간격 20초 구간만 STT | 전체 STT(이미 전사한 구간은 재사용) |
| `VIDEO` | 고른 간격 키프레임 4~6장(512px) + 처음·중간·끝 20초 STT | 전체 STT + 프레임(지금 영상 전처리). 로직별 깊이(예: RECIPE·PROCEDURE 는 단계 전환 지점 촘촘한 프레임)는 등록표 설정 |
| `CHAT` | 날짜 구간별 고른 표본, ≤ 3,000자 | 전체 파싱 |
| `OWNER_TEXT` | 질문 + 답변 전체 | 같은 글 |

- **훑기 결과는 캐시해 본 추출에서 재사용**한다(같은 STT 구간·같은 프레임을 다시 만들지 않음).
- **`NONE` 이면 `full()` 을 부르지 않는다**(무관 자료의 본 추출 비용 0).
- **이번에 실제로 만드는 것:** 지금 전처리 4종을 `probe`/`full` 로 나누고, `full` 은 지금 전처리 그대로(로직별 깊이 차이 없음). 새 확장자:
  - `avi` → `VIDEO`(ffmpeg 가 디코딩).
  - `docx` → `DOC_TEXT`(docx 는 zip+XML, 문단·표 추출). 라이브러리(`python-docx`) 추가 또는 표준 라이브러리 XML 파싱 중 계획 단계에서 고른다.
  - `hwp` → `DOC_TEXT`. **hwpx**(zip+XML)는 XML 파싱. **hwp 5.0 이진 형식**은 OLE 구조라 별도 파서가 필요하다(`pyhwp` 계열 또는 `olefile`+본문 압축 해제). 계획 단계에서 라이선스·컨테이너 크기·추출 품질을 보고 고른다. 이미지·수식은 처음엔 건너뛰고 기록한다.
  - 한계·상한(쪽 수·바이트)은 `capabilities.py` 에 추가하고 업로드 화면은 capabilities 를 그대로 따른다.

### B-D3 분류 호출
- 자료당 **1회**. 가장 싼 경량 모델(`config.py` `intake_classifier_model`), 온도 0, JSON 출력. 프롬프트 `api/prompts/classify_intake.ko.txt`.
- 입력은 `probe()` 의 IR 표본(글자 + 작은 이미지, 위치 표시). 출력(구간별):
```json
{"sections": [
  {"range": {"kind": "PAGE|TIME|DATE|LINE|WHOLE", "start": "...", "end": "..."},
   "ranking": [{"logic": "RECIPE", "score": 0.72}, {"logic": "PROCEDURE", "score": 0.21}],
   "reason": "짧은 근거"}]}
```
- **구간("부분 부분")**: 한 자료에 레시피와 마감 절차가 섞이면 구간별로 다른 로직. 표본에 없는 구간은 가장 가까운 표본 구간의 판정을 따른다.
- 원가·지연: 원장 단계 `ROUTE`. 추정(실측 전): 텍스트 1회 약 0.3~0.5원, 이미지 6장 1~2원, 1~2초. 영상·음성은 훑기 STT 약 1분(whisper 단가)이 더해진다.

### B-D3a 점주 선택 칩 (B-U16)
- 화면: 업로드 입력창("새로 알려줄 것 넣기")의 찍기·파일 옆에 "이건 어떤 자료인가요? (선택, 여러 개 가능)" 칩: **레시피 · 업무 순서 · 매장 규칙 · 매장 정보 · 공지**(각각 `RECIPE`·`PROCEDURE`·`POLICY`·`REFERENCE`·`NOTICE`). 안 골라도 넣을 수 있다. 점주 답변 첨부에도 같은 칩.
- 저장: 자료에 `owner_hints text[]`(가산 칸, 허용값은 로직 이름). 업로드 API 요청에 선택 칸으로 받는다.
- 분류 반영 두 겹:
  1. **프롬프트에 알림**: "점주가 고른 종류: …. 참고하되 내용이 다르면 내용을 따르라."
  2. **점수 가산**: 점주가 고른 로직의 점수에 `intake_owner_hint_boost`(`config.py`, 시작값 0.15)를 더한 뒤 B-D4 규칙을 적용. 모델이 애매할 때(1·2위 근소)는 점주 선택이 이기고, 모델이 확실히 다른 쪽이면 내용이 이긴다.
- 기록(B-D6): 점주 선택, 모델 원래 순위, 가산 뒤 순위, 최종 결정, `hint_changed_decision`(점주 선택 때문에 결정이 바뀌었는가). 가산값 조정은 이 기록과 분류기 평가로 한다.
- 분류 호출 수는 그대로 1회(정확도를 높이는 장치이지 호출을 줄이는 장치가 아님).

### B-D3b 통합 자료 — 구간 나누기와 병렬 추출 (B-U17)
```
자료 → ① 경계 후보(코드, 무료) → ② 분류 1회: 후보 구간마다 로직 → ③ 이웃한 같은 로직 합치기·같은 로직끼리 묶기
     → ④ 로직별 추출기 병렬 → ⑤ 원장이 중복 정리
```
1. **경계 후보는 코드가 먼저 만든다**(표본만 보고 모델이 경계를 정하면 놓친다):
   - `DOC_TEXT`: 쪽 나눔·제목(docx·hwp 문단 스타일, pdf 글자 크기·굵기)·표 시작/끝
   - `DOC_IMAGE`: 쪽(쪽 안 구역 나누기는 기존 LAYOUT 경로)
   - `AUDIO`·`VIDEO`: 일정 길이 창(설정) + 말 끊김 지점
   - `CHAT`: 날짜
   - 분류 입력은 후보 구간마다 표본을 붙여 보낸다. 분류기는 후보마다 로직 순위를 낸다(B-D3 출력의 `sections` = 후보 구간).
2. **한 구간 두 로직**(예: 레시피 표 아래 환불 각주): 2위 점수가 `intake_multi_label_min`(시작값 0.35) 이상이면 두 추출기 모두에 보낸다. 두 배 비용은 그 구간만.
3. **잘린 맥락 붙이기**: 구간마다 문서 제목, 그 구간의 상위 제목, 앞 구간 끝부분(설정 글자 수)을 **맥락**으로 함께 준다. 맥락은 사실로 저장하지 않는다.
4. **경계 중복**: 경계에 걸친 내용이 두 추출기에서 같은 사실로 나오면 원장의 같은 사실 판정(대상·규격·속성 identity)으로 하나가 된다(Phase A·W2 그대로).
5. **너무 잘게 쪼개지 않는다**: 구간 수 상한 `intake_max_sections`(설정), 작은 구간(설정 글자 수·초 미만)은 이웃과 합친다.
6. **병렬**: 로직별 묶음을 W3a 의 `gather_in_order` + 전역 모델 게이트(`ingest_model_concurrency`)로 동시에 실행, 결과는 구간 순서로 합친다.
- 예: 통합 매뉴얼(오픈 절차 3쪽 + 레시피 표 5쪽 + 환불 규칙 1쪽 + 이번 달 공지 1쪽) → 분류 1회 → `PROCEDURE`·`RECIPE`·`POLICY` 추출기 병렬 각 1회 + `NOTICE` 구간은 공지 초안(Phase C).

### B-D4 결정 규칙 (B-U3)
- 각 구간은 `ranking` 1위 로직으로 간다. **애매해도(점수 낮음·1·2위 근소) 1위 = 가장 가까운 로직.** 기본 로직으로 떨어뜨리지 않는다.
- 1위 로직에 **등록된 추출기가 없으면** `ranking` 에서 **등록된 로직 중 가장 높은 것**(가장 가까운 등록 로직).
- `NOTICE` → 사실을 추출하되 카드로 조립하지 않고 검수 대기(사유 `INTAKE_NOTICE`). **Phase C 가 이것을 공지사항 초안(`store_notices`)으로 바꾼다**(`W_PHASE_C_NOTICE_KNOWLEDGE_TAB_DESIGN_20261010.md`). 공지 자료 안의 지식 변경 구간은 구간 라우팅으로 RECIPE·POLICY 등 카드 쪽으로 간다. `NONE` → `full()`·추출 안 함(`NO_RESULT`).
- 분류 호출 실패(모델 오류·JSON 깨짐): 기존 재시도 정책. 끝내 실패하면 작업 실패(재시도 가능). 조용히 다른 로직으로 가지 않는다(CLAUDE.md "실패하면 멈춘다").

### B-D8 외부 모델 관찰 템플릿 (B-U12)
로직별 전용 추출기를 만들기 전에, 강한 외부 모델이 그 종류의 자료를 **어떻게** 처리하는지 여러 번 관찰하고 공통 전략을 뽑는 절차를 재사용 가능하게 남긴다. 예전 레시피 관찰(G8)을 일반화한다.

산출물 `docs/dev/templates/extraction_observation/`:
1. **지시문 = 공통 본문 + 로직 부록 + 형식 부록 조립 (B-U13).** 예전 지시문(레시피·PDF/PNG 한정, 2026-10 사용자 제공)을 공통 본문의 기준으로 삼고, 로직·형식에 따라 달라지는 부분만 부록으로 뺀다. 확장자 × 로직 곱으로 지시문을 만들지 않는다.
   - **`INSTRUCTION_CORE.md` 공통 본문** — 예전 지시문의 뼈대 그대로:
     - 머리말("신입 직원이 업무를 하는 데 필요한 사실을 빠짐없이, 방법은 자유, 실제로 한 것을 기록")
     - **1부 작업 기록**(실제로 한 것만): 단계 번호 · 한 일 · 도구·코드 실행 여부 · 사용 도구와 코드 원문 · 왜 필요했나 · 바뀐 것. "한 일" 예시는 형식 부록이 채운다
     - **2부 추출 결과 JSON**: `meta` + `results`. `results` 칸은 4-3 공통 핵심(`page` → `locator`) + `confidence` + `must_have` + 로직 `ext`. `meta` 는 모델·파일·`pages_or_images` 대신 형식 부록이 정하는 **분량 칸**(쪽 수/길이/메시지 수)·`method_summary`·`self_check`·`unreadable`·`new_attributes`
     - 공통 규칙: 추정 금지(못 읽은 건 빼고 `unreadable`), 사실 하나에 값 하나, 규격별 값은 `variant` 로 나누고 범위로 합치지 않기, 환산값 처리, 각주·단서·주의사항 포함, 속성은 사전 이름 우선·새 속성은 `new_attributes`
     - **3부 자기 점검**: 공통 2문항(확대·재확인 후 바뀐 값 전부, 가장 놓쳤을 곳과 이유) + 로직·형식 부록 문항. 점수 매기지 않기
     - 돌릴 때 함께 적을 것(서비스·모델·모드, 파일명, 걸린 시간, 화면에 보인 도구 실행)
   - **`logic/<LOGIC>.md` 로직 부록 5개**(`RECIPE`·`PROCEDURE`·`POLICY`·`REFERENCE`·`NOTICE`): 무엇을 사실로 보나, 4-3 속성 사전, `ext` 칸 설명, 로직 규칙, 로직 자기 점검 문항.
     - `RECIPE`: 예전 규칙 그대로(메뉴×규격 행, 괄호 환산, 블렌더·펌프 등). 점검 "표·목록 행 수와 뽑은 행 수", "같은 표의 모든 행이 같은 속성 집합"
     - `PROCEDURE`: 단계 순서·선행·분기(조건별 다른 단계)·반복·완료 기준을 각각 사실로, 한 단계에 동작이 여럿이면 나누기. 점검 "단계 번호 연속·빠진 단계", "선행 관계가 순서와 맞는가"
     - `POLICY`: 허용/금지를 `polarity` 로, 예외·한도·대상을 빠짐없이. 점검 "금지 문장 중 부정으로 안 적힌 것", "예외가 붙은 규칙"
     - `REFERENCE`: 대상-속성-값, 위치는 원문 경로 그대로. 점검 "같은 대상이 다른 값으로 두 번 나오는 곳"
     - `NOTICE`: 기간·대상, 날짜는 원문 그대로 + 해석한 날짜, 모르면 null. 점검 "기간이 없는 공지"
   - **`format/<NORMALIZER>.md` 형식 부록 6개**: 그 형식에서 쓸 법한 "한 일" 예시, `locator` 쓰는 법, `meta` 분량 칸, 형식 자기 점검 문항.
     - `DOC_TEXT`(pdf 글자·docx·hwp): 글자 층·문서 구조 추출, 표 행 전사 / `PAGE`·문단 / "문서의 표 행 수와 뽑은 행 수"
     - `DOC_IMAGE`(스캔 pdf·사진): 쪽 이미지 변환, 영역 잘라 확대, OCR / `PAGE` / "작은 글씨 칸을 확대해 확인했는가"
     - `AUDIO`: 전사, 구간 반복 청취 / `TIME` 시작~끝 초 / "들리지 않은 구간과 시간"
     - `VIDEO`: 전사 + 프레임 추출, 화면 속 글자·동작 확인 / `TIME` / "말과 화면이 다른 곳", "화면에만 나온 수치"
     - `CHAT`: 날짜·화자 구분, 정정 메시지 추적 / `DATE`+`LINE` / "나중 메시지가 앞의 값을 바꾼 곳"
     - `OWNER_TEXT`(+첨부): 질문 맥락과 답변 구분 / `WHOLE` 또는 첨부의 형식 / "질문에 답한 사실과 덧붙인 사실 구분"
   - 조립 결과 예: `RECIPE × DOC_IMAGE` = 예전 지시문과 사실상 같다(회귀 기준). 조립 스크립트 `api/scripts/build_observation_instruction.py <LOGIC> <NORMALIZER>` 가 공통 본문 + 두 부록을 이어 붙여 한 파일로 낸다.
2. **`RUN_SHEET.md` — 실행 기록부.** 실행 id(익명), 로직·형식, 앱·모델·추론 설정, 입력 형태(원본/이미지 변환/확대 여부), 소요 시간, 결과 건수, 저장 경로(Git 제외 `추출결과/<로직>/<자료>/<실행 id>/`).
3. **`ANALYSIS.md` — 전략 비교 양식.** 실행별 작업 기록을 단계 단위로 맞춰 표로: 공통 단계(과반 실행이 한 것), 갈린 단계와 결과 차이, 값이 수렴한 조건(예: 확대 배율·띠 단위), 결과 건수·참조 대비 재현. 결론 = **"평균적인 처리 순서" → 우리 추출기의 단계·코드 검사·모델 역할 분담 초안**.
4. **다수결 참조 일반화:** `build_consensus_reference.py` 의 레시피 전용 부분(실행 이름·우선순위 하드코딩, 칸 키)을 로직별 키 함수와 실행 목록 파일(`RUN_SHEET` 에서 읽음)로 분리한다. 기존 레시피 참조 결과는 바뀌지 않게(같은 입력 → 같은 출력 회귀 테스트).
- 이 절차로 얻은 결론은 로직별 추출기 설계 문서의 근거로 쓰고, 참조는 정답지가 아니다(`W_REFERENCE_EXTRACTION_20260920.md` 역할 한계 그대로).
- 외부 앱 실행 자체는 사용자가 한다(앱 사용료는 사용자 기록).

### B-D9 체크리스트 = 카드 단위 (B-U7)
- 오늘 항목: 근무조 연결로 정해진 카드마다 **한 줄**, 문구 = 공개 판 제목. 체크 키는 기존 표 그대로 `(card_version_id, line_no=1)` — migration 없음.
- "N개 남았어요" = 남은 카드 수. 제출 `total_lines`·`done_lines` 는 카드 수(열 이름 그대로).
- 항목 제목을 누르면 직원 카드 상세로 이동, 체크박스는 체크만.
- 기록 달력·점주 현황의 "줄" 표시도 카드 제목으로(`split_lines` 사용처 교체).
- 같은 영업일에 카드가 재공개되면 판 단위 키라 체크가 풀린다 — 유지할지 계획 단계에서 사용자 확인.

### B-D10 기타
- 업로드 화면 문구(G5)는 그대로(분류기가 실제로 나눈다). 지원 확장자 안내는 capabilities 를 따른다.
- 작업 상태 `CLASSIFYING` 은 이제 실제 분류 단계 이름이 된다(상태값 그대로).

## 6. 검증
- 단위 B-D7 + 체크리스트 카드 단위(항목 수·제출 수·제목 표시·누르면 이동) + 다수결 참조 회귀.
- 실제 DB: 업로드(형식별 대표) → 훑기 → 분류(합성 대역) → 구간별 로직 → 본 추출 → 사실·카드(`ext` 보존), `intake_route_decisions` 행·원장 `ROUTE` 행, `NONE` 에서 본 추출 없음; 점주 답변(글만 / 글 + 첨부 / 늦게 끝난 첨부 보충) 같은 흐름; 분류 실패 시 작업 실패.
- 관찰 템플릿: 조립 스크립트가 `RECIPE × DOC_IMAGE` 에서 예전 지시문과 같은 규칙을 내는지 대조, 로직·형식 부록 11개 존재.
- web: `pnpm check`, 저장소 스킬 2개, 합성 API Playwright(오늘 할 일 카드 단위·항목 눌러 카드 열기, 업로드 화면 새 확장자).
- 격리 검사. 실제 모델 정확도 평가·외부 앱 관찰은 사용자 승인·실행.

## 7. 범위 밖
- 에이전트 완전 위임(서버 에이전트 세션에 자료를 통째로 맡기기) — 기본 경로로 쓰지 않는다. 굳히기 어려운 드문 형식의 보험으로만 고려(로드맵 §2-1).
- 역할별 모델 전환(API 오류 시 넘기기·비용 효율 비교) — **Phase E**(로드맵 §2-1).
로직별 전용 추출기(PROCEDURE·POLICY·REFERENCE)와 로직별 `full()` 깊이, NOTICE 의 기한 있는 지식, 비카드 결과물(할 일 목록), 체크리스트 연결 제안, 분류 결과 화면, hwp 안의 이미지·수식.

## 8. 위험
| 위험 | 대응 |
|---|---|
| 표본이 자료를 대표하지 못해 오분류 | 고른 간격 표본 + 구간 판정, 평가 하네스로 측정, 상한은 설정값 |
| 분류 호출이 실패하면 업로드가 막힌다 | 기존 재시도, 끝내 실패는 명확한 작업 실패(재시도 가능) |
| 미등록 로직이 모두 `RECIPE` 로 가 지금과 품질이 같다 | 의도(B-U6). 분류 기록 + 관찰 템플릿으로 전용 추출기 우선순위·설계를 정한다 |
| hwp 5.0 이진 파서의 품질·라이선스 | 계획 단계 비교, 실패 시 명확한 `FAILED`(지원 안 되는 hwp) — 추정 추출 금지 |
| 훑기 캐시가 본 추출과 어긋남 | 같은 구간 id·같은 설정일 때만 재사용, 단위 테스트 |
| 체크 키가 판 단위라 같은 날 재공개 시 체크가 풀림 | 계획 단계에서 사용자 확인 |
| 점주가 칩을 잘못 눌러 엉뚱한 추출기로 감 | 가산값은 근소한 경우만 뒤집게 작게 시작, `hint_changed_decision` 기록으로 조정 |
| 경계 후보가 실제 주제 경계와 어긋남 | 구간 맥락 붙이기 + 원장 중복 정리, 평가 하네스에 섞인 자료(구간 정답) 포함 |
| 점주 답변 화면이 R 소유면 첨부 UI 를 W 가 못 고침 | 계획 단계에서 주 편집자 확인, R 이면 인계로 요청(W API 는 먼저 준비) |
| `ext` 가 커지며 사실상 로직별 스키마가 갈라짐 | `ext` 는 로직별 스키마로 검증, 공통 핵심에 넣을지는 R 계약 검토 뒤 |
