# C0 pull·결정·구현 계획 검토

> 검토일: 2026-09-14. 대상: `8b8e447..65c2403`와 [C0 결정·계획](../C0_DECISIONS_AND_PLAN.md). 후속 사용자 원가 회신과 계측 우선순위 재검토를 §7에 반영했다.
> 이번 검토는 현재 담당 에이전트의 코드 대조·순수 반례 재현·설계 재검토다. 다른 개발자의 독립 승인이나 운영 보안 인증을 의미하지 않는다.

## 1. 결과와 범위

pull로 추가된 계약 타입과 D18~D21은 유지한다. C0-1의 `schema 완료`, C0-4의 `확정됨`은 각각 **타입 기반 존재**, **핵심 제품 수치 결정**으로 범위를 바로잡았다. 실제 계약 보강·공유 fixture·DB/API 접점·월 원가 입력이 남아 있다.

- 기존 `tests.test_contracts`: 22개 통과.
- 추가 offline probe: 정상/거절 대조군 3개 PASS, 목표 계약 대비 GAP 16개, 실행 ERROR 0개.
- GAP는 계약 미구현/표현 불가/검증 부족의 관측이며 운영 공격이 성공했다는 뜻은 아니다. runtime이 아직 이 타입을 소비하지 않는 상태를 함께 확인했다.
- DB·서버·유료 AI API·실자료·holdout을 호출하지 않았다. pull 커밋의 `147 passed`는 과거 작성자 기록이며 이번 22개 재실행과 구분한다.
- 이번 변경은 결정서·정본 동기화·재현 도구다. 발견한 애플리케이션 코드와 DB 결함을 수정 완료로 표시하지 않는다.

## 2. 재현 방법

`api`에서 저장소의 Python 환경으로 실행한다.

```text
python -B -m unittest tests.test_contracts -q
python -B scripts/audit_c0_contracts.py
```

이번에는 로컬 bundled Python을 사용했다. [재현 스크립트](../../../api/scripts/audit_c0_contracts.py)는 합성 데이터만 메모리에서 만들고 JSON으로 결과를 출력한다. exit 1은 발견된 GAP, exit 2는 재현 도구 오류다. 따라서 현재 exit 1을 정상 제품 CI 통과로 집계하지 않는다. CP-01에서 이 사례를 서비스·schema별 목표 불변식 테스트로 전환한다.

## 4. 계획 재검토에서 수정한 사항

### 4.1 동시 개발과 소유권

W는 공개 포인터/공통 renderer, R은 index 준비·chat·인용을 소유하게 했다. 공유 config/manifest는 W, main/deps/Web 공통 경로는 R을 초기 편집자로 지정했다. 계약 PR에서 주 편집자를 한 명씩 기록하며 다른 쪽의 직접 동시 수정은 피한다.

후속 회신에 따라 CP-00A~C 원가 계측을 선행하고 CP-01 오류 보강·R 보안은 병행한다. 그 뒤 CP-02~03 fixture로 독립 개발하고 CP-04 DB·CP-05 품질 하네스로 연결한다. W 전체 완료를 기다리는 직렬 의존성은 만들지 않았다. 실제 W 승인 snapshot의 종단 승격은 J1로 유지했다.

### 4.2 불변 snapshot과 current 상태

준비 단계에서 최종 revision/hash를 먼저 확정하면 CAS에서 다른 공개와 경합할 수 있다. 준비 content hash와 최종 snapshot hash를 구분하고, commit 시 publication row 아래서 revision을 발급한다. 답변 저장도 같은 잠금 규칙을 따라 검사와 저장 사이 경합을 닫는다.

source 삭제 상태를 과거 snapshot에 덮어쓰면 불변 hash가 깨진다. immutable provenance와 현재 source availability overlay를 분리했다. D20에 따라 승인 사실/카드는 남고 UI는 원본 링크 상태를 보여준다. source 삭제와 카드 제외를 혼동하지 않는다.

### 4.3 RAW·규격·원문

RAW를 fact-only 모델에 억지로 맞추면 역추출 fact에 승인 상속이 발생할 수 있다. 승인 원문 span 참조를 별도 표현으로 지정했다. 같은 메뉴 여러 규격 카드와 특정 규격 fact 선택을 동시에 지원하고 조건/선행 참조가 따라가도록 했다.

일괄 문자열 trim은 점주 원문 보존과 충돌하므로 원문과 정규화 필드를 분리한다. Pydantic frozen만으로 list까지 불변이 되지 않으므로 nested tuple/불변 구조 및 DB version 규칙을 함께 요구했다.

### 4.4 질문 상태와 전달

기존 서버 chat_session을 context 소유권에 사용해 새 로그인 session 체계를 불필요하게 도입하지 않는다. context TTL 10분/CLARIFY 2턴, 요청 멱등성과 의미 pending 중복을 분리했다. 모호한 서로 다른 직원 질문을 한 pending으로 합치지 않게 한다.

직원 원문 전달 상태와 W 지식화 상태는 별개다. 요청/알림/outbox의 durable commit을 성공 단위로 하고 Push 실패는 업무 저장을 취소하지 않는다. outbox에 원문을 중복 저장하지 않고 필요한 ID로 내부 조회한다.

### 4.5 예산과 승격

D18을 유지하며 median 순증·A/A 폭·최소 5건·총비용 관측을 구체화했다. A/A 폭이나 2/3 방향을 통계적 보장으로 취급하지 않는다. 질문 수/원본 truth를 섞지 않고 W 누락을 올바른 ESCALATE 성과로 숨기지 않는다.

D21 5초를 단계마다 새로 주는 오류를 막기 위해 전체 deadline을 공유한다. timeout으로 답변을 포기해 p95만 낮추지 못하도록 오류율·완전답변·coverage를 함께 검사한다. 최초 검토의 U1/U2 질문은 후속 회신으로 운영 변동비 범위 확정·시나리오/관측 방식 결정으로 해결했다. 실제 비용 계측과 운영 원가 판정은 아직 수행하지 않았다.

## 7. 사용자 원가 회신 이후 재검토

원가 범위와 미래 사용량 처리 방향을 [원가 계측 계획](../plan/C0_COST_MEASUREMENT_PLAN.md)에 반영했다. 이번 후속은 계획/입력 fixture 작성과 코드 읽기 검토이며 기존 22개 unit·16개 GAP를 새로 재실행한 결과는 아니다.

### 후속 개정 검증 결과
