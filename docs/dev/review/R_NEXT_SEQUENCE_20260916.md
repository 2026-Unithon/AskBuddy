# R 후속 순서 구현: 재시도·평가·문맥·조건·RAW·FAQ

2026-09-16. `R_REMAINING_AUDIT_20260916.md` 권장 순서의 구현 후속이다. 기존 작업 트리를 보존했다. Docker, 외부 모델 호출, W 코드 수정, 운영 배포, commit/push는 실행하지 않았다.

## 1. 점주 답변 인계 재시도

`learn/owner_handoff.py`:

- 자동 시도 최대 10회. 실패 후 2/4/8/16/32/60초(이후 60초) backoff. 10번째 시도 중 worker가 종료되어도 다음 claim에서 종료 실패로 전환한다.
- 오류 계약의 retry 가능 여부도 확인하여 외부 `retryable=true`만으로 권한·의미 오류를 반복하지 않는다.
- 종료 실패는 lease에 `TERMINAL:` 오류를 기록하고 지식 상태 FAILED 및 앱 내 점주 운영 알림을 같은 transaction에 저장한다. 원문 전달 성공 상태를 뒤집지 않는다.
- 최신 답변에 밀린 사건은 STALE로 소비하며 불필요한 종료 실패 알림을 만들지 않는다.
- 수동 재처리는 같은 event ID를 사용하고 점주 권한·최신 revision·종료 실패를 확인한다. 이전 시도 수와 사유를 operations에 기록하고 멱등 재요청은 worker를 다시 초기화하지 않는다. 새 claim token으로 이전 worker를 차단한다.
- `POST /learn/v2/owner-events/{event_id}/retry`와 점주 상세의 event ID/시도 수/재처리 가능 정보를 추가했다. 원문이나 업무 payload를 outbox에 복제하지 않는다.
- heartbeat 간격 20초 상수와 기존 60초 lease를 유지한다. 실제 W worker의 실행/heartbeat 스케줄은 공동 인수다.

## 2. 평가 연결

- `evaluation_usage_scope`는 신뢰된 격리 in-process 하네스용 ContextVar 범위다. v2 검색 임베딩/reranker sink가 이 범위에서 EVALUATION으로 기록된다. 서로 다른 동시 평가·예외 후 범위가 섞이지 않는 반례를 검증했다.
- HTTP header/body로 평가 귀속을 지정할 수 없다. 원격 HTTP 평가 서버는 별도 격리 설정이 필요하며 이 코드만으로 원격 평가까지 완료했다고 주장하지 않는다.
- 사람 검토의 `required_raw_blocks`를 sidecar뿐 아니라 EvaluationCase에도 보존한다. 최종 보고에서 card/version/block/raw_span이 모두 인용됐는지 대조한다. 의미 판정이 true여도 필수 RAW 인용 누락은 grounded 성공으로 세지 않는다.
- 의미 정답과 근거 완전성을 별도 필드로 남긴다. 미검토 의미 정답을 자동 true로 바꾸지 않는다.
- 보고 지표 버전은 `r_v2_report/v2`. 과거 manifest에 새 선택 필드의 기본값을 채운 뒤 hash를 비교하지 않도록 수정해 기존 동결 산출물의 재보고 호환성을 유지한다. 과거 보고 파일은 수정하지 않았다.
- 단일/다회 수집 source hash에 평가 귀속 모듈을 포함한다.

## 3. 후속 질문의 적용 범위

- router가 원질문+사용자 선택으로 판정한 resolved question을 보존한다. 저장 직전 DB context를 CAS/권한/TTL 검사하여 수락한 뒤 같은 원질문+선택인지 재대조한다.
- assessment의 질문 hash를 새 질문에 맞춰 임의 재발급하지 않는다. 원질문 조건 누락·선택 변경·다른 문맥에 재사용하면 거절한다.
- 검증된 context에서 조건/예외 답변과 명시 의미 묶음을 허용한다. context ID만 붙인 미검증 planner 호출은 계속 보류한다.

## 4. 복합 조건과 묶음

- AND 조건은 원문 전체를 유지하고 순서 변경 및 `그리고`/`및` 연결을 허용한다.
- 승인 조건이 `(A 또는 B)` 형태로 명확히 묶인 경우 각 분기를 지원한다. 원문에 없는 OR를 추론하지 않는다. 매칭되는 접두부만 소비해 모든 순열의 정규식을 생성하지 않는다.
- 동일 대상/규격의 복수 값은 단순히 질문 문구가 하나와 맞는다는 이유로 선택하지 않는다. `A인 경우`/`A이 아닌 경우`, 동일 속성·단위·기준값의 이상/미만 또는 초과/이하처럼 배타성이 증명되는 제한 형식만 분기한다. 조건 없는 일반 규칙과 조건부 규칙의 겹침, 이상/이하의 경계 겹침은 계속 충돌이다.
- 조건의 ‘온도’ 단어를 요청 속성으로 오인하지 않도록, 승인 조건+질문 전체 파싱이 성공한 경우에만 속성 키워드 판정을 보완한다.
- 의미 키 `r-explicit-question/v3`에 실제 선택한 조건 분기 `scope_bindings`를 포함했다. 같은 사실을 참조해도 다른 조건 분기를 자동 병합하지 않는다. 과거 키의 pending은 재작성/자동 병합하지 않는다.

## 5. RAW 절차 확장

- 승인 Q/A에서 준비·제조·청소·마감·오픈·보관 작업과 온도가 같은 제한 질문 표현을 대응시킨다. 예: ‘라테 준비는 어떻게 해?’ ↔ ‘라테 준비 방법 알려줘’.
- 명확한 `대상 작업 방법/절차/순서:` 제목의 단일 승인 RAW 블록을 같은 작업 질문에 연결한다.
- 답변은 주의·조건·예외를 포함한 RAW 전체를 그대로 반환한다. 절차 일부만 잘라내거나 새 typed fact를 만들지 않는다. 대상/작업/온도가 다르거나 추가 조건·배수·대체 요청이 있으면 허용하지 않는다.
- 제목/명시 질문이 없는 자유 서술 전체의 의미 충분성, 임의 중첩 논리, 자유로운 표현 전체의 동치는 여전히 미완료다. 이번 확장은 제한된 지원 영역이며 일반 의미 모델을 구현/검증한 것이 아니다.

## 6. v2 FAQ와 읽기 갱신

- 기존 FAQ 조회에 v2 receipt/citation 및 최신 점주 지식화 결과를 연결했다. 현재 승인된 정확한 card version만 읽는다. 점주 원문 전달만 성공하거나 지식 상태 PENDING/REVIEW/FAILED이면 FAQ 지식으로 취급하지 않는다.
- v1 메시지는 기존 경로, v2는 별도 근거 경로로 읽어 중복 집계를 막는다. v2는 전체 resolved question·슬롯·대상·규격·현재 card version을 기준으로 묶으며 단어 겹침으로 다른 조건을 합치지 않는다.
- 과거 후속 receipt에 resolved question이 없으면 보존된 context 원질문을 사용한다.
- FAQ는 조회 시 현재 승인 상태를 반영한다. 학습 로드맵은 기존 `20260911100000_dynamic_roadmap.sql`의 발행 버전 변경 트리거와 현재 버전 조회를 사용하므로 중복 동기화기를 추가하지 않았다. 검색은 기존 공개 index 소비 경로를 유지한다. 실제 W 발행이 세 읽기 경로까지 연결되는지는 DB/W 공동 검증이다.
