## 개선된 부분과 남은 실패

직전 v9는 사건 A/B별 part 안에 여러 업무 entity 근거를 혼합해 검증 모델 호출 전 거절됐다. 이번 v10은 인계(entity 8)·결제(6)·환불(1)를 parts 3개로 나누고 A/B 결론 2개에서 조합했다. 부모 참조 합집합과 제안 구조 검사를 통과했다. 모델 입력에는 필요한 근거가 모두 있었다. 실패 응답에 receipt 후보 메타데이터가 없어 `run.json` 후보 집계는 0이지만 검색 누락을 뜻하지 않는다.

검증 모델은 `supported=true`를 반환했고 사건별 조치 구조 검사는 통과했다. 그러나 규칙 r4의 `conclusion_quote`가 실제 결론 안의 문장이 아니어서 서버가 거절했다.

- 검증기가 반환한 문장: “당직 관리자에게 확인을 요청한다. 승인 실패나 결제 완료로 단정하지 않는다.”
- 실제 결론 일부: “…당직 관리자에게 원결제 상태 확인을 요청해야 하므로 승인 실패나 결제 완료로 단정하지 않고 관리자 확인 요청 및 대기 상태 조치 사항을 적어야 합니다.”

검증기는 승인 원문 문장을 결론 인용에 넣었다. 저장된 두 모델 출력을 변경 없이 서버 검사 함수에 다시 넣어 `rule coverage quote not in conclusion`을 재현했다. 인용을 사후 교체하거나 검사를 완화하지 않았다. `supported=true`와 중간 제안의 구조 통과를 최종 정답으로 세지 않는다.

또한 미전달 B 결론은 “2만원 초과 또는 이전 영업일 결제 건 등 점주 승인이 필요한 항목임을 명시하여”라고 썼다. 사용자에게 금액·결제일을 받지 않았으므로 이 조건을 사건의 사실처럼 표현할 위험이 있다. 기계적 인용 오류만 고쳐도 이 제안이 정답이 되는 것은 아니다. 이는 보조자의 잠정 내용 검토이며 독립 사람 평가가 아니다.

## 예산과 실행 차이

기존 관찰 예약 8,748원 + 전송 진단 전체 여유분 864원 + 이번 예약 216원 = **보수적 누적 예약 9,828원/10,000원**, 잔여 예약 172원이다. 예약은 실제 지출 합계가 아니다. 이번 사용량 추정 35.87원과 구분하며, 추가 유료 호출은 하지 않았다.

계획은 migration 42개였지만 러너는 동시 작업의 `20261008130000_kakao_auth_join_sessions.sql`까지 43개를 적용했다. 실행 후 목록·hash를 `migration-observation.json`에 기록했다. 이전과 완전히 같은 DB schema라고 주장하지 않는다. 일반 의미 source hash는 계획과 같았다.

진단 API/모델 시간 예산은 30초/27초이며 운영 기본값 5초/3초를 변경하지 않았다. 임시 DB는 삭제됐고 PostgreSQL 서버도 종료했다. 운영 상태·외부 알림 변경은 없다. W 실제 출력, 실제 임베딩 검색 품질, 후속 A/B 선택, 운영 인수는 이번 평가 범위 밖이다.
