# 카드 fact 부분 편집과 원본·빈 상태 — W/R 확정 방향

작성일: 2026-10-05 (KST)

확인 기준: main `1b062b09508e134340e91ff04d1c5cd01183fc3f`

범위: 현재 카드 편집 화면·저장 API·fact 수정 서비스의 정적 코드 확인. 제품 코드 변경이나 실제 브라우저·DB 실행 결과가 아니다.

## 1. 공유할 핵심

**현재 카드는 제목과 본문 전체를 자유롭게 편집할 수 있다. fact의 정량적인 값만 수정하는 화면이 아니다.**

다만 카드 본문 수정이 fact 수정으로 연결되지는 않는다. 숫자를 바꾸든 말투를 바꾸든 새 카드 초안을 저장하며, 이 경로에서 새 fact revision을 만들지 않는다.

**목표는 카드에서 fact에 해당하는 부분만 수정할 수 있도록 바꾸는 것이다.** “넣어주세요 → 넣습니다” 같은 표현 편집은 제공하지 않는다. 아래 §2는 변경 전 구현 확인이며, §3 이후는 2026-10-05 사용자의 최신 결정과 구현 과제다. 직전 대화의 “자유 편집 유지 후 fact 변경만 반영” 방향은 최신 결정으로 대체됐다.

## 2. 현재 구현

### 화면과 저장 흐름

1. 점주 카드 상세의 **카드 내용 수정하기**를 누른다. 제외되지 않았고 초안이 있는 카드에서 표시된다.
2. 제목 `Input`과 본문 `Textarea`에서 텍스트 전체를 편집한다.
3. **초안 저장**은 `updateProductCardDraft` → `PATCH /cards/{card_id}/draft`로 제목·본문·예상 초안 버전 ID를 보낸다.
4. API가 권한·매장·제외 상태·초안 버전 충돌을 확인한다.
5. `create_draft`가 `card_versions`에 `OWNER_EDIT` 새 버전을 만들고 기존 `card_evidence`를 복사한다. 카드 제목·본문·초안 포인터를 갱신하고 `EDIT_DRAFT` 사건을 남긴다.
6. 저장만으로 직원에게 공개되지 않는다. **수정본 직원 공개**를 실행해야 새 공개판에 반영된다.

| 수정 예시 | 현재 저장 처리 | 이 경로의 fact 변경 |
|---|---|---|
| “컵에 넣어주세요” → “컵에 넣습니다” | 새 카드 초안·편집 사건 | 없음 |
| “시럽 2번” → “시럽 3번” | 새 카드 초안·편집 사건 | 없음 |
| “항상 제공” → “요청할 때 제공” | 새 카드 초안·편집 사건 | 없음 |
| 금지·예외·순서 문장 추가 또는 삭제 | 새 카드 초안·편집 사건 | 없음 |

제목은 1~200자, 본문은 1~4,000자이며 공백 정리·빈 값 검사가 있다. 숫자만 수정하게 제한하거나 문구 수정과 사실 수정을 의미적으로 구분하는 검사는 이 저장 경로에 없다.

### fact 수정 서비스는 별도로 존재

`FactChange`에는 `value`, `unit`, `polarity`, `conditions`, `exceptions`, `step_order`, `assertion`, `original_assertion`이 있다. 따라서 fact 자체도 정량 정보만 다루는 구조가 아니다. 조건·부정·예외·순서·사실 문장도 대상이다.

`revise_fact`는 새 사실 revision을 만드는 서비스지만, 현재 카드 편집 API·화면에서 호출하지 않는다. 서비스가 있다는 것과 사용자가 화면에서 사실을 수정할 수 있다는 것은 구분해야 한다.

## 3. 사용자 확정 방향

1. **점주 답변은 텍스트 파일로 정리하고 원본자료로 활용한다.** 답변 원문과 연결을 보존하며 이를 fact·카드의 출처로 사용한다. 저장 위치·파일 생성 시점·기존 owner_answer 출처와의 호환은 구현 시 구체화한다. 이 PR은 파일 생성이 이미 구현됐다는 보고가 아니다.
2. **카드에서 fact에 해당하는 부분만 수정할 수 있게 한다.** 현재 제목·본문 전체 자유 편집을 목표 방식으로 유지하지 않는다. 말투·어미·장식 문구는 편집 대상에서 제외하며, 별도의 표현 편집 기능을 선택지로 두지 않는다. 제목도 연결된 fact 항목이 확인되는 부분에 한해 같은 규칙을 적용한다.
3. **카드가 없으면 정상적인 빈 상태로 전달한다.** 점주에게 “아직 등록된 지식이 없어요. 자료를 등록해 주세요.”처럼 안내한다. 마지막 카드 제외도 정상적인 빈 공개 상태다. 첫 점주 답변은 기존 후보 0개로 새 지식 처리에 들어갈 수 있어야 한다. 승인 지식이 있는데 색인 조회가 실패한 장애는 빈 상태로 숨기지 않는다.

fact는 숫자만 뜻하지 않는다. 값·단위뿐 아니라 대상·규격·조건·부정·예외·순서 등 업무 사실에 해당하는 내용이 포함된다. 기존 사실 수정은 새 `fact_revision`과 이전 판 연결로 기록하고 재승인한다. 변경하지 않은 사실은 기존 revision을 유지한다. 카드 버전·편집 사건·과거 인용 보존 정책은 유지한다.

| 카드의 내용 | 수정 가능 여부 | 저장 방향 |
|---|---|---|
| “시럽 2번”의 수량 2 → 3 | 연결된 fact의 값으로 수정 가능 | 해당 fact 새 revision → 카드 초안 갱신 → 재승인 |
| “요청할 때 제공”의 적용 조건 변경 | 연결된 fact 조건으로 수정 가능 | 해당 fact 새 revision → 카드 초안 갱신 → 재승인 |
| 금지·예외·절차 순서 변경 | 연결된 fact 항목으로 수정 가능 | 관련 사실의 의미·의존 관계 검증 후 새 revision |
| “넣어주세요” → “넣습니다” | 표현 변경이므로 수정 대상 아님 | 별도 표현 편집·fact 변경 없음 |
| 같은 숫자가 카드에 여러 번 등장 | 선택한 부분에 연결된 fact만 수정 | 문자열 전체 치환 금지, 다른 대상·규격의 fact 유지 |

## 4. 카드 생성 시 fact와 편집 가능한 부분을 연결

사용자가 제안한 “카드를 생성할 때 어떤 부분이 fact인지 알고 있으니 그 부분만 수정”하는 방식으로 구현을 구체화한다. 완성된 문장에서 단어를 다시 추측하기보다 **생성·렌더링할 때 사용한 fact와 항목 정보를 함께 전달**하는 것이 출발점이다.

### 현재 있는 기반과 추가할 것

- 현재 ingest는 `card_facts`로 카드와 사실의 연결을 저장한다. 이는 카드 단위 연결이며 화면의 각 단어·필드 위치를 알려주는 정보는 아니다.
- [CardPlan·CardBlock](../../../api/app/contracts/card.py)은 블록의 `fact_revision_ids`를 표현할 수 있다. 하지만 블록 참조만으로 특정 단어가 어느 fact 항목인지 자동으로 확정되지는 않는다.
- [현재 공개 생산 코드](../../../api/app/publish/content.py)는 본문을 RAW 구간으로 고정하고 `fact_revisions=()`를 전달한다. 현재 자유 편집 카드에 이미 단어별 fact 연결이 완성됐다고 간주하면 안 된다.
- W3에서 화면에 표시할 부분과 `card_version / block / fact_revision / field`의 대응 정보를 정의하고 저장 또는 동일하게 재생성해야 한다. 구체적인 DTO·저장 형식은 구현 설계 과제다.
- 조건·부정·예외는 단어 하나보다 문장·구절 단위가 될 수 있다. 숫자 하이라이트만으로 편집 범위를 정하지 않는다.

### 목표 처리 흐름

1. W가 사실 참조로 카드를 생성하고 서버가 렌더링하면서 fact별 편집 가능한 부분의 연결 정보를 만든다.
2. 화면은 해당 부분만 선택·수정 가능하게 보여준다. fact에 연결되지 않은 말투·표현은 읽기 전용이다.
3. 저장 요청은 전체 자유 본문의 교체 대신 대상 fact·필드·새 값·예상 버전을 전달한다. 서버에서도 매장·카드·fact 연결, 허용 필드, 버전 충돌을 검사한다.
4. 실제로 변경된 fact만 새 revision으로 만들고 카드 초안과 참조·렌더링 결과를 일치시킨다. 값이 같으면 불필요한 fact revision을 만들지 않는다.
5. 승인 전에는 기존 공개판을 유지한다. 재승인 시 새 카드·사실 참조·색인을 함께 전환하며 과거 인용은 보존한다.

레거시 RAW 카드에는 이 연결이 없을 수 있다. 없는 연결을 추정해 편집을 허용하지 않으며, W가 사실 연결을 만드는 전환 절차를 설계한다. 구조화되지 않은 원문을 억지로 숫자 fact로 바꾸지 않는다.

완료 확인 사례:

- 수치 수정: 새 사실 revision·카드 초안이 생기고 승인 전에는 기존 공개 내용이 유지된다.
- 조건·부정·예외 수정: 숫자가 없어도 의미 변경으로 반영된다.
- 승인 이후: 카드 화면과 R 답변·인용이 같은 승인 사실을 가리킨다.
- 과거 인용: 새 수정·승인 이후에도 당시 승인판의 내용을 확인할 수 있다.
- 표현 편집 차단: fact에 해당하지 않는 어미·말투는 화면에서 수정할 수 없고, API로 임의 본문 변경을 보내도 새 편집 계약을 우회할 수 없다.
- 부분 연결 정확성: 같은 값이 반복되거나 HOT/ICE 값이 같아도 선택한 fact 항목만 변경된다. 변경하지 않은 fact와 값이 같은 재저장에는 새 revision을 만들지 않는다.
- 레거시 RAW 카드: 전환 중에도 기존 공개판과 출처가 보존된다.
- 점주 답변: 텍스트 파일 원본과 fact·카드·인용의 연결이 보존된다.
- 카드 0개: 등록 안내가 정상 표시되고, 마지막 카드 제외와 첫 점주 답변 처리가 색인 장애로 오인되지 않는다.

## 6. 이번 공유의 검증 범위

현재 화면·API·저장 함수와 fact 서비스의 호출 관계를 정적으로 대조했다. 문서 링크 및 Git diff 형식을 확인한다. 이 문서 추가로 제품 코드·DB·운영 설정은 변경하지 않으며, 테스트·브라우저 사용 흐름을 새로 실행했다고 주장하지 않는다.
