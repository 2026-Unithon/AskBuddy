# 카드 문구 편집과 fact 수정 — W/R 공유 검토

작성일: 2026-10-05 (KST)

확인 기준: main `1b062b09508e134340e91ff04d1c5cd01183fc3f`

범위: 현재 카드 편집 화면·저장 API·fact 수정 서비스의 정적 코드 확인. 제품 코드 변경이나 실제 브라우저·DB 실행 결과가 아니다.

## 1. 공유할 핵심

**현재 카드는 제목과 본문 전체를 자유롭게 편집할 수 있다. fact의 정량적인 값만 수정하는 화면이 아니다.**

다만 카드 본문 수정이 fact 수정으로 연결되지는 않는다. 숫자를 바꾸든 말투를 바꾸든 새 카드 초안을 저장하며, 이 경로에서 새 fact revision을 만들지 않는다.

“표시 문구 수정과 사실 내용 수정을 분리한다”는 설명은 현재 기능 설명이 아니라 W3에서 검토할 설계다. 현재 구현, 사용자 의향, 아직 결정하지 않은 사항을 아래처럼 구분한다.

## 2. 현재 구현

### 화면과 저장 흐름

1. 점주 카드 상세의 **카드 내용 수정하기**를 누른다. 제외되지 않았고 초안이 있는 카드에서 표시된다.
2. 제목 `Input`과 본문 `Textarea`에서 텍스트 전체를 편집한다.
3. **초안 저장**은 `updateProductCardDraft` → `PATCH /cards/{card_id}/draft`로 제목·본문·예상 초안 버전 ID를 보낸다.
4. API가 권한·매장·제외 상태·초안 버전 충돌을 확인한다.
5. `create_draft`가 `card_versions`에 `OWNER_EDIT` 새 버전을 만들고 기존 `card_evidence`를 복사한다. 카드 제목·본문·초안 포인터를 갱신하고 `EDIT_DRAFT` 사건을 남긴다.
6. 저장만으로 직원에게 공개되지 않는다. **수정본 직원 공개**를 실행해야 새 공개판에 반영된다.

| 수정 예시 | 현재 저장 처리 | 이 경로의 fact 변경 |
|---|---|---|
| “컵에 넣어주세요” → “컵에 넣습니다” | 새 카드 초안·편집 사건 | 없음 |
| “시럽 2번” → “시럽 3번” | 새 카드 초안·편집 사건 | 없음 |
| “항상 제공” → “요청할 때 제공” | 새 카드 초안·편집 사건 | 없음 |
| 금지·예외·순서 문장 추가 또는 삭제 | 새 카드 초안·편집 사건 | 없음 |

제목은 1~200자, 본문은 1~4,000자이며 공백 정리·빈 값 검사가 있다. 숫자만 수정하게 제한하거나 문구 수정과 사실 수정을 의미적으로 구분하는 검사는 이 저장 경로에 없다.

### fact 수정 서비스는 별도로 존재

`FactChange`에는 `value`, `unit`, `polarity`, `conditions`, `exceptions`, `step_order`, `assertion`, `original_assertion`이 있다. 따라서 fact 자체도 정량 정보만 다루는 구조가 아니다. 조건·부정·예외·순서·사실 문장도 대상이다.

`revise_fact`는 새 사실 revision을 만드는 서비스지만, 현재 카드 편집 API·화면에서 호출하지 않는다. 서비스가 있다는 것과 사용자가 화면에서 사실을 수정할 수 있다는 것은 구분해야 한다.

## 3. 사용자 의향과 미확정 사항

2026-10-05 대화에서 사용자는 다음 방향을 제시했다.

- 문구만 바꾸는 경우에는 별도의 사실 변경 기록이 필요하지 않다.
- 수치·조건 등 업무 내용이 바뀌면 새로운 사실 내용으로 정리해야 한다.
- 현재 화면이 fact 항목만 수정하는 구조인지, 표현 변경도 가능한지 먼저 확인하고 싶다.

이 의향은 **현재 카드 버전·편집 사건을 삭제하라는 결정이 아니다.** 문구만 바뀔 때 별도 fact revision을 만들 필요가 없다는 방향과, 공개판·과거 인용을 보존하는 카드 버전 정책은 따로 다뤄야 한다.

또한 자유로운 표현 편집 기능을 앞으로도 유지할지, 새로 별도 제공할지는 아직 확정하지 않았다. 숫자만 편집하게 제한하는 정책도 확정하지 않았다.

기존 사실을 고치는 경우는 정본의 새 `fact_revision`과 이전 판 연결 원칙을 따른다. 독립된 사실을 추가하는 것과 기존 사실의 새 판을 만드는 것은 구분한다.

## 4. W3에서 결정할 편집 방식

W3 목표는 대상별 사실 revision을 모아 CardPlan의 참조를 검증하고 서버가 카드 본문을 렌더링하는 것이다. 현재의 자유 본문 편집을 그대로 연결하면 카드 문장과 참조 fact가 서로 달라질 수 있다.

예: 본문에서 “시럽 2번”을 “시럽 3번”으로 바꿨지만 연결된 fact는 여전히 2번이면, 직원 카드와 fact 기반 답변이 다른 내용을 보여줄 수 있다. 이는 W3 연결 시 방지해야 할 불일치이며, 이번 확인에서 운영 장애를 재현한 것은 아니다.

| 선택지 | 동작 | 함께 정할 것 |
|---|---|---|
| A. 사실 항목 편집 중심 | 값·단위·조건·예외·순서 등 사실을 수정하고 서버가 본문을 다시 렌더링 | 기존 자유 본문 편집의 전환·레거시 RAW 카드 처리 |
| B. 사실 편집 + 제한된 표시 문구 편집 | 사실은 위와 같이 수정하고 의미를 바꾸지 않는 표시 설정만 별도로 제공 | 허용 필드·표현 범위, 사실을 덮어쓰지 않게 하는 검증·저장 방식 |

팀 검토 출발점은 A로 두고, 표현 편집이 실제로 필요한 경우에만 B의 범위를 구체화하는 것을 제안한다. **이는 제안이며 사용자·팀의 확정 결정은 아니다.** 임의 자유 문장을 “문구만 수정”으로 분류하는 체크박스만으로 사실 일치가 보장되지는 않는다.

## 5. 담당별 다음 작업

| 담당 | 다음 작업 |
|---|---|
| W | 편집 방식 A/B와 레거시 카드 전환안을 제시한다. 사실 편집 UI·API를 `revise_fact` 및 카드 재조립에 연결하고, 새 초안의 사실 참조를 고정한다. 수치뿐 아니라 조건·예외·부정·순서도 편집 범위에 포함한다. |
| R | 새 공개판의 카드·블록·fact revision 일치를 검토한다. 승인 전에는 이전 공개판을 조회하고, 승인 후에는 새 판을 검색·인용하며 과거 답변의 인용이 유지되는지 검증한다. |
| W + R | 카드 수정→사실 새 판→초안 재조립→승인→색인→직원 답변의 계약과 실패 시 원자성을 함께 검증한다. |

완료 확인 사례:

- 수치 수정: 새 사실 revision·카드 초안이 생기고 승인 전에는 기존 공개 내용이 유지된다.
- 조건·부정·예외 수정: 숫자가 없어도 의미 변경으로 반영된다.
- 승인 이후: 카드 화면과 R 답변·인용이 같은 승인 사실을 가리킨다.
- 과거 인용: 새 수정·승인 이후에도 당시 승인판의 내용을 확인할 수 있다.
- 표시 문구 편집을 제공하는 경우: 별도 fact revision 없이 허용 범위만 변경되며 사실·근거가 달라지지 않는다. 카드 버전·공개 정책은 별도로 합의한다.
- 레거시 RAW 카드: 전환 중에도 기존 공개판과 출처가 보존된다.

## 6. 이번 공유의 검증 범위

현재 화면·API·저장 함수와 fact 서비스의 호출 관계를 정적으로 대조했다. 문서 링크 및 Git diff 형식을 확인한다. 이 문서 추가로 제품 코드·DB·운영 설정은 변경하지 않으며, 테스트·브라우저 사용 흐름을 새로 실행했다고 주장하지 않는다.
