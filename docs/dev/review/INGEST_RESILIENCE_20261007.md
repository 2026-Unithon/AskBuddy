## 변경

- `INGEST_STAGE_RETRIES=3`: 최초 1회 + 추가 3회. timeout·연결 오류·429·408·5xx·일시 DB 장애에 지수 backoff+jitter. 인증/입력/제약 오류·예산 초과·출력 잘림을 무작정 반복하지 않는다.
- 시작 receipt는 DB 저장만 재시도. 완료 receipt/응답 원문 저장 실패도 저장만 재시도하며 유료 호출은 반복하지 않는다. 시작 저장의 결과가 불명확한 뒤 unique 충돌이 나면 중복 과금 방지를 위해 중단한다.
- 공급자 재시도는 매 시도마다 별도 receipt와 attempt_no를 남긴다. Gemini/Anthropic SDK의 숨은 재시도를 끄고 공통 계측 경로에서 최대 4회로 통일했다.
- `INGEST_DB_TIMEOUT_SECONDS=10`: receipt·원문 INSERT 대기 제한. 완료 receipt의 종전 0.2초×2회 제한을 10초×최대4회로 변경. 시작 실패 로그에 acquire/insert 단계를 남긴다.
- `INGEST_SOURCE_CONCURRENCY=2`, `INGEST_MODEL_CONCURRENCY=4`: 프로세스/event loop 전체 제한. 자료 내부의 `LAYOUT_CONCURRENCY=4`와 별개다. 초과 작업은 슬롯을 기다린다. 이 제한은 ingest 모델 경로이며 채팅·STT 등 서비스 전체 공급자 호출 제한은 아니다.
- 평가 하네스는 장시간 점유하던 연결을 ShortSession으로 교체. 기존 DB 풀 10개 중 한 개를 실행 전체 동안 잡지 않는다.
- 병렬 띠 하나가 실패해도 형제 호출의 종료·기록을 기다리고 구역 실패로 처리한다. 다음 구역과 미완료 호출이 중첩되지 않는다.
- 원장 checkpoint는 트랜잭션 단위로 재시도하고 커밋 후 ID를 반영한다.
- `ASSEMBLE_BATCH_FACTS=200`: 동일 대상의 모든 규격을 같은 배치로 유지하며 카드 조립을 나눈다. 한 대상만 200건을 넘으면 묶음을 보존하므로 이 값은 엄격한 토큰/사실 상한이 아니다. 너무 큰 단일 대상이나 긴 텍스트의 출력 잘림 가능성은 남는다.
- 예산 검사/사용량 누적을 공통 계측 경로로 이동해 기존에 빠지던 일반 추출·조립도 실행 예산에 포함한다. 이미 진행 중인 호출과 사용량 미보고까지 포함한 엄격한 청구액 상한은 아니다.

## 동시 호출 계산과 실측

사용자 수 U, 사용자당 순간 호출 C이면 N=U×C. 풀 P=10에서 같은 순간 DB를 빌리려는 N>10부터 대기가 생긴다. 대기는 실패와 다르다. 작업당 연결 점유시간 d초를 일정하다고 가정하면 마지막 완료시간은 대략 ceil(N/P)×d이며, timeout T초를 넘는 요청부터 실패할 수 있다. 연결 생성·네트워크·쿼리 편차는 별도다.

수정 후 ingest 공급자 동시 호출은 프로세스당 최대 4개. N개의 모델 요청이 이미 준비돼 있고 각각 L초 걸린다는 단순 모형에서 마지막 요청의 시작 대기는 floor((N−1)/4)×L이다. L=15초 가정 시:

| 사용자 | 1인당 호출 | 준비된 모델 요청 | 동시 실행 | 최대 시작 대기(가정) |
|---:|---:|---:|---:|---:|
| 1 | 4 | 4 | 4 | 0초 |
| 2 | 4 | 8 | 4 | 15초 |
| 5 | 4 | 20 | 4 | 60초 |
| 10 | 4 | 40 | 4 | 135초 |
| 20 | 4 | 80 | 4 | 285초 |
| 50 | 4 | 200 | 4 | 735초 |
| 50 | 8 | 400 | 4 | 1,485초 |

모델 평균 지연 L초, 프로세스 동시 제한 G=4, 계정 RPM=R, TPM=M, 호출당 평균 토큰 K이면 지속 처리량의 상한은 `min(G/L, R/60, M/(60K))` 호출/초다. 사용자당 초당 요청량이 λ이면 `U×λ`가 이 값보다 작아야 대기열이 계속 늘지 않는다. 계정 R/M은 이번 환경에서 확인되지 않아 사용자 수의 공급자 한계는 미확정이다.

위 표는 모델 요청만의 계산이며 전체 문서 완료시간이 아니다. 자료 처리는 동시 2개이므로 나머지 자료는 앞단에서도 기다린다. 실제 LOW 추출 receipt 평균은 이전 두 실행에서 14.1~16.6초였지만 단계별 편차와 순차 의존성이 크다.

## 검증

- 격리 UUID DB에 migration을 적용한 실제 DB 검증: 원문 보존·타 매장 조회/갱신 차단·재사용·PARTIAL 재시도 22개 통과. 검증 DB는 종료 시 삭제했다. 전체 rebuild 부가 검증은 W publish 92개까지 통과했으나 이후 별도 검증의 고정 포트 55439 접속 거부로 중단되어 전체 통과로 보고하지 않는다.
- 전체 단위 테스트: 1,734 passed, 4 xfailed, 131 subtests passed.
- 추가 회귀: 4번 후 중단, 영구 오류/취소 즉시 전달, 공급자 시도별 receipt, 시작 저장 실패 시 모델 미호출, 원문 저장 4회에도 모델 1회, 400요청에서 최대 동시4, 취소 후 permit 반환, 대상/규격 보존 배치.
- 변경 파일 25개 격리 AST 검사: 위반 없음. ingest 전체 폴더 검사는 변경하지 않은 기존 repository.py의 15건을 보고하며, 이를 이번 수정으로 해결했다고 주장하지 않는다.
- 운영 capacity의 나머지 변수: 공급자 계정별 RPM/TPM/일일 quota, 문서 크기·페이지 수·토큰 수, CPU·메모리, HTTP 업로드/폴링 부하. 계정 quota와 실사용 트래픽 부하시험 없이 “N명까지 무조건 안전”을 확정할 수 없다.
- 제한은 프로세스 단위이므로 W개 worker이면 모델 최대4W, 자료 최대2W, DB 연결 최대10W. 여러 서버/worker의 전역 한도에는 공유 admission/queue가 추가로 필요하다. 현재 BackgroundTasks의 무제한 접수·프로세스 종료 복구까지 이 제한이 대체하지 않는다.

### 충전 후 재개

현재 store-a는 자료81 하나이며, **reset_eval_store.py를 실행하지 않는다**. source_id가 재사용 키에 포함되므로 삭제·재업로드하면 성공 응답을 재사용할 수 없다. 같은 자료·설정·용어집·카테고리를 유지한다.

```bash
cd api
.venv/bin/python scripts/run_extract_eval.py \
  --store store-a --reuse-sources \
  --label layout-low-resilience-resume --max-usd 3.0 \
  --env-override SCAN_EXTRACT_MODE=LAYOUT \
  --env-override LAYOUT_RECHECK_MAX_CALLS_PER_SOURCE=10 \
  --env-override LAYOUT_GEMINI_THINKING_LEVEL=LOW \
  --env-override EXTRACT_REUSE_ENABLED=true \
  --env-override EXTRACT_REUSE_FOR_EVALUATION=true
.venv/bin/python scripts/compare_reference.py \
  --store store-a --source-key a-scan-recipebook \
  --label layout-low-resilience-resume
```

재개는 성공 응답 캐시를 조회하며 없는 호출만 공급자에 요청한다. 입력이나 설정이 바뀌거나 캐시 조회가 실패하면 새 호출이 생길 수 있다. store-a에 다른 자료를 추가하면 --reuse-sources는 그것도 처리하므로 실행 전 자료 구성을 확인한다. 이 실행은 복구 검증이며 독립적인 품질 반복 실험으로 세지 않는다. 이번 턴에서는 충전·추가 결제·재개 호출을 수행하지 않았다.
