# R 근거 범위와 사건별 결론 구분 — 2026-10-08

직전 실제 Gemini 제안은 A/B 사건별로 parts를 만들면서 한 part에 인계·결제·환불 등 서로 다른 knowledge entity의 RAW를 넣었다. 서버가 이를 거절하는 것은 기존 참조 범위 계약에 따른 동작이다. 이번에는 **모델에 전달하는 근거 소속표, 출력 계약 설명, 오류 진단과 회귀/통합 검증**을 보완했다. 유료 호출은 하지 않았다.

## 구현

- 일반 의미 v10. `reference_scopes`는 검색 후보만을 실제 승인 entity별로 묶어 참조 목록을 제공한다. 검색되지 않은 블록이나 다른 매장 자료를 후보로 늘리지 않고 근거의 필요성도 미리 판단하지 않는다.
- 제안 입력의 capabilities와 검증 입력에 같은 소속표를 넣는다. 검증에서는 request_hash에 포함한다. typed 사실의 속성/규격/조건 검사는 기존대로 별도 수행한다.
- 모델 schema의 AnswerPart 및 결론 필드 설명, 제안/검증 프롬프트에서 **근거별 parts**와 **사건별 conclusions**를 명시적으로 구분한다. 인계·결제·환불의 parts 3개로 A/B 결론 2개를 만들 수 있고 공통 근거는 재사용할 수 있다.
- RAW 참조가 해석 entity 범위를 넘으면 구체적 오류로 거절한다. 승인 ID 보정이나 실패 제안의 자동 재분할은 없다. 부모/자식 참조 합집합, 질문/사용자 발화 인용, 현재 승인판, 결론/규칙/사건 적용, 렌더·저장 검사를 유지한다.

이 변경은 모델이 계약을 지키도록 입력과 설명을 명확히 한 것이다. 새로운 소속표가 자연어 의미 판단을 대신하거나 실제 Gemini 형식 오류 재발을 보장해서 막지는 않는다. 기존 두 호출 구조와 기본 OFF를 유지하고, 추가 호출/자동 재시도/운영 활성화는 없다. 공개 API·DB schema는 변경하지 않았다. 소스 hash가 달라 기존 실제 평가 release는 재사용할 수 없다.

3턴 통합 검증은 `verify_r_part_scope_flow.py`로 실행했다. 실제 승인 공개 조정자·검색·API·DB·문맥·저장·인용 조회를 쓰되 모델 출력은 합성으로 고정했다. 첫 답변은 3개 지식 범위→2개 사건 결론, 재질문은 실제 설명형 A/B 선택지를 반환한다. 평가 러너가 `question=option="A는 결제 상태 미확인"`과 서버의 context_id/revision을 보내면 선택된 A만 확정 문맥으로 전달되고 최종 인용 답변이 저장된다. 이는 이전 422 러너 오류의 실제 API/DB 경로 수정 확인이며 **Gemini의 실제 답변 품질 성공이 아니다.**

실제 실패 모델 출력은 `api/tests/fixtures/r_part_scopes_live_20261008.json`에 그대로 보존했다. 재분할된 양성 예제와 검증기의 supported 응답은 합성임을 명시했고, 과거 제안을 정답으로 고쳐서 실제 평가에 합산하지 않았다.

## 다음 확인

실제 Gemini에 새 소속표/계약이 전달됐을 때 첫 제안이 업무별 parts를 올바르게 만들고 사건별 결론/선행 규칙 검증까지 통과하는지 확인해야 한다. 그다음 설명형 사건 선택 후속까지 재평가한다. 기존 보수적 예약 장부는 9,612원/1만원이며 추가 호출은 잔여 예약·실제 사용량 근거를 대조해 사전 동결한 예산 안에서만 수행한다. 이번 검증에 비용을 추가하거나 이전 실제 실패 결과를 덮지 않았다.
