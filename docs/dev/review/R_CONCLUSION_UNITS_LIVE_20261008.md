## 개선 확인 범위

직전 v10 첫 질문은 검증기가 승인 원문을 결론 인용에 넣어 거절됐다. 이번 결론이 있는 1·3턴은 서버 문장 ID를 실제 선택했고 규칙 인용 및 문장별 사건 사실 검사의 형식 오류가 없었다. 이전 러너의 선택 question/option 불일치 422도 이번에는 재발하지 않았다. A/B 선택을 API 계약에 맞게 전달했고 이전 사용자 문맥이 두 후속 요청에 포함됐다.

미확인 환불 금액·날짜 단정은 이번 출력에서 관찰되지 않았다. 그러나 첫 답변이 구체적 조치를 생략하며 짧아졌으므로, 해당 단정 방지의 안정적 효과가 증명된 것은 아니다. 비교는 같은 첫 질문의 단계별 관찰이며 이전 1턴과 이번 3턴의 전체 비율을 개선율로 직접 비교하지 않는다.

## 실패 원인과 예시

첫 답변은 다음과 같이 안내했다.

> 미해결 건인 A(결제 상태 미확인)와 B(환불 승인 대기)를 다음 담당자에게 인계할 때는 주문번호 또는 사건번호, 현재 상태, 다음 조치, 기한, 담당자를 모두 적어야 합니다.

출처는 맞지만 “다음 조치”라는 필드명만 제시했다. 검증기는 일반 양식 질문이라고 해석해 `case_action_review.scope=NOT_APPLICABLE`로 반환했다. 필요한 결제/환불 근거는 모델 후보 안에 있었으므로 검색 누락이 아니라 질문의 범위를 축소한 의미 판정 문제다.

참고용 개선 답안(실제 Gemini 출력 아님): A/B를 별도로 기록하고 각각 사건번호·현재 상태·다음 조치·기한·담당자를 적는다. A는 원결제 상태 미확인으로 대기를 유지하며 당직 관리자에게 확인을 요청한다. B는 환불 승인 대기 상태와 점주 승인 확인을 다음 조치로 적는다. 확인되지 않은 금액·날짜·승인 사유는 임의로 적지 않는다.

마지막 A 선택 뒤 제안은 읽음만으로 완료 처리할 수 없고 지정 인수자의 업무 인수 확인이 필요하다고 설명했다. 그러나 검증기가 인용한 상태 **“메시지 읽었대”**가 결론의 **“메시지를 읽었다는”**에 문자 그대로 포함되지 않아 `missing_case_actions=[0]`이 됐다. 원문 사용자 출처·사건명·다음 행동 인용과 새 규칙 문장 ID 검사는 통과했다. 원본 출력을 변경 없이 서버 함수에 넣어 같은 결과를 재현했다.

이 검사는 바꿔쓴 표현을 거절했지만 미전달 제안을 완전한 정답으로 세지는 않는다. 사전 답안이 요구한 원결제 미확인 유지·대기·관리자 확인 조치도 빠졌기 때문이다. 문자열 검사 완화와 답변의 내용 완결성은 별도로 검증해야 한다.

필요한 재질문은 적절한 대응으로 인정했다. 다만 제2턴은 사전의 “읽음만으로 완료 아님을 함께 안내” 항목을 충족하지 못했고 제3턴이 실패해 대화 완결은 아니다. 판정은 보조자의 잠정 검토이며 독립 사람 채점이나 모델의 일반 정확도 지표가 아니다.
