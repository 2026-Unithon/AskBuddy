# C0 R 구현 엄밀 검토

> 후속 상태: 사용자 요청으로 R 자체 결함을 수정했다. 아래 발견 사항은 수정 전 기록이며, 현재 수정 결과는 문서 끝의 **R 자체 수정 결과**를 따른다.

대상: 이번 작업 디렉터리의 R 변경과 `C0_DECISIONS_AND_PLAN.md`, `C0_COST_MEASUREMENT_PLAN.md`.
방법: 변경 diff와 기존 호출자·발급기·리포트 소비자를 대조하고 offline 반례 5개를 실행했다.
제품 코드는 이번 검토에서 수정하지 않았다. 아래 P1은 즉시 회귀 수정 또는 새 경로 연결 전 해결,
P2는 원가/기능 인수 전 해결을 뜻한다. 실제 공격·유료 모델 품질·운영 비용 검증은 아니다.

## 결론

이전의 테스트 169개 통과는 테스트 실행 결과로 맞지만, 계획 충족 또는 회귀 없음의 증거로 충분하지 않다.
새 테스트는 JWT에 직접 exp를 넣고, 조건 없는 단일 속성·확정 온도와 큰 비용 예제를 사용하여 아래 반례를 놓쳤다.
현재 R 전체/C0 전체는 완료되지 않았으며, W 산출물 대기와 별도로 R이 바로 고칠 수 있는 결함도 남아 있다.

## 발견 사항

### RR-01 · P1 · 새 exp 필수 검증과 기존 토큰 발급기가 충돌

- 위치: `api/app/deps.py:60`, `api/scripts/dev_token.py:83`.
- `get_claims`는 exp가 없는 JWT를 거절하도록 바뀌었지만 `mint`는 exp를 넣지 않는다.
- **재현:** 실제 `mint(force=True, team=True)` 함수의 DB만 fake로 대체하여 발급한 토큰을 실제 `get_claims`에 넣으면 401이다. 토큰/비밀값은 출력하지 않았다.
- 영향: 문서에 안내된 개발 토큰, `/team` 내부 평가 토큰, `ingest_smoke.py`의 로컬 mint fallback이 깨진다. 일반 `/auth` 토큰은 exp를 발급하므로 이 회귀와 구분한다.
- 수정 방향: exp 검증을 유지하고 모든 허용 발급기를 같은 만료 정책으로 보강한다. 발급기→검증기 왕복 테스트가 필요하다. W 선행과 무관하다.

### RR-02 · P1 · 질문 predicate 하나만 맞으면 무관한 블록도 함께 통과

- 위치: `api/app/learn/answer_validation.py:114`.
- 현재 구현은 질문 predicate의 존재 여부만 검사한다. 다른 predicate의 블록이 실제 prerequisite인지, 승인된 필수 주의인지 검사하지 않는다.
- **재현:** 우유량 질문에 우유량 블록과 같은 카드·규격의 별도 업무 블록을 선택했다. 두 사실 사이 requires 관계가 없는데도 인용 2개로 통과한다.
- 계획 §5.2의 질문별 선택·predicate·dependency 검증을 충족하지 않는다. 승인 근거에 있다는 사실과 질문에 필요한 근거라는 사실은 다르다.
- 수정 방향: 답변 대상 사실 집합을 확정하고 그 dependency closure·승인 필수 주의만 추가 허용한다. 전체 블록 선택 정책만으로 다른 무관한 블록 선택을 허용하면 안 된다.
- 현재 validator는 제품 경로 미연결이므로 현재 직원 답변에서 재현된 오류라고 주장하지 않는다.

### RR-03 · P1 · 조건·예외가 있는 사실도 적용성 확인 없이 성공 반환

- 위치: `api/app/learn/answer_validation.py:23`, `api/app/learn/answer_validation.py:105`.
- ResolvedSelection은 entity/predicate/variants만 가지며 사용자 확인 조건·예외를 전달할 수 없다.
- **재현:** 사실에 `포장 주문에만 적용`, `특별 행사일 제외`를 넣어도 동일 질문 객체로 통과했다. 조건이 사실에 남아 있다는 것과 해당 질문에 적용 가능한지 검증하는 것은 별개다.
- 계획 §5.2는 조건·예외 검사를 포함한다. 이전 구현 기록은 의미 적용성을 후속으로 명시했으므로 은폐된 완료 주장은 아니지만, 일반적인 최종 `validate_answer_plan`으로 연결할 수 없는 명시적 미완성이다.
- 수정 방향: query 조건과 승인 조건의 대응 규칙을 추가한다. 그 전에는 조건부 사실을 추가 검증 없이 승인하지 말고 검토 미완료 상태로 구분한다. 단순 문자열 같음으로 의미 판정을 대신해서는 안 된다.

### RR-04 · P2 · Decimal 도입 후에도 합산 전에 반올림하여 작은 비용이 소실

- 위치: `api/app/team/runner.py:162`, `api/app/team/metrics.py:312`.
- estimate_cost가 매 호출마다 소수점 6자리로 반올림한 float를 반환하고 aggregate가 이 값들을 합산한다.
- **재현:** 가상 단가 입력 1,000토큰당 0.0004 USD, 호출당 입력 1토큰, 출력 0으로 1,000회를 합산했다. 구현은 0 USD, 합계 후 반올림한 값은 0.0004 USD다.
- 원가 계획 §5.7의 “합계 후 반올림”과 다르다. 반올림 위치 문제는 기존에도 있었고 이번 Decimal 변경으로 해결되지 않았다.
- 수정 방향: receipt부터 합산까지 충분한 정밀도의 Decimal/NUMERIC을 유지하고 출력 경계에서 반올림한다. DB `evaluation_results.cost_usd`의 정밀도도 함께 검토해야 한다. 실제 공급자 요율 예제가 아니다.

### RR-05 · P2 · 명백한 답변 모델 미호출과 관측 누락을 구분하지 못함

- 위치: `api/app/team/runner.py:102`, `api/app/team/metrics.py:306`.
- 검색 MISS에서 답변 모델은 호출하지 않지만 답변 토큰/비용은 전부 None이다. 새 집계는 이 행을 관측 누락으로 센다.
- **재현:** fake 검색 MISS로 `_execute`를 실행하면 prompt/completion/answer cost가 모두 null이다.
- 원가 계획은 측정된 0·NOT_BILLABLE과 UNKNOWN을 구분한다. 정상적인 HIT+MISS 평가에서 답변 단계 관측이 완전해도 총액이 영구 partial이 될 수 있다.
- 수정 방향: 단계별 호출 여부/미과금 근거/관측 상태를 저장한다. **MISS의 전체 질문 비용을 0으로 바꾸면 안 된다.** 검색 임베딩은 호출됐을 수 있고, 현재 해당 비용은 미계측이다. 공통 receipt 연결 전까지 단계 범위를 명시해야 한다.

### RR-06 · P2 · 새 부분합 필드가 기존 Markdown 비용 리포트에 전달되지 않음

- 위치: `api/scripts/run_eval.py:270`, `api/scripts/run_eval.py:277`.
- aggregate가 `cost_usd_total=null`, `cost_usd_known_total`, 관측 건수/상태를 반환하지만 Markdown labels에는 이전 total 필드만 있다. null 항목은 출력하지 않는다.
- 따라서 부분 원가가 있는 실행에서 알려진 비용도 누락 이유도 Markdown 표에 표시되지 않는다. JSON에는 남지만 두 출력의 정보가 달라진다.
- 원가 계획 §6의 부분합·미확정 보고를 충족하지 않는다. 기존 출력 소비자까지 함께 검증하지 않은 연결 누락이며 정적 코드로 확인했다.
- 수정 방향: known subtotal, missing count, 관측 범위, UNKNOWN 이유를 CLI/Markdown에 명시하고 partial 보고서 golden test를 추가한다. W 선행 없이 가능한 R 작업이다.

## 일반적인 제품 기능과 다른 제한 — 즉시 결함과 구분

1. **RAW 전체 거절·규격 없는 사실 전체 거절:** 현 W 계약에서 승인 RAW와 NOT_APPLICABLE을 증명할 수 없어 보수적으로 거절하는 방향은 이해된다. 다만 영업시간·보관 위치·공통 주의까지 처리하는 일반 질문 엔진은 아니다. 계획의 RAW/규격 적용 범위 인수는 남아 있다.
2. **선택한 사실을 모두 한 entity로 제한:** 명시적인 entity 간 dependency를 지원하는 계획보다 좁다. 현재 schema 미지원 사항으로 문서화되어 있으며 연결 전에 해소해야 한다.
3. **W/R revision 타입 불일치:** AnswerPlan은 string, snapshot은 int이고 consumer가 str로 임시 비교한다. 최초 동결 전의 단계적 변경 자체를 버전 위반으로 단정하지 않는다. 하지만 양쪽 타입 동결·생산자/소비자 동시 인수가 끝난 상태는 아니다.
4. **전체 snapshot 재직렬화·전체 그래프 순회:** 현재 함수는 매번 전체 manifest를 받아 검사한다. 작은 fixture에는 적합하지만 계획 §3.4의 승인 색인 조회 경로를 구현한 것은 아니다. 성능 문제를 실측한 것은 아니며 인증/캐시된 manifest 검증과 요청별 선택 검증을 분리할 필요가 있다.
5. **인증 체계가 아직 둘:** CurrentStoreId를 쓰는 경로는 DB membership을 검사하지만 ApiClaims만 쓰는 일부 기존 경로까지 이번 변경이 보강한 것은 아니다. “모든 API 회원 회수 보장”으로 확대 해석하면 안 된다. 기존 설계의 잔여 위험이며 이번 변경에서 새로 생긴 우회로라고 주장하지 않는다.
6. **W 산출물 대기는 일부만 정당화:** durable usage·RAW·publication/M0/M1의 실제 통합 대기는 계획 선행에 맞는다. 토큰 발급기 회귀, report 소비자, validator의 지원 범위/거절 정책은 R 자체 수정이 가능하다. 전체 잔여 작업이 W 때문에 막혔다고 표현하면 부정확하다.

## 계획에 맞는 변경

`/reg` 인증 필수와 JWT 매장 내 slug 대조, 공개 version 본문 조회, action 배타성,
immutable tuple, bigint decimal string, 모델 파싱 실패 뒤 usage 보존, null/부분합 분리 방향,
nearest-rank p95 수정은 계획에 부합한다. 이번 리뷰에서 뒤집을 이유를 발견하지 않았다.

## 재현과 검증 한계

- `api`에서 requirements가 설치된 Python으로 `python -B scripts/audit_c0_r_implementation.py`.
- 5개 probe는 발견을 출력하는 진단 도구다. exit 0은 진단 실행 완료이지 제품 합격이 아니다.
- 반례는 현재 작업 디렉터리에서 실행했다. 제품 코드 변경이 없으므로 기존 전체 pytest를 이번 검토에서 반복하지 않았다. 이전 169 passed는 그대로 이전 실행 기록이다.
- DB·LLM·네트워크 호출은 하지 않았다. token mint DB도 fake이며 token 문자열을 출력하지 않았다.
- 실제 PostgreSQL/경합/운영 비용/지연/프론트 인수는 여전히 미검증이다.

수정 순서: RR-01 발급 호환성 → RR-02/03 선택 검증 경계 → RR-04/05 비용 정밀도·상태 → RR-06 출력 연결. W 계약과 맞물리는 부분은 독립 수정과 통합 인수를 구분한다.

## R 자체 수정 결과

| 항목 | 수정 | 검증 |
|---|---|---|
| RR-01 | 개발·team 발급기에 설정의 jwt_expire_minutes 기준 UTC exp 추가. 검증기의 exp 필수 정책 유지 | 실제 mint→get_claims 왕복에서 OWNER/team 모두 통과, 기존 exp 누락/만료 거절 유지 |
| RR-02 | 질문 predicate에 해당하는 선택 사실과 그 transitive requires 집합만 허용 | 관계 없는 추가 블록 거절, 같은 블록을 실제 선행 사실로 연결하면 허용 |

| RR-06 | CLI/Markdown에 부분합·누락 건수·관측 상태·범위·UNKNOWN 표시 | partial 보고서 출력과 JSON 직렬화 검증 |

비용 저장은 W의 공통 receipt 원장을 새로 만드는 방식이 아니다. 기존 `evaluation_runs.metrics` JSON 보고서의
`answer_cost_details`(`r_answer_cost/v1`)에 case_id별 반올림 전 decimal string과 답변 호출 상태를 보존한다.
기존 `evaluation_results.cost_usd NUMERIC(12,6)`은 표시 정밀도를 유지하고, repository가 같은 store/run의 해당 case 보고서 항목으로 읽기 값을 복원한다.
SQL은 문항마다 전체 보고서를 반복 전송하지 않고 그 case 항목만 선택한다. 결과와 보고서는 기존 동일 트랜잭션에서 저장되며 종료 run freeze를 변경하지 않았다.
과거 보고서가 없는 행은 기존 금액/UNKNOWN을 유지한다. 누락·오염된 새 보고서는 조용히 0이나 표시 금액으로 폴백하지 않는다.

비용 범위는 항상 `ANSWER_MODEL_ONLY`, 산정은 `ESTIMATED`이며 임베딩·Storage·미관측 재시도를 포함한 전체 질문 원가는 UNKNOWN이다.
공통 receipt 연결과 실제 요율 검증은 여전히 W와 합류 후 인수 대상이다.

최종 검증: **179 passed, 30 subtests passed**, Starlette/AnyIO deprecation warning 1건.
변경 application 파일 5개에서 매장 격리 정적 검사 위반 0건, `git diff --check` 통과.
