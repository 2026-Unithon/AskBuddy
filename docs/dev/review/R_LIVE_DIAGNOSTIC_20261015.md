## 2. 막은 지점 — `not_applicable_fact_ids`

서버 검사(`app/learn/general_semantics.py:226-229`):

```python
null_variants={f.fact_revision_id for f in facts if (f.variant.temperature,f.variant.size)==(None,None)}
if set(query.not_applicable_fact_ids)!=null_variants: raise ValueError('null variant is not automatically not-applicable')
```

요구하는 값은 **"고른 사실 중 규격(온도·사이즈)이 비어 있는 것 전부"** 다.
모델이 보낸 값은 **"질문에 해당하지 않는 사실"**(쉬운·복합 모두 `["2"]`=R02)이었다.

| | 서버가 요구한 값 | 모델이 보낸 값 |
|---|---|---|
| 쉬운 | `{"1"}` (고른 R01 자신) | `["2"]` |
| 복합 | `{"1","3"}` (고른 R01·R03) | `["2"]` |

**모델을 탓할 근거가 약하다.** 이 필드만 `Field(default=())` 로 **description 이 없다**
(같은 클래스의 다른 필드는 긴 설명을 달고 있다). 이름은 "적용되지 않는 사실" 인데
요구하는 내용은 "고른 사실 중 규격이 비어 있는 것" 이다. 환불 규칙처럼 **규격 개념이
아예 없는 지식**에서는 고른 사실 전부를 여기 적어야 해서 이름과 가장 크게 어긋난다.

코드 주석은 의도를 이렇게 적어 두었다 — "null variant 가 곧 not-applicable 은 아니다.
명시적인 적용 주장을 받아 별도 의미 검증을 거치게 한다." 의도는 타당하지만 **그 의도가
모델에게 전달되는 경로가 없다.**

## 3. 두 번째로 보이는 것 — W 조립 구조와의 상호작용

이번 fixture 에서 W 는 사실 26개를 **카테고리당 카드 1장·블록 1개**로 묶었다.

```
card 1 "환불"  block b1(QUANTITIES)  facts = [R01, R02, R03, R04]
card 2 "오픈"  block b1               facts = [S01, S02]
```

선택 단위는 블록이 아니라 사실이라 계약상 문제는 없다(부분 선택 허용). 다만 한 블록에
서로 다른 규칙 4개가 같이 있으니 모델이 **형제 사실을 "not applicable" 로 표시하고
싶어지는 유인**이 생긴다. 실제로 두 번 다 R02 를 그렇게 적었다. 이 fixture 는 평가용
합성 조립이므로 실제 추출기의 카드 분할과는 다르다 — 그대로 일반화하지 않는다.

## 4. 세 번째 — 원가 원장 (초판의 판단을 정정한다)

**초판에서 "모델명이 비어 있어 단가를 못 붙인다" 고 적은 것은 틀렸다.** `ai_usage_attempts`
에는 `model` 컬럼이 없고 `requested_model`·`reported_model` 이 있는데, 초판은 없는 이름을
읽고 `None` 을 본 것이다. 실제 기록은 이렇다.

```
requested_model=gemini-3.6-flash  reported_model=gemini-3.6-flash  price_status=PRICED
known_cost_usd=0.0110055  cost_usd=null  missing_reason='추가 공급자 usage의 과금 포함 관계 확인 필요'
```

즉 **원장은 모델도 단가도 제대로 적는다.** `cost_usd`(확정 총액)만 비워 두고 그 이유를
남긴다 — 캐시·도구 사용 같은 추가 usage 항목의 과금 포함 여부가 확인되지 않았기 때문이다.
D21 의 "미관측은 UNKNOWN" 을 지키는 동작이지 결함이 아니다.

검산: 원장 `known_cost_usd` 합계가 손계산과 1e-5 안에서 일치한다(§10).

### 8-1. 쉬운 질문의 새 벽 — `variants=[[null,null]]`

모델이 `variants: [[null, null]]` 을 보냈다. 서버는 `target_variants`(SPECIFIC 사실의 규격
모음)와 `query.variants` 가 같기를 요구하는데(`answer_validation.py:194`), 고른 사실이
규격 무관이라 `target_variants` 는 빈 집합이다 → `set() != {(None,None)}` → 거절.

즉 **규격이 없는 사실만 고를 때는 `variants=[]` 여야 하고 `[[null,null]]` 은 안 된다.**
프롬프트는 RAW 전용 경우에만 `variants=[]` 를 지시하고, 규격 없는 typed 사실에 대해서는
말하지 않는다. 1차에서는 모델이 우연히 `[]` 를 보냈다(같은 모델·같은 질문에서 실행마다
갈렸다 — 안정성 관찰로도 기록해 둔다).

### 8-2. 복합 질문의 새 벽 — 산문 속 조건 vs `obligations`

모델이 선택한 두 사실의 **본문 전체를 조건으로** 적어 보냈다. 서버는 `obligations` 가
사실의 구조화된 `conditions`/`exceptions` 와 **정확히 같기**를 요구하는데
(`general_semantics.py:234-236`), 이 fixture 의 사실 4개는 전부 `conditions=[]`·`exceptions=[]`
다 — 조건이 전부 `original_assertion` 산문 안에 들어 있다.

이는 **평가 fixture 의 성질**이다. P3 가 "복합 문장을 임의로 원자화하거나 조건을 추정하지
않았다" 고 적은 대로, 규칙 한 줄을 통째로 한 사실로 뒀다. 실제 W 추출기는 `conditions` 를
채우므로 이 실패가 운영에서 같은 모양으로 날지는 **이 실행으로 알 수 없다.** 다만
"조건이 산문에만 있는 사실" 이 들어오면 모델이 조건을 읽어 보고하는 쪽이 자연스럽고,
그때마다 `invented` 로 거절된다는 것은 확인됐다.

## 9. 3차 — `variants` 표기 정규화 뒤 (같은 날)

§8-4 의 1번을 적용했다. `Interpretation` 이 `variants` 에서 `[null,null]` 쌍을 떨군다.
그 쌍은 "규격 축이 없다" 는 뜻이라 어떤 SPECIFIC 사실과도 짝지어지지 않아 **빈 목록과
의미가 같은데**, `answer_validation.py:194` 의 비교는 둘을 다르게 봤다.

**결과: 쉬운 질문이 끝까지 통과했다. 첫 실제 유료 답변이다.**

## 11. 4차 — 복합 질문: fixture 성질인가 계약 취약인가

§8-2 가 남긴 질문에 답했다. **같은 질문·같은 본문**에 조건만 구조화한 대조본을 만들어
돌렸다(`challenge-hard-structured.json`, `build_r_diagnostic_challenge.py --fact-patch`).
본문(`assertion`)은 한 글자도 바꾸지 않고 `conditions` 만 채웠다.

```
R01  conditions = ["배달앱으로 결제한 건일 때"]
R03  conditions = ["2만원을 초과한 결제일 때", "이전 영업일에 결제한 건일 때"]
R04  conditions = ["이미 환불이 완료된 거래일 때"]
```

**답: fixture 성질이었다.** `condition/exception omitted or invented` 벽은 사라졌다.
모델이 보낸 obligations 3건이 고른 두 사실의 구조화 조건과 정확히 일치했고, 각 조건에
사용자 원문 인용까지 붙었다.

### 11-1. 그 다음 벽 — 한 답변은 predicate 하나다

이번에는 `AnswerReferenceError: INVALID_REFERENCE` 에서 멈췄다. 원인은 모델 제안의
모양이다.

| 모델이 보낸 것 | |
|---|---|
| `parts` | **0개** |
| `interpretation.predicate` | `rule_R01` 하나 |
| 고른 사실 | `1`(rule_R01) · `3`(rule_R03) |

`answer_validation.py:154` 는 `targets` 를 **질의 predicate 와 같은 사실**로만 잡고,
`:165` 에서 `targets` 의 선행(`requires`) closure 가 고른 사실 전체와 같아야 한다고 본다.
`rule_R03` 은 `rule_R01` 의 선행이 아니므로 closure 에 들어오지 않는다 → 거절.

즉 **답변 하나는 "대상 1 + predicate 1 + 선행 closure" 다.** 서로 다른 규칙을 함께
답하려면 계약상 `parts` 로 나눠야 한다.

### 11-2. 이번 것은 우리 잘못이 아니다

앞선 두 벽(§2 · §8-1)은 **명세가 모델에게 전달되지 않은** 문제였다. 이번은 다르다 —
`prompts/r_general_proposal.txt` 는 같은 지시를 **세 군데**에 적어 두었다.

- 6행 "서로 다른 대상이나 속성을 묻는 복합 질문은 parts 최대 8개로 분해할 수 있다"
- 8행 "동일 entity 내에서도 predicate/variant/조건이 다른 typed 사실은 … 분리한다"
- 32행 "서로 다른 대상·속성은 parts로 분리한다"

**명시적이고 반복된 지시를 모델이 따르지 않았다.** 이번 진단에서 처음 나온 순수
모델 품질 신호다. 그래서 프롬프트를 더 손대지 않았다 — 표본 1건으로 문구를 덧붙이면
그 한 건에만 맞추는 짓이 된다. 반복 실행으로 빈도를 보고 나서 정할 일이다.

## 13. 5·6차 — 지연 분해와 countTokens 왕복 제거 (2026-10-18)

### 13-1. 성공 턴의 시간은 거의 전부 모델이다

3차 성공 턴(16,934 ms)을 분해했다.

| 구간 | 시간 |
|---|---|
| `proposal_ms` | 6,113 ms (그중 generate 3,226) |
| `verification_ms` | 10,616 ms (그중 generate 8,305) |
| 검색·저장·렌더 | **~200 ms** |

둘을 합치면 전체의 **98.8%**다. 서버 쪽 코드가 느린 게 아니다. 그런데 **generate 밖에서
5.2초**가 사라졌다 — 단계마다 `countTokens` 가 생성과 **별개의 왕복**을 한다
(제안 2,887 ms · 검증 2,311 ms).

### 13-2. 고친 것 — 같은 한도를 더 싸게 지킨다

토큰 하나는 최소 1바이트를 먹으므로 **바이트 수가 토큰 수의 상한**이다. 바이트로 센
상한이 같은 여유분(10%, 최소 32)까지 두고도 한도 안이면 정확한 수를 물어볼 이유가
없다 — 어떤 값이 나와도 한도를 넘을 수 없다. **한도에 가까울 때만** 공급자에게 묻는다.
한도를 푼 게 아니고, 응답 뒤 실제 사용량 재검사도 그대로다.

### 13-3. 실측 — 적용된 곳에서는 효과가 분명하다

| | 3차(변경 전) | 6차(변경 후) |
|---|---|---|
| `proposal_ms` | 6,113 ms | **4,169 ms** |
| └ 그중 generate | 3,226 ms | 3,258 ms |
| `countTokens` 왕복 | 2회 | **1회** |
| `verification_ms` | 10,616 ms | 13,912 ms |
| └ 그중 generate | 8,305 ms | **12,852 ms** |
| 턴 전체 | 16,934 ms | **18,169 ms** |

- 제안 단계가 **1,944 ms 줄었다.** generate 시간은 그대로(3,226→3,258)이므로 줄어든
  만큼이 통째로 없어진 왕복이다.
- 검증 단계는 **여전히 묻는다.** 그 프롬프트(14,529 토큰)는 바이트 상한이 60k 토큰
  한도에 가까워 보수적으로 정확한 수를 확인한다 — 가드가 제 일을 한 것이다.
- **그런데 턴 전체는 더 느려졌다.** 검증 generate 가 8,305 → 12,852 ms 로 튀었기
  때문이다. 내 변경과 무관한 **모델 변동**이다.

**표본이 조건당 1건이라 턴 수준 개선을 주장할 수 없다.** 주장할 수 있는 것은
"왕복 하나가 없어졌고 그 단계가 1.9초 줄었다" 까지다.

### 13-4. p95 에 관해 이번에 실제로 배운 것

같은 검증 프롬프트의 generate 지연을 세 번 관측했다: **8,305 / 8,778 / 12,852 ms.**
범위가 4.5초, 최솟값 대비 55% 변동이다.

- **검증 단계 하나만으로 운영 목표 p95 5초를 넘는다.** 서버 최적화로 닿을 거리가 아니다.
- 지배항은 모델 호출 지연이고 **변동이 크다.** 평균을 줄이는 것보다 변동을 다루는
  설계(단계적 응답·타임아웃 정책·역할별 모델)가 필요하다. Phase E 의 역할별 모델
  전환과 같은 문제다.
- 검증을 빼는 것은 선택지가 아니다. `verdict.supported` 와 `candidate_coverage` 는
  제안 모델의 자기 오류를 잡는 독립 검사이고, D12 의 "서버 검증·렌더링" 이 여기 걸려 있다.

### 13-5. 덤으로 나온 것 — 검증 출력 상한이 빠듯하다

5차는 `IncompleteModelOutput: generation did not finish with STOP` 으로 실패했다.
검증 출력이 **1,981 토큰**으로 계획의 `max_output_tokens_per_call=2000` 에 닿아 잘렸다
(3차엔 1,745 로 87%). 제품 결함이 아니라 **내가 잡은 계획값이 빠듯했던 것**이다.
6차는 4,000 으로 올려 통과했다(최악의 호출 1회 84원 ≤ 예산 400원). 앞으로 유료 계획의
검증 출력 상한은 **4,000 이상**으로 잡는다.
