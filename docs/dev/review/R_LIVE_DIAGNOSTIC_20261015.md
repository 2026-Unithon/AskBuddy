## 2. 막은 지점 — `not_applicable_fact_ids`

서버 검사(`app/learn/general_semantics.py:226-229`):

```python
null_variants={f.fact_revision_id for f in facts if (f.variant.temperature,f.variant.size)==(None,None)}
if set(query.not_applicable_fact_ids)!=null_variants: raise ValueError('null variant is not automatically not-applicable')
```

요구하는 값은 **"고른 사실 중 규격(온도·사이즈)이 비어 있는 것 전부"** 다.
모델이 보낸 값은 **"질문에 해당하지 않는 사실"**(쉬운·복합 모두 `["2"]`=R02)이었다.

| | 서버가 요구한 값 | 모델이 보낸 값 |
|---|---|---|
| 쉬운 | `{"1"}` (고른 R01 자신) | `["2"]` |
| 복합 | `{"1","3"}` (고른 R01·R03) | `["2"]` |

**모델을 탓할 근거가 약하다.** 이 필드만 `Field(default=())` 로 **description 이 없다**
(같은 클래스의 다른 필드는 긴 설명을 달고 있다). 이름은 "적용되지 않는 사실" 인데
요구하는 내용은 "고른 사실 중 규격이 비어 있는 것" 이다. 환불 규칙처럼 **규격 개념이
아예 없는 지식**에서는 고른 사실 전부를 여기 적어야 해서 이름과 가장 크게 어긋난다.

코드 주석은 의도를 이렇게 적어 두었다 — "null variant 가 곧 not-applicable 은 아니다.
명시적인 적용 주장을 받아 별도 의미 검증을 거치게 한다." 의도는 타당하지만 **그 의도가
모델에게 전달되는 경로가 없다.**

## 3. 두 번째로 보이는 것 — W 조립 구조와의 상호작용

이번 fixture 에서 W 는 사실 26개를 **카테고리당 카드 1장·블록 1개**로 묶었다.

```
card 1 "환불"  block b1(QUANTITIES)  facts = [R01, R02, R03, R04]
card 2 "오픈"  block b1               facts = [S01, S02]
```

선택 단위는 블록이 아니라 사실이라 계약상 문제는 없다(부분 선택 허용). 다만 한 블록에
서로 다른 규칙 4개가 같이 있으니 모델이 **형제 사실을 "not applicable" 로 표시하고
싶어지는 유인**이 생긴다. 실제로 두 번 다 R02 를 그렇게 적었다. 이 fixture 는 평가용
합성 조립이므로 실제 추출기의 카드 분할과는 다르다 — 그대로 일반화하지 않는다.

## 4. 세 번째 — 원가 원장 (초판의 판단을 정정한다)

**초판에서 "모델명이 비어 있어 단가를 못 붙인다" 고 적은 것은 틀렸다.** `ai_usage_attempts`
에는 `model` 컬럼이 없고 `requested_model`·`reported_model` 이 있는데, 초판은 없는 이름을
읽고 `None` 을 본 것이다. 실제 기록은 이렇다.

```
requested_model=gemini-3.6-flash  reported_model=gemini-3.6-flash  price_status=PRICED
known_cost_usd=0.0110055  cost_usd=null  missing_reason='추가 공급자 usage의 과금 포함 관계 확인 필요'
```

즉 **원장은 모델도 단가도 제대로 적는다.** `cost_usd`(확정 총액)만 비워 두고 그 이유를
남긴다 — 캐시·도구 사용 같은 추가 usage 항목의 과금 포함 여부가 확인되지 않았기 때문이다.
D21 의 "미관측은 UNKNOWN" 을 지키는 동작이지 결함이 아니다.

검산: 원장 `known_cost_usd` 합계가 손계산과 1e-5 안에서 일치한다(§10).

### 8-1. 쉬운 질문의 새 벽 — `variants=[[null,null]]`

모델이 `variants: [[null, null]]` 을 보냈다. 서버는 `target_variants`(SPECIFIC 사실의 규격
모음)와 `query.variants` 가 같기를 요구하는데(`answer_validation.py:194`), 고른 사실이
규격 무관이라 `target_variants` 는 빈 집합이다 → `set() != {(None,None)}` → 거절.

즉 **규격이 없는 사실만 고를 때는 `variants=[]` 여야 하고 `[[null,null]]` 은 안 된다.**
프롬프트는 RAW 전용 경우에만 `variants=[]` 를 지시하고, 규격 없는 typed 사실에 대해서는
말하지 않는다. 1차에서는 모델이 우연히 `[]` 를 보냈다(같은 모델·같은 질문에서 실행마다
갈렸다 — 안정성 관찰로도 기록해 둔다).

### 8-2. 복합 질문의 새 벽 — 산문 속 조건 vs `obligations`

모델이 선택한 두 사실의 **본문 전체를 조건으로** 적어 보냈다. 서버는 `obligations` 가
사실의 구조화된 `conditions`/`exceptions` 와 **정확히 같기**를 요구하는데
(`general_semantics.py:234-236`), 이 fixture 의 사실 4개는 전부 `conditions=[]`·`exceptions=[]`
다 — 조건이 전부 `original_assertion` 산문 안에 들어 있다.

이는 **평가 fixture 의 성질**이다. P3 가 "복합 문장을 임의로 원자화하거나 조건을 추정하지
않았다" 고 적은 대로, 규칙 한 줄을 통째로 한 사실로 뒀다. 실제 W 추출기는 `conditions` 를
채우므로 이 실패가 운영에서 같은 모양으로 날지는 **이 실행으로 알 수 없다.** 다만
"조건이 산문에만 있는 사실" 이 들어오면 모델이 조건을 읽어 보고하는 쪽이 자연스럽고,
그때마다 `invented` 로 거절된다는 것은 확인됐다.

## 9. 3차 — `variants` 표기 정규화 뒤 (같은 날)

§8-4 의 1번을 적용했다. `Interpretation` 이 `variants` 에서 `[null,null]` 쌍을 떨군다.
그 쌍은 "규격 축이 없다" 는 뜻이라 어떤 SPECIFIC 사실과도 짝지어지지 않아 **빈 목록과
의미가 같은데**, `answer_validation.py:194` 의 비교는 둘을 다르게 봤다.

**결과: 쉬운 질문이 끝까지 통과했다. 첫 실제 유료 답변이다.**
