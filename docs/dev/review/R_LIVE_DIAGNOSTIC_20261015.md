## 1. 결과 한 줄

**두 질문 모두 답변에 이르지 못했다 — 같은 한 곳에서 막혔다.** 검색과 사실 선택은
거의 정확했고, 막은 것은 모델의 지식 오류가 아니라 **제안 계약의 한 필드**다.

|---|---|---|---|
| 쉬운 `E01` "배달앱으로 결제한 손님 환불은 어디서 해?" | ANSWER(R01) | **503 `GENERAL_INVALID_PROPOSAL`** | R01 **정확히 1개** (정답) |

## 2. 막은 지점 — `not_applicable_fact_ids`

서버 검사(`app/learn/general_semantics.py:226-229`):

```python
null_variants={f.fact_revision_id for f in facts if (f.variant.temperature,f.variant.size)==(None,None)}
if set(query.not_applicable_fact_ids)!=null_variants: raise ValueError('null variant is not automatically not-applicable')
```

요구하는 값은 **"고른 사실 중 규격(온도·사이즈)이 비어 있는 것 전부"** 다.
모델이 보낸 값은 **"질문에 해당하지 않는 사실"**(쉬운·복합 모두 `["2"]`=R02)이었다.

| | 서버가 요구한 값 | 모델이 보낸 값 |
|---|---|---|
| 쉬운 | `{"1"}` (고른 R01 자신) | `["2"]` |
| 복합 | `{"1","3"}` (고른 R01·R03) | `["2"]` |

**모델을 탓할 근거가 약하다.** 이 필드만 `Field(default=())` 로 **description 이 없다**
(같은 클래스의 다른 필드는 긴 설명을 달고 있다). 이름은 "적용되지 않는 사실" 인데
요구하는 내용은 "고른 사실 중 규격이 비어 있는 것" 이다. 환불 규칙처럼 **규격 개념이
아예 없는 지식**에서는 고른 사실 전부를 여기 적어야 해서 이름과 가장 크게 어긋난다.

코드 주석은 의도를 이렇게 적어 두었다 — "null variant 가 곧 not-applicable 은 아니다.
명시적인 적용 주장을 받아 별도 의미 검증을 거치게 한다." 의도는 타당하지만 **그 의도가
모델에게 전달되는 경로가 없다.**

## 3. 두 번째로 보이는 것 — W 조립 구조와의 상호작용

이번 fixture 에서 W 는 사실 26개를 **카테고리당 카드 1장·블록 1개**로 묶었다.

```
card 1 "환불"  block b1(QUANTITIES)  facts = [R01, R02, R03, R04]
card 2 "오픈"  block b1               facts = [S01, S02]
```

선택 단위는 블록이 아니라 사실이라 계약상 문제는 없다(부분 선택 허용). 다만 한 블록에
서로 다른 규칙 4개가 같이 있으니 모델이 **형제 사실을 "not applicable" 로 표시하고
싶어지는 유인**이 생긴다. 실제로 두 번 다 R02 를 그렇게 적었다. 이 fixture 는 평가용
합성 조립이므로 실제 추출기의 카드 분할과는 다르다 — 그대로 일반화하지 않는다.

## 4. 세 번째 — 원가가 원장에 안 남는다

유료 호출 3건 모두 평가 usage 원장에 이렇게 적혔다.

```
stage=ANSWER  model=None  cost_usd=None  rate_card_version=2026-10-06-gemini  cost_purpose=EVALUATION
```

토큰 수는 남지만 **모델명이 비어 있어 단가를 붙이지 못하고 `cost_usd` 가 null** 이다.
요율표에는 `gemini-3.6-flash` 가 실단가로 있는데도 그렇다. D21 원가 집계가 이 경로에서
비어 있다는 뜻이다. 이번 실행의 비용은 아래처럼 **손으로** 계산했다.

## 6. 이번 실행이 드러낸 배선 결함 (고쳐서 다시 돌렸다)

유료 경로를 처음 돌려서 나온 것들이다. 합성 실행에서는 전부 보이지 않았다.

| # | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1 | 첫 유료 실행이 양성 대조 0번째 턴에서 `503 MODEL_UNAVAILABLE` | 러너가 **채점 매장**으로 평가 usage 범위를 열어 두는데 대조는 **다른 매장**에서 돈다 → `request_usage_sink` 가 `evaluation request store mismatch` 로 거절, 일반 `except` 가 MODEL_UNAVAILABLE 로 덮음 | 대조 동안만 같은 `evaluation_run_id` 로 대조 매장 범위를 덮어씀 |
| 2 | 그 503 의 원인을 알 수 없었다 | 대조 실패가 `raise_for_status()` 로 상태 코드만 던짐 | 서버 오류 본문을 예외 메시지에 실음 |
| 3 | `GENERAL_INVALID_PROPOSAL` 의 사유가 어디에도 안 남음 | `ValueError/KeyError/StopIteration` 를 사유 없이 ApiError 로 변환 | 코드가 쓴 상수 문구만 `logger.warning('general_proposal_rejected detail=…')` 로 기록. 계약 위반은 **위치·종류만** 남기고 입력값은 싣지 않는다 |
| 4 | 질문 1개짜리 진단을 등록하려면 반복 3회·대조 3회를 거짓으로 적어야 했다 | 사전등록이 캠페인 모양만 허용 | `run_kind=CAMPAIGN\|DIAGNOSTIC` 추가. 진단은 반복 하한 없음·대표 개선량 금지, `check_campaign` 은 진단을 `DIAGNOSTIC_NOT_A_CAMPAIGN` 으로 거절 |
| 5 | 예산 계획이 `BudgetPolicy` 에 안 맞아 첫 시도가 멈춤(유료 호출 0) | 금액이 문자열이어야 하고 `max_prompt_bytes ≤ 200000`, **최악의 호출 1회가 예산 안에 들어가야** 함 | 계획값 조정(호출당 상한 60k/2k 토큰, 예산 400원) |

1~3 이 없었으면 이번 분석은 "503 이 났다" 에서 끝났다.

## 7. 다음에 할 것 (제안, 아직 안 함)

1. **`not_applicable_fact_ids` 를 모델이 맞출 수 있게 만든다.** 두 갈래 중 선택이 필요하다.
   - (a) 필드에 description 을 달고 프롬프트에 규칙을 적는다 — 가장 싸다. 이름이 여전히
     오해를 부르므로 설명이 길어진다.
   - (b) **서버가 계산한다.** 고른 사실의 규격이 비어 있는지는 서버가 snapshot 으로 이미
     안다. 모델에게 물을 필요가 없다. 다만 코드 주석이 밝힌 "명시적 적용 주장" 의도를
     버리게 되므로, 그 의도를 **별도 필드**(예: 규격 없는 사실을 이 질문에 적용해도 되는가)
     로 옮길지 함께 정해야 한다.
2. 고친 뒤 **같은 두 질문을 다시** 돌려 어디까지 가는지 본다(검증 단계까지 가는지).
   비용은 회당 약 17원이다.
3. 원장 `model`·`cost_usd` 공백을 메운다 — 안 하면 유료 평가를 늘려도 D21 원가가 안 쌓인다.
4. 복합 질문의 **R04 누락**은 계약 문제를 고친 뒤 다시 봐야 판단할 수 있다. 지금은
   제안이 검증까지 가지 못해 "필수 사실 회수 실패" 인지 "선택 누락" 인지 구분되지 않는다.
