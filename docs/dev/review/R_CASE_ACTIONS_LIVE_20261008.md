## 턴별 관찰

1. **A 결제 미확인/B 환불 승인 대기의 인계:** 중간 제안에는 A의 원결제 상태 확인 요청, B의 점주 승인 확인 등 사건별 조치가 작성됐다. 그러나 모델이 사건별로 parts를 두 개 만들고 각 `interpretation.entity_id=8`(인수인계)에 결제(6)/환불(1) RAW까지 넣어 서버의 단일 해석 대상 범위 검사에서 `INVALID_REFERENCE`로 거절됐다. 공개 오류는 `GENERAL_INVALID_PROPOSAL`. 승인 참조 ID 자체가 사라졌거나 후보가 검색되지 않은 오류는 아니다. 검증 모델까지 도달하지 않았으므로 새 사건별 검증의 효과나 해당 제안의 의미 정확성이 확인된 것은 아니다. 사용자에게 최종 답변도 제공되지 않았다.
2. **“그 건은 읽었대. 인계 완료로 해도 돼?”:** 앞선 오류의 사용자 원문이 제품의 문맥 복구 경로를 통해 전달됐고, 모델/검증기가 `A는 결제 상태 미확인`, `B는 환불 승인 대기` 선택지를 반환했다. 필요한 재질문으로 인정한다. 다만 읽음만으로 완료가 아니라는 공통 규칙 안내는 함께 표시하지 않아 원래 grading_checks를 모두 충족한 것은 아니다.
3. **실제 A 선택:** 사전 별칭과 실제 설명형 선택지의 유일 매칭은 성공했다. 러너가 `option="A는 결제 상태 미확인"`, `question="A"`로 전송해 두 값이 같아야 하는 실제 `ChatRequest` 계약에서 **422 INVALID_CONTRACT**로 거절됐다. 이 턴에는 모델 호출이 없었고 모델 오답으로 세지 않는다. 이전 실행의 미실행과 달리 이번에는 실제 요청이 나갔다.

직전 전체 6턴과 이번 3턴을 직접 비교하지 않는다. 같은 OD06에서 공통 필드 답변→사건별 조치를 포함한 중간 제안, 미실행→422 요청까지의 변화는 관찰됐으나 최종 사용자 해결은 여전히 없다.

## 실행 후 평가 러너 수정

실제 결과를 보존한 뒤 선택 후속의 question도 반환된 실제 option과 같게 보내도록 수정했다. 사전의 `A`는 expected/choice_resolution에 계속 남는다. 전송 전에는 제품의 실제 `ChatRequest.model_validate`를 호출해 API 입력 계약을 검사한다. 분석기도 설명형 별칭으로 확장된 질문을 연결하도록 보완했다.

기존 합성 HTTP 테스트가 question/option 불일치를 허용했던 것이 이번 버그를 놓친 원인이다. 실제 DTO를 거치도록 변경하고, 기존 잘못된 요청의 거절·수정된 설명형 선택의 통과·모호한 선택 미전송을 확인했다. 관련 **29 tests 통과**(`api/tmp/r-case-actions-live-harness-02.log`). 첫 검증에서 실제 계약에 맞지 않는 합성 세션 ID/짧은 요청 ID도 드러나 fixture를 수정했다. 제품의 검사를 완화하지 않았다.

이후 **유료 재호출은 하지 않았다.** 이번 보고서는 수정 전 실행 결과다. 런타임 의미 검사와 프롬프트는 실행 도중/이후 변경하지 않았으며 직전 v9 검증 기록(전체 1,892 tests·PG17 통합 통과)은 별도다.

다음 우선순위는 **사건별 결론과 업무 entity별 검증 단위의 구분**이다. parts는 근거의 해석 범위별로 검증하고 A/B 결론은 검증된 여러 근거를 조합해야 한다. 이를 모델 출력 계약·예제로 일치시키고 실제 실패 재생에서 잘못된 혼합은 계속 거절되는지 확인한다. 그다음 수정된 선택 요청으로 최종 후속 답변을 평가한다. 구조 제약을 느슨하게 바꾸거나 중간 제안을 성공 답변으로 재분류하지 않는다.
