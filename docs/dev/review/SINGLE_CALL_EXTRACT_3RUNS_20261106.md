## 추가 형식 — 사진·카톡 캡처·글자 PDF (2026-11-07)

제품이 받는데 시험이 없던 형식을 합성 자료로 채웠다(`rendered_cases.json`, `render_single_call_cases.py`). 사진은 책상 위 종이를 폰으로 찍은 모양(기울임·약한 원근·그림자·흐림·잡티·JPEG), 손글씨 메모는 글자 흔들기와 취소선 정정, 카톡 캡처는 말풍선 그림, 글자 PDF 는 크롬 인쇄(글자층 있음). 11건, 정답 사실 93개, 같은 조건 3회.

| 형식 | r1 | r2 | r3 |
|---|---|---|---|
| 사진 5건(공지·손글씨 메모·레시피 표·화이트보드·포스터) | 46/46 | 46/46 | 46/46 |
| 카톡 캡처 3건(번복·질문답변·잡담 섞임) | 11/11 | 11/11 | 11/11 |
| 글자 PDF 3건(근무 규칙 2쪽·레시피 표·오픈 매뉴얼) | 36/36 | **31/36** | 36/36 |

- 사실 93개 중 매번 성공 88, 매번 실패 0, 갈림 5.
- 갈림 5개는 전부 **r2 의 오픈 매뉴얼 한 건**이다 — 7단계 중 4단계까지 뽑고 사실 7개에서 멈췄다(미해결 메모도 없음). r1·r3 은 같은 문서에서 13~14개. **두 번째 조용한 조기 종료**다. 지금까지 129회 호출 중 2회(약 1.6%), 둘 다 자료 중간에서 끊겼다.
- 취소선 정정(우유 3개→4개)과 카톡 번복(3번→2번 냉장고)은 3회 모두 새 값을 현재 값으로 잡았다.
- 한계: 합성 사진은 실제 사진보다 깨끗하다(조명 반사·초점 흐림·접힘·실제 손글씨 없음). 사진 100% 를 실제 사진 성능으로 읽지 않는다.

## 판단 (S2 = 90%)
- **품질은 기준을 넘는다.** 3회 중앙값 98.6%, 조기 종료가 없는 실행(r2·r3)은 98.6~99.2%.
- **단, 조용한 조기 종료가 있다(추가 형식까지 129회 중 2회).** 막지 않으면 r1 처럼 자료 하나가 통째로 비고 그 실행 수치가 84.5% 로 떨어진다. 한 번 호출로 가려면 **끊김 검사가 필수 조건**이다.
- 갈리는 9개는 촘촘한 스캔에 몰려 있다. 사장님 승인 화면에서 원본과 함께 보여 주거나, 스캔만 두 번 뽑아 합치는 보강을 검토할 수 있다(비용 2배, 측정 전).

## 끊김 판단 기준 (사용자 지적 반영)

"사실 개수가 적으면 재시도" 는 정답 개수를 안다고 가정하므로 쓸 수 없다(새 자료의 정답은 모른다). 기준은 **입력이 처리됐는가** 다.

1. **사후 검사(비용 0)** — 원문 인용(`original_assertion`)이 입력 줄을 덮는 정도. 글 입력(docx·카톡·전사·사장님 글)만 계산된다.
   | | 덮은 비율 | 끝부분 연속 공백 |
   |---|---|---|
   | r1 끊긴 사례 | 3% | 24% (67줄 중 끝 16줄) |
   | 같은 사례 정상 실행 | 96% | 0% |
   | 카톡(정상) | 33~40% | 0~3% |
   | 그 외 정상 | 50~100% | 0% |
   - 덮은 비율만 보면 카톡(잡담 줄)을 오판한다. **끝부분 연속 공백**은 정상 실행이 전부 3% 이하라 끊김과 갈렸다.
   - 다만 관찰된 끊김이 **1건뿐**이라 기준선을 정할 근거가 부족하다. 6글자 겹침으로 세는 근사라 다듬은 인용은 덜 잡힌다(끊긴 사례의 공백이 24% 로 실제보다 작게 나온 이유). PDF 는 계산하지 못한다.
2. **구조 보장(추천)** — 입력에 줄·쪽 번호를 붙이고, 모든 번호에 대해 "사실 f…" 또는 "업무 내용 없음(인사·잡담)" 을 답하게 한다. **빠진 번호 = 처리 안 됨** → 그 지점부터 다시 호출한다. 정답도 기준선도 필요 없다. 출력이 조금 늘어난다. 제품의 줄 위치 표지(W1-4 `extract_locator_hints`) 위에 얹을 수 있다.
