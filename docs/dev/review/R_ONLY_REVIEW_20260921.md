# R 우선 구현 검토 — 2026-09-21

## 결론과 범위

사용자 요청에 따라 W 추출·조립·worker 수정은 이번 작업 대상에서 제외하고, R이 소유한 질문·답변·저장·상태 표시·인계 수신을 검토했다. 기준 제품 코드는 `7f0e461`이다. 앞선 전체 감사의 로컬 문서·재현 도구는 보존했다.

**R도 “단독으로 고칠 부분이 없다”고 판정할 수 없다. W 없이 재현되는 R 화면 결함 2건을 확인했다.** 서버의 권한·참조·문맥·멱등 저장 경로를 확인하고 관련 회귀를 실행했으며, 이번에 새로 확정한 결함은 아래 화면 연결 두 건이다. 이 결론이 다른 결함의 부재나 실자료 의미 정확도를 보증하지는 않는다.

근거 계획은 [MVP](../ASKBUDDY_MVP_CURRENT.md)의 답변/상태·새로고침·복원 계약, [전체 TODO](../DEV_TODO_CURRENT.md) R0~R5/J2, [R 구현 계획](../plan/R_IMPLEMENTATION_PLAN.md), [확정 범위·인계](../plan/R_SEQUENCE_HANDOFF_20260919.md)다. 프론트 검토에는 저장소의 web-async-state-check와 ui-state-walkthrough 절차를 참고했다.

## R 단독 수정 대상

### R-F01 — P2: 페이지 경계에서 새 답변과 명확화 선택지가 숨겨짐

- 위치: `api/app/learn/v2_router.py:230`의 history, `web/lib/query.ts:27`, `web/components/r-v2-chat.tsx:43` 및 `:66` 이후 선택 버튼 조건.
- history는 오래된 메시지부터 100개를 반환한다. 응답이 정확히 100개이면 실제 다음 행 유무와 관계없이 `next_after`를 반환한다.
- 질문 성공 후 화면은 이미 로드한 페이지를 invalidate/refetch한다. 방금 저장한 답변이 다음 페이지에 있으면 새 페이지를 자동 조회하지 않는다. 입력은 비워지지만 답변은 화면에 나타나지 않는다.
- 명확화/안전 확인 버튼도 `!history.hasNextPage`일 때만 표시한다. 정확히 100번째 메시지가 현재 마지막 CLARIFY여도 불필요한 다음 페이지 조회 전에는 선택지가 숨겨진다.

**브라우저 재현:** 실제 Next 화면에 API와 동일한 오름차순/100개 pagination을 합성 제공했다. 초기 100번째 CLARIFY의 HOT 선택 버튼 수는 0이었다. 새 질문을 제출하면 서버 대역에 102개가 저장되고 입력은 비워지지만 새 답변 표시 수는 0이었다. ‘다음 대화 기록 보기’를 누른 뒤에야 답변이 보였다.

영향은 데이터 삭제가 아니라 새 결과 접근 실패/지연이다. 대화가 길어지면 제출 성공과 눈에 보이는 결과가 어긋나며, 재제출을 유발할 수 있다.

**R 수정 방향:** 최신 메시지를 첫 진입에서 조회하고 과거를 더 불러오는 방식, 또는 최신 응답을 반드시 회수하는 별도 cursor/query 계약을 정한다. 이미 읽은 첫 페이지의 invalidate만으로 최신 조회를 대체하지 않는다. API는 `limit+1` 등으로 실제 다음 행 여부를 판정한다.

**완료 기준:** 99/100/101/200개 메시지에서 질문→ANSWER/CLARIFY/SAFE_ROUTE, 새로고침·재진입을 검증한다. 최신 응답·선택지가 추가 수동 페이지 이동 없이 보여야 하며 과거 페이지의 순서·중복·인용도 보존해야 한다. API pagination과 UI를 함께 고쳐야 한다.

### R-F02 — P2: 앞선 질문이 점주 답변 대기여도 뒤 질문이 완료되면 갱신 중단

- 위치: `web/lib/query.ts:32`의 `rHistoryQuery.refetchInterval`.
- 자동 조회 조건은 로드된 메시지의 `knowledge_status === PENDING` 또는 **마지막 메시지의 ESCALATE**다.
- 질문 A가 ESCALATE한 뒤 질문 B가 ANSWER로 끝나면, A는 여전히 점주 답변 대기지만 마지막 메시지가 달라져 조회가 멈춘다. 점주 답변은 아직 로드되지 않았으므로 그 답변의 PENDING 상태도 감지할 수 없다.

**브라우저 재현:** A=ESCALATE, B=ANSWER를 표시한 뒤 합성 서버에 A의 점주 답변을 추가했다. 설정된 5초 주기보다 긴 6.2초 동안 추가 history 요청은 0회, 점주 답변 표시는 0개였다. ‘새 답변 확인’을 누르면 즉시 나타났다. 실제 W worker 없이 R 화면·query 조건만으로 재현됐다.

**R 수정 방향:** 세션 내 미해결 pending/delivery 상태를 서버가 요약해 제공하고 이를 갱신 조건으로 사용한다. 화면에 로드된 마지막 메시지에서 세션 전체의 대기 상태를 추정하지 않는다. 과거 ESCALATE가 하나라도 있으면 무조건 영구 폴링하도록 바꾸는 것도 피한다. 완료·탈퇴·실패·종료 상태까지 구분해야 한다.

**완료 기준:** A 이관→B 답변→A 점주 답변 도착, 복수 pending, 앞 페이지의 pending, 전부 해결된 상태를 검증한다. 도착은 수동 새로고침 없이 표시하고 모든 대기 종료 후에는 불필요한 조회를 멈춘다.

### R-V01 — 검증 도구: 오류창 선택자가 Next 내부 알림과 충돌

- 위치: `api/scripts/verify_r_ui.cjs:153`의 `page.getByRole('alert').waitFor()`.
- 새 production build에서 기존 검증을 실행하면 앞의 17개 검사 후 이 지점에서 중단된다. 앱 오류창과 `#__next-route-announcer__`가 모두 alert로 잡혀 strict mode 오류가 난다. 단독 재실행에서도 같은 결과였다. Playwright는 CI 설정과 같은 1.62.1이고 로컬 브라우저는 Edge다.
- 제품의 오류 표시 실패와 구분한다. 원본 검증 파일은 그대로 두고, 임시 복사본에서 Next 내부 알림만 제외했을 때 **40개 기존 브라우저 검사 전부 통과**했다. 원격 CI의 과거 성공을 부정하거나 원본 로컬 스크립트까지 통과했다고 기록하지 않는다.
- R 단독으로 앱 컨테이너/오류 메시지/test ID에 선택자를 한정하고 두 신규 UI 반례를 회귀에 추가할 수 있다. 배열의 첫 alert를 무조건 고르는 식으로 숨기지 않는다.
