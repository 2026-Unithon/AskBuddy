# 평가 자료 — 넣는 법

> 이 폴더는 **Git 제외**다 (`SPLIT.md` 만 예외).
> 브랜드명·상호·로고를 파일명·JSON·DB 어디에도 쓰지 않는다. 익명 slug 만 쓴다.

## 1. 파일을 넣는다

```
store-a/
  sources/
    video/   *.mp4        제조 영상, 매장 둘러보기
    voice/   *.m4a *.mp3  구두 인수인계 녹음
    scan/    *.pdf *.jpg  레시피북, 공지·규칙
    kakao/   *.txt        점주–알바 대화 내보내기
  truth/
    facts.json            사실 정답지 (아래 3번)
  manifest.json           자료 목록 (아래 2번)
```

**4개 유형을 전부 넣는다.** 하나라도 빠지면 그 유형의 추출 손실을 모른다.
`VOICE`·`KAKAO` 가 없으면 직접 만들어도 된다 — 점주 역할로 녹음하고 대화를 작성한다.
정답을 우리가 아는 자료라 사실 정답지 쓰기가 쉽고, 충돌을 의도적으로 심을 수 있다.

### 아무거나 넣으면 안 된다

| 조건 | 이유 |
|---|---|
| **같은 한 매장의 자료** | `store-a` 는 매장 하나다. 자료마다 다른 매장이면 값이 달라도 '진짜 충돌' 이 아니라 '다른 매장 정보' 라서 병합 검증이 무너진다 |
| **업무 지식이 들어있을 것** | 카드가 0장 나오면 추출 손실의 분모가 0 이다 |
| **레시피만 있으면 안 됨** | 한 카테고리만 테스트된다. 자동 분류와 `기타` 처리를 검증하지 못한다 |

### 유형별로 담을 내용

| 유형 | 담을 것 | 안 되는 것 |
|---|---|---|
| `VIDEO` | 제조 과정, 매장 둘러보기(물건 위치), 기계 조작 | 잡담, 브이로그 |
| `SCAN` | 레시피북 **+ 공지·규칙·근무수칙**(레시피 아닌 것 필수) | 내용 없는 페이지 |
| `VOICE` | 구두 인수인계 — 오픈·마감 절차, 발주, 손님 응대 | 대본 낭독 (자연스러운 말투여야 STT 변형이 나온다) |
| `KAKAO` | 점주–알바 대화 — 지시, 질문답변, **번복된 지시** | 이모티콘만 있는 대화 |

### 일부러 설계해야 하는 것

"아무거나" 로는 절대 안 나온다. 13.3 병합·충돌 검증의 재료다.

1. **겹침** — 같은 대상을 두 자료가 다른 깊이로 다룬다.
   영상엔 제조 순서만, 레시피북엔 수량만 → **한 카드로 합쳐져야 한다**
2. **충돌** — 같은 값이 자료마다 다르다.
   녹음 "라떼 우유 250 정도" vs 레시피북 "275ml" → **`CONFLICT` 로 올라가야 한다**
   자연 발생이 없으면 녹음할 때 일부러 틀리게 말한다. 현장에서 늘 일어나는 일이다
3. **번복** — 카톡에서만 나오는 실패.
   "우유 3번 냉장고에" → 며칠 뒤 "아까 그거 2번으로 옮겼어" → 최신이 이겨야 한다

### 최소 체크리스트

- [ ] 4개 유형 전부
- [ ] 레시피 아닌 자료 최소 1개 (공지·규칙·마감절차)
- [ ] 카테고리 3개 이상 커버
- [ ] 겹치는 대상 최소 3개
- [ ] 의도적 충돌 최소 2개
- [ ] 카톡에 번복 1개

분량 감각: 영상 1~2개 · 레시피북 1부 + 공지 1장 · 녹음 5~10분 · 카톡 50~100줄
→ 카드 30장 정도가 나온다.

## 2. `manifest.json`

자료 하나당 한 항목.

| 필드 | 값 |
|---|---|
| `source_key` | 사실 정답지가 참조할 식별자. 매장 안에서 유일 |
| `type` | `VIDEO` `VOICE` `SCAN` `KAKAO` |
| `file` | `manifest.json` 기준 상대 경로 |
| `authority` | `OWNER_ANSWER` > `RECIPE_BOOK` = `NOTICE` > `OTHER` |

`authority` 는 값이 충돌했을 때 **기본 제안**을 고르는 참고값이다.
자동 확정 근거가 아니다 — 레시피북이 오래됐을 수도 있다.

## 3. `truth/facts.json` — 사실 정답지

**원본을 사람이 읽고, 거기 담긴 업무 사실을 하나씩 적는다.**
이게 `E-O0` 추출 손실의 채점 기준이다. 카드를 보고 적으면 안 된다 —
그러면 추출이 놓친 것을 영원히 못 찾는다. **원본만 보고 적는다.**

| 필드 | 뜻 |
|---|---|
| `fact_id` | `a-0001` 형식. 안 바뀐다 |
| `subject` | 대상. 예: `카페라떼` |
| `variant` | 규격. 예: `HOT` `ICE` `L`. **없으면 빈 문자열이 아니라 생략** |
| `attribute` | 속성. 예: `스팀우유량` |
| `value` | 값. 예: `275ml` |
| `must_have` | 이게 빠지면 치명적인가 |
| `source_key` | 어느 자료에서 나왔나 |
| `locator` | 어디서 나왔나. `PAGE`+`page` / `TIMESTAMP`+`timestamp_sec` |

머리에 넣을 것 셋:

- **같은 이름 다른 규격은 반드시 `variant` 로 가른다.**
  HOT 275ml 와 ICE 225ml 는 **다른 사실**이다. 합쳐지면 안 된다.
- **여러 자료에 걸친 것을 일부러 남긴다.**
  영상엔 제조 순서만, 레시피북엔 수량 — 이게 병합 검증의 재료다.
- **누가 정답을 확정했는지 남긴다.** `judged_by`, `judged_at` 과 함께 `owner_confirmed` 를 채운다.

  | 값 | 뜻 |
  |---|---|
  | `true` | **실제 점주가 확인했다.** 매장 사실 관계의 정본 |
  | `"TEST"` | **팀이 자체 판정했다.** 점주 확인이 아니다 |
  | `false` | 아직 확인 전. 채점에 쓰지 않는다 |

  `"TEST"` 로 낸 수치는 **"우리가 정답이라고 본 것 대비"** 이지 "매장 사실 대비" 가 아니다.
  리포트와 발표 자료에 이 한계를 반드시 함께 적는다. 없는 검증을 있는 것처럼 쓰지 않는다.

## 4. 검증한다

```bash
cd api && python scripts/check_eval_data.py --store store-a
```

라벨링 도중에도 자주 돌린다. 다 쓰고 나서 형식이 틀린 걸 알면 다시 해야 한다.

## 5. 매장을 만든다

```bash
cd api && python scripts/seed_eval_stores.py
```

`eval-a` ~ `eval-e` 가 생긴다. 분할은 `SPLIT.md` 가 정본이다.
